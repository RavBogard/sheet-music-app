<acceptance_criteria>

## AC-1: Successful redemption writes an audit doc
```gherkin
Given a valid, unexpired, unused setup code
When the bridge GETs /api/bridge/setup-code?code=X
Then a new doc is created at bridge-redemptions/{autoId} with:
  code, createdBy (from the redeemed code doc), redeemedAt (server Timestamp),
  redeemerIp (from x-forwarded-for or x-real-ip), redeemerUserAgent, success:true
And the audit write happens inside or immediately after the same transaction that marks the code used
```

## AC-2: Successful redemption triggers an admin email
```gherkin
Given a successful redemption and RESEND_API_KEY configured
When the audit doc is written
Then sendBridgeRedemptionAlert() is called with redeemerIp, UA, timestamp, code
And the email subject is "Bridge credentials redeemed — centralreform.live"
And the body names the timestamp, IP, UA, and "if this wasn't you, rotate FIREBASE_PRIVATE_KEY now"
```

## AC-3: Email failure must not fail the redemption
```gherkin
Given RESEND_API_KEY is not configured (or Resend returns an error)
When a successful redemption occurs
Then the credentials are still returned to the caller (200)
And the audit doc is still written (Firestore is the source of truth)
And the email failure is logged but not surfaced to the bridge
```

## AC-4: Failed redemptions do NOT write audit or send email
```gherkin
Given an invalid/expired/already-used code
When the GET is processed
Then no bridge-redemptions doc is created
And no email is sent
And the existing 4xx response is unchanged
```

## AC-5: Firestore rules deny client access to the audit collection
```gherkin
Given any authenticated client
When it attempts to read or write bridge-redemptions/*
Then the request is denied by rules (only Admin SDK writes; admin panel reads server-side if ever needed)
```

      2. Fetch createdBy from the code doc (we already read it in the transaction via `data.createdBy`; pass it out of the tx closure into a variable captured in outer scope).

      3. Fire the audit write (best-effort; log on failure but do NOT fail the redemption):
         await db.collection("bridge-redemptions").add({
             code,
             createdBy,
             redeemedAt,
             redeemerIp,
             redeemerUserAgent,
             success: true,
         }).catch(err => logger.error("bridge audit write failed:", err))

      4. Fire the email (best-effort, fire-and-forget is acceptable since Vercel functions now support graceful shutdown):
         sendBridgeRedemptionAlert({ code, redeemedAt, redeemerIp, redeemerUserAgent })
             .then(r => { if (!r.ok) logger.warn("bridge alert email:", r.reason) })
             .catch(err => logger.error("bridge alert email threw:", err))

      5. Return credentials as before.

    Place these AFTER the `if ("error" in redeemed)` early-return so failed redemptions never touch them (AC-4).

    Do NOT:
      - Block the response on email send (fire-and-forget)
      - Leak createdBy out of the transaction via shared mutable state — use a local variable reassignment inside the tx callback with `let createdBy: string | undefined` declared just above
      - Log the raw private_key
  </action>
