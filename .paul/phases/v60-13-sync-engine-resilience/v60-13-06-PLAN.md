<objective>

## Goal
Stop the SetlistGridHydrator from re-firing its Dexie writes on the second
Firestore snapshot emission (the one with `metadata.fromCache=false` that
follows the cached emission), so editing the setlist no longer "auto-refreshes"
under Daniel's hands shortly after page load.

## Purpose
Daniel UAT 2026-05-13 (multiple session reports): "when i'm editing a setlist,
it is doing an auto refresh thing early on after loading that is a real pain,
because i'll be in the middle of editing something, and it will refresh."

Hypothesis: the hydrator processes BOTH snapshot emissions (cached, then
network) as authoritative writes to Dexie. The second write triggers a
useLiveQuery re-render in SetlistGrid → looks like a "refresh" mid-edit.

Root cause class: **content-equality dedup missing** — server data hasn't
materially changed between the cached and network snapshot, but we still
write it through, causing downstream useLiveQuery subscribers to re-render.

## Output
- SetlistGridHydrator dedup at the hydrate-write site: skip writes when the
  incoming server payload is content-equal to what's already in Dexie
- Test coverage: hydrator with two identical-content snapshot emissions
  produces ONE Dexie write, not two
- `.paul/phases/v60-13-sync-engine-resilience/v60-13-06-SUMMARY.md`

</objective>
