<objective>
## Goal
Surface engine `'conflict'` state to the user as a blocking, accessible reconciliation modal that lists every `failed`-status outbox row, shows a per-row diff (your edit vs. server's current value), and routes the user's "Keep mine" / "Take theirs" choice through `engine.resolveConflict()` so the outbox drains cleanly. Production `/setlists/[id]` no longer silently swallows version mismatches — every losing write produces a visible, explicitly resolvable prompt.

## Purpose
v50-06-01 made the substrate honest: every track-update applyEdit threads `expectedUpdatedAt`, the production adapter re-reads server timestamps, and a real two-writer race produces a `VersionMismatchError` → `'conflict'` state → addressable `failed` outbox row. None of that is visible to the user yet. v50-06-02 closes that gap. This is the part of the v5.0 rewrite that earns the word "bulletproof" — the band can never again lose an edit without knowing it lost.

## Output
- `<ReconciliationProvider>` mounted at `/setlists/[id]`, owning the modal and the resolution flow
- Modal subscribes to engine state via `useSyncStatus(s => s.state === 'conflict')` + reads failed outbox rows via `useLiveQuery`
- Per-row diff (one card per failed row) listing every patched field with **Your version** / **Their version** + `mine`/`theirs` radio
- "Resolve all and save" applies each choice via `engine.resolveConflict(localId, choice, { newExpectedUpdatedAt })`
- "Cancel" closes the modal, leaves outbox in `'conflict'` (SyncIndicator continues to flag it)
- Property-failures harness gains coverage for both `'mine'` and `'theirs'` resolution branches (full round-trip — drain succeeds after `'mine'` re-queue with refreshed precondition; row vanishes after `'theirs'`)
- jest-axe a11y pass at zero violations across closed / open-one / open-many states
- `.paul/phases/v50-06-concurrent-edit-safety/v50-06-02-SUMMARY.md` documenting per-row scope decision (vs ARCHITECTURE.md §6.9 per-field aspiration), what shipped, what deferred to v50-06-03+
</objective>

  <decision>Per-row vs per-field reconciliation granularity for v50-06-02</decision>
  <context>
    ARCHITECTURE.md §6.9 shows per-field radio choice ("Key: ◯ Keep mine ● Take theirs", "Lead: ◯ Keep mine ● Take theirs") so the user can accept some fields and reject others granularly. The v50-06-01 substrate API is per-row: `engine.resolveConflict(localId, 'mine'|'theirs', opts)` either re-queues the WHOLE failed payload with a refreshed precondition, or deletes the WHOLE row. There is no per-field merge in the engine.

    Implementing per-field would require either:
    (a) A new engine API like `resolveConflict(localId, mergedPayload, opts)` that overwrites the outbox row's payload before re-queuing — non-trivial, expands engine surface, deserves its own plan.
    (b) UI-side merge: read the failed row, build a merged patch from the user's per-field choices, call `applyEdit('update', collection, docId, mergedPatch, freshUpdatedAt)` directly, then `resolveConflict(localId, 'theirs')` to discard the original failed row. Doable but couples UI to engine internals and double-writes (one new outbox row + one delete).

    Per-row keeps this plan tight (~3 tasks), preserves the substrate boundary, and ships a working modal. Per-field is an honest follow-up — the modal copy can say "your edit will replace the remote version" so the user knows what they're choosing.
  </context>
  <options>
    <option id="per-row-now">
      <name>Per-row "Keep mine / Take theirs" — ship in v50-06-02; per-field deferred</name>
      <pros>Matches substrate API; 2-3 task plan; unblocks v50-06-03 (cross-leader live-edit). Diff display is still per-field (informational), only the choice is per-row. Mirrors GitHub's "Use mine / Use theirs" merge UI which users recognize.</pros>
      <cons>User cannot keep their key change while accepting the other tab's lead change in one motion — they have to pick whole-row, then re-edit the field they wanted to keep from the other side. Acceptable for v1; the band's actual conflict frequency is low and the per-row outbox-grain matches their mental model ("save my Aleinu edit OR take the other tab's").</cons>
    </option>
    <option id="per-field-now">
      <name>Per-field radios — ship the full ARCHITECTURE.md §6.9 spec in v50-06-02</name>

      <cons>Requires either new engine API (option a above) or UI-side merge plumbing (option b). Either route expands plan to 4-5 tasks, blurs the substrate boundary just stabilized in v50-06-01, and risks shipping less polished code under time pressure. The "feels easier than Sheets" goal of v5.0 is served better by a working per-row prompt now than a half-finished per-field prompt.</cons>
    </option>
