<objective>
## Goal
Rework the cell-dropdown picker across all 6 sites (Key / Lead / Type / AddRowPlaceholder / ChartBindPopover / BatchActionBar Bulk) so that on iPad/touch:
- Tapping a cell opens an **anchored popover** (NOT a bottom Sheet)
- The system keyboard does NOT appear automatically for discrete-value pickers (Key, Type, Bulk-Key, Bulk-Type, AddRow). The keyboard MAY appear for free-text / search pickers (Lead with "+ Add custom", ChartBind for song search) only when the user explicitly taps into a search field.
- Key picker specifically: chromatic order (C, C♯/D♭, D, D♯/E♭, E, F, F♯/G♭, G, G♯/A♭, A, A♯/B♭, B); Major | Minor tabs inside the picker; default tab inferred from current value.

## Purpose
Daniel's UAT 2026-04-27 surfaced this as Issue 2 — "I click key and it opens a whole new screen on the bottom right with the keyboard open. Yuck. Also: the order of the keys don't make sense." This is the band-onboarding gate: tablet-first app, picker yuck blocks tablet-first work. Fix once at the wrapper level so all 6 dropdown sites benefit uniformly. Per the v5h-01 postmortem, this is action item #3 (Issue 2 routing) resolved.

## Output
- `TouchOrPopover` rewritten to always-anchored Popover (Sheet branch removed)
- `DropdownCell` extended with discrete-mode (no auto-keyboard on touch) + searchable-mode (current behavior; keyboard via explicit field tap on touch)
- `KeyCell` rewritten with structured 12-major + 12-minor chromatic data + Radix Tabs
- All existing passing tests stay green; new tests cover Major/Minor tab switch + chromatic order + no-keyboard-on-touch invariant
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>How does the Key picker present Major | Minor switching, AND should ChartBind suppress its initial keyboard on touch?</decision>
  <context>
Two micro-decisions to lock at APPLY entry, after /ui-ux-pro-max consultation:

(a) **Major | Minor switching** — three viable presentations:
  - Tabs inside the popover (Radix Tabs at top of content)
  - Segmented control at top of popover (custom button-pair, smaller footprint)
  - Major shown by default with a "Show minor" link/toggle expanding minor below

(b) **ChartBind keyboard on iPad** — currently the popover opens with a focused search input → keyboard pops. Two options:
  - Suppress: open with NO focused input on touch; user taps the search field to bring up keyboard (parity with the discrete pickers' "no keyboard by default" rule)
  - Keep: search-IS-the-feature for chart binding; keyboard appearing immediately is a feature not a bug; preserve current behavior on touch

Both are visual / UX decisions and benefit from /ui-ux-pro-max input.
  </context>
  <options>
    <option id="tabs-suppress">
      <name>Tabs for Major/Minor + Suppress ChartBind keyboard on touch</name>
      <pros>Symmetric with discrete pickers (no keyboard by default); Tabs scale well to future picker variants; clean visual hierarchy</pros>
      <cons>Tab-bar adds vertical pixels; ChartBind users must tap twice to start searching on touch</cons>
    </option>
    <option id="tabs-keep">
      <name>Tabs for Major/Minor + Keep ChartBind keyboard on touch</name>
      <pros>Tabs for keys; ChartBind retains "type to find a song" immediacy; minimal behavior change for ChartBind users</pros>
      <cons>ChartBind remains slightly inconsistent with the "no keyboard" rule; one extra rule to remember</cons>
    </option>
    <option id="segmented-suppress">
      <name>Segmented control for Major/Minor + Suppress ChartBind keyboard on touch</name>
      <pros>Smaller footprint than Tabs; uniform "no keyboard by default" across all 6 sites</pros>
      <cons>Segmented control is a custom component; less discoverable than tabs for non-technical users</cons>
    </option>
  </options>
  <resume-signal>Select: tabs-suppress, tabs-keep, or segmented-suppress (default recommendation: tabs-suppress — symmetry + future-proofing wins over the one-extra-tap cost on ChartBind).</resume-signal>
</task>
