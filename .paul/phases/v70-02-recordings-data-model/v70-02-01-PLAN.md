<objective>

## Goal
Lay the data-model foundation for the v7.0 recordings domain: a NEW `recordings/{id}` Firestore collection (NOT an embedded array), its `Recording` TypeScript type, a Firebase Storage path convention for recording audio files, Firestore security rules + a composite index for the recording-by-song query, and emulator-backed rules coverage. This is purely the foundation — no upload route, no UI, no playback (those land in v70-03 / v70-06).

## Purpose
v7.0 milestone constraints #1/#4/#5: recordings are stored in Firebase Storage, attributed via a free-form `notes` field, and modeled as a NEW top-level collection with a `songId?` foreign key — not embedded on song or setlist docs. v70-02 is the Wave 1 foundation: v70-03 (per-track recording-bind UI + inline `<audio>` playback) and v70-06 (recording-match + pre-creates `recordings/*` docs) both build directly on the type, rules, and Storage paths defined here. This is an HFG-relevant data-layer phase — it ships emulator-backed rules coverage, no clause-(b) waiver (memory `feedback_harness_real_firestore`; HFG counter must stay 0/3).

## Output
- `Recording` interface in `src/types/models.ts` — `{ id, songId?, title, fileName?, mimeType?, storagePath, durationSeconds?, notes?, createdAt, createdBy }`
- `getRecordingStoragePath(recordingId, ext)` exported helper in `src/lib/firebase-storage.ts` — `recordings/{recordingId}.{ext}` convention
- `match /recordings/{recordingId}` block in `firestore.rules` — read `isMember()`, write band-leader/admin (mirrors `songs/{songId}`); deployed to production
- Composite index `recordings: songId ASC, createdAt DESC` in `firestore.indexes.json` — for the "recordings for this song, newest first" query v70-03/v70-06 will run; deployed
- `src/lib/recordings/__tests__/firestore-rules-recordings.emulator.test.ts` — read × write × auth-context matrix (mirrors the v60-12-01 tracks rules test)
- `.paul/phases/v70-02-recordings-data-model/v70-02-01-SUMMARY.md`

</objective>

    2. **src/lib/firebase-storage.ts** — add an EXPORTED helper:
       ```
       /** v70-02: Storage path convention for recording audio files.
        *  Recordings live under their own top-level `recordings/` prefix,
        *  keyed by recording doc id — parallel to library/{fileId} for charts. */
       export function getRecordingStoragePath(recordingId: string, ext: string): string {
           const clean = ext.replace(/^\.+/, '')           // tolerate caller passing '.mp3' or 'mp3'
           if (!clean) return `recordings/${recordingId}`
           if (recordingId.toLowerCase().endsWith(`.${clean.toLowerCase()}`)) {
               return `recordings/${recordingId}`           // no double-extension (mirrors getStoragePath guard)
           }
           return `recordings/${recordingId}.${clean}`
       }
       ```
       Place it adjacent to the existing module-private `getStoragePath` so the
       two path conventions sit together. Do NOT modify `getStoragePath`,
       `getCandidatePaths`, or any existing function — this is purely additive.
    3. Avoid: embedding recordings on song/setlist docs (constraint #5 — NEW
       collection only); reusing the `library/` Storage prefix (recordings get
       their own `recordings/` namespace so the chart sync engine never touches
       them); making `songId` required (a recording can exist before it is linked).
  </action>
