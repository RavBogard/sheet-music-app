<objective>
## Goal
Kill the cold-load + sign-in race that lets the proxy bounce a signed-in user to `/login` just because the `__session` cookie hadn't landed yet when the first navigation fired. After this plan, a successful sign-in or a cold page load on a gated route should deterministically land on the destination without looping through `/login`.

## Purpose
Wave 2B traced a ~125ms window after `onAuthStateChanged` where `profileReady` resolves from the Firestore cache while `sessionReady` waits on the `/api/auth/session` POST. Any click (or pre-existing nav that arrived mid-sync) during that window hits a proxy with no cookie, gets redirected to `/login`, and if the `Set-Cookie` hasn't been applied by the time `/login`'s useEffect fires `router.replace('/setlists')`, we loop. The fix is not an additional layer — it's removing the race: await the cookie before dropping `loading=false`, force a middleware re-eval once it lands, and make the cold-load refresh path actually fire regardless of throttle state.

## Output
- `auth-context.tsx` `onAuthStateChanged` callback awaits the session cookie POST before flipping `loading=false`. (Sequencing is implicit today via `sessionReady`/`profileReady` flags; the flip still fires even if the POST rejected — we add a `router.refresh()` on success so middleware sees the fresh cookie.)
- After a successful `syncSessionCookie`, trigger `router.refresh()` so any already-rendered page re-evaluates with the now-valid cookie. This self-heals users who landed on `/login` mid-race.
- Cold-load refresh on mount fires unconditionally when the app first loads with a Firebase user, bypassing the 24h `crc_session_refreshed_at` throttle. The throttle remains in force on subsequent `visibilitychange` events (its original purpose).
- Login page: disable the Google button while `loading=true` so users don't retrigger the sign-in flow mid-sync.
- Login page: on sign-in success but session POST failure, surface a concrete error state (not silent loop-back).
- Regression test for the cold-load race where feasible (full happy-path test; edge cases covered in P10-05 Playwright).
- `10-02-SUMMARY.md`.
</objective>

<task type="auto">
  <name>Task 2: Cold-load refresh bypasses throttle on first mount</name>
  <files>src/lib/auth-context.tsx</files>
  <action>
    Currently the mount-refresh useEffect (lines ~232–252) calls `maybeRefreshSession()`, which reads `crc_session_refreshed_at` from localStorage and skips if less than 24h. That's correct for visibility-change events (don't spam the server), but wrong for mount — a stale-but-recent throttle flag shouldn't block the very first sync after a cold reload.

    Refactor:
      - Split into two helpers: `refreshOnMount()` (always runs the POST once) and `maybeRefreshOnVisibility()` (the existing throttled version).
      - On mount, call `refreshOnMount()` directly (bypass throttle but still write the timestamp so the visibility throttle is seeded).
      - Keep the visibilitychange listener using the throttled version.

    Guard: if there's no current `user` yet, don't fire. The effect already checks for `user`; keep that.

    Do NOT:
      - Remove the visibility throttle — it has real purpose (mobile users toggling tabs every few minutes).
      - Fire on every render. Once per mount, guarded by a ref if needed.
  </action>
  <verify>`npx tsc --noEmit` clean; manually trace the branch in code review</verify>
  <done>AC-3 satisfied</done>
