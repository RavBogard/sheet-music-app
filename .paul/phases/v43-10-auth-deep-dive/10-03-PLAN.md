<objective>
## Goal
Make the client-side drift-repair chain reliable and diagnosable. Today's chain is fire-and-forget with per-step warn logs in different shapes, so a transient failure on step 1 can leave the user on stale state with no visible signal and no retry. After this plan: each step is retried with backoff, every outcome is logged with a consistent `[drift]` tag, and the chain's overall result is exposed for future surfacing.

## Purpose
FINDINGS-v2 RC-3: the four-step drift chain (sync-claims → getIdToken(true) → syncSessionCookie → refresh-session) runs on every profile-listener callback where `profile.role !== claim.role`. Transient network or server hiccups silently leave the user partially-repaired, and the only recovery is the next profile event (which may not come without a navigation). This plan wraps every step with exponential backoff and consistent telemetry, and extracts the chain into a testable module.

## Output
- `src/lib/drift-repair.ts` — a single exported `repairDrift(user)` function. Internally runs the four steps with up to 3 attempts each (0ms, 200ms, 800ms backoff). Returns a structured summary `{ syncClaims, idTokenRefresh, sessionCookie, refreshSession }` each `'ok' | 'failed'`.
- Every step logs with a consistent prefix: `[drift] step=syncClaims attempt=1 outcome=ok` (and `outcome=failed error=...` on failure). Uniform shape makes Vercel log search trivial.
- `src/lib/auth-context.tsx` drift branch swapped to call `repairDrift(currentUser)`. Preserves the current ordering (ID token refresh before cookie sync, etc.). `router.refresh()` still fires once the chain returns.
- The chain is now a true awaited sequence — each step's result gates whether it makes sense to run the next (e.g., if ID token refresh fails three times, don't bother calling sync-session, surface the failure to logs cleanly).
- Unit tests that drive the function against mocked fetch + mocked Firebase user, covering: all-green, transient failure on each step, terminal failure on each step.
- `10-03-SUMMARY.md`.
</objective>

<acceptance_criteria>

## AC-1: repairDrift returns a structured summary
```gherkin
Given a user with a role/claim mismatch
When repairDrift(user) is called
Then it runs the four steps in order (syncClaims, idTokenRefresh, sessionCookie, refreshSession)
And it returns an object with one 'ok'|'failed' value per step
```

## AC-2: Each step retries up to 3 times with exponential backoff
```gherkin
Given sync-claims fails with a network error on the first attempt
When repairDrift runs
Then it waits ~200ms and retries
And on second failure waits ~800ms and retries
And returns 'ok' if any attempt succeeds, 'failed' if all three fail
```

## AC-3: Every attempt logs with a consistent `[drift]` prefix
```gherkin
Given any step runs
Then logs include: '[drift] step=<name> attempt=<n> outcome=<ok|failed>'
And failure logs additionally include the error message (trimmed)
And success logs at attempt > 1 include 'recovered-after=<ms>' for observability
```

## AC-4: Terminal failure in an earlier step short-circuits later ones
```gherkin
Given sync-claims fails all 3 attempts
When repairDrift continues
Then idTokenRefresh is skipped (would produce a stale token anyway)
And sessionCookie AND refreshSession are skipped
And the return value has step=failed for the remainder with reason='skipped-prereq'
```
Note: "skipped" is distinct from "failed" — add a third outcome `'skipped'`.

## AC-5: No behavioral regression on happy path
```gherkin
Given all four steps succeed on first attempt
When repairDrift runs
Then cumulative runtime is < 500ms (no extra waits)
And one log line per step is emitted
```

## AC-6: auth-context delegates to repairDrift
```gherkin
Given the existing profile-listener drift detection fires
When the code path reaches the drift-repair chain
Then it calls repairDrift(currentUser) exactly once per drift event
And router.refresh() fires after the chain returns (same as 10-02)
```

  <name>Task 1: Extract repairDrift module</name>
  <files>src/lib/drift-repair.ts (new)</files>
  <action>
    Create the new module with this public surface:

      ```ts
      import type { User } from "firebase/auth"

      export type StepOutcome = 'ok' | 'failed' | 'skipped'

      export interface DriftSummary {
          syncClaims: StepOutcome
          idTokenRefresh: StepOutcome
          sessionCookie: StepOutcome
          refreshSession: StepOutcome
      }

      export async function repairDrift(user: User): Promise<DriftSummary>
      ```

    Internal retry helper: `async function withRetry(step: string, fn: () => Promise<boolean>): Promise<'ok' | 'failed'>` — up to 3 attempts at 0ms, 200ms, 800ms. Logs one line per attempt.

    Step bodies (each returns boolean 'did-work'):
      - syncClaims: `apiFetch('/api/auth/sync-claims', { method: 'POST' })` → ok if res.ok
      - idTokenRefresh: `user.getIdToken(true)` → ok if it resolves with a truthy string
      - sessionCookie: inline the existing `syncSessionCookie` logic (import from auth-context OR move the function here and re-import from auth-context; preferred: move it here since this module becomes the drift home)
      - refreshSession: `apiFetch('/api/auth/refresh-session', { method: 'POST' })` → ok if res.ok

    Short-circuit rule (AC-4): if syncClaims is 'failed' → idTokenRefresh, sessionCookie, refreshSession = 'skipped'. If idTokenRefresh is 'failed' → sessionCookie + refreshSession = 'skipped'. sessionCookie failure does NOT skip refreshSession (they're independent mint paths).

    Logging shape (AC-3):
      ```
      [drift] step=syncClaims attempt=1 outcome=ok
      [drift] step=syncClaims attempt=1 outcome=failed error="network"
      [drift] step=sessionCookie attempt=2 outcome=ok recovered-after=210ms
      ```
    Use `logger.info` for ok / recovered, `logger.warn` for failed attempts, `logger.error` for terminal 3-strikes failure.

    Do NOT:
      - Add an outer try/catch that swallows Promise rejection — let the function's own Promise resolve cleanly with the summary.
      - Introduce jitter on the backoff (deterministic 200ms/800ms is fine; jitter only matters with thundering herd).
      - Expose retry counts as part of the return (logs carry that; summary stays simple).
  </action>
