<objective>
## Goal
Render the v53-03 AddBar (split-button "+ Song" CTA + chevron 5-tile popover) as a coarse-pointer-only sticky-bottom variant that stays visible while the row list scrolls, AND hides itself when the iOS/iPadOS virtual keyboard opens (so it never overlaps an active inline-edit field). Desktop fine-pointer surfaces keep the current in-flow AddBar verbatim.

## Purpose
Closes the third and last Wave 4 deferral folded forward from v5.4 (originally v53-03 CONTEXT Q1, deferred at v53-03 plan-time as "v54-?? Mobile AddBar variant", folded forward at v5.4 close into v6.0 as v60-10). Daniel's primary surface is iPad — currently a long setlist scrolls the AddBar off-screen, forcing a scroll-to-bottom every time he wants to add a row. On the iPad in landscape this is a multi-second friction point that the old pre-v50-02 AddBar solved via sticky-bottom positioning. The keyboard-hide guard preserves text-cell editing on coarse pointers — without it the sticky bar would obscure the bottom row's inline editor when the iPad keyboard pops.

## Output
- Sticky-bottom AddBar variant active on `(pointer: coarse)` viewports (iPad + phone) — chosen approach locked at the /ui-ux-pro-max checkpoint:decision (fixed-bottom vs sticky-within-scroll-container vs floating-FAB).
- `useVirtualKeyboardOpen()` hook in `src/hooks/use-virtual-keyboard-open.ts` — `visualViewport.resize` listener with SSR + JSDOM guards.
- Coarse-pointer sticky variant hides itself when `useVirtualKeyboardOpen()` is true (and re-shows when keyboard dismisses).
- Bottom-padding spacer on the row-list container so the last MobileRowCard stays tap-accessible when sticky AddBar is visible.
- New + extended jest-axe + behavioral tests covering both render paths (fine: in-flow / coarse: sticky / coarse + keyboard: hidden).
- SUMMARY.md at `.paul/phases/v60-10-mobile-addbar-variant/v60-10-01-SUMMARY.md`.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>Sticky AddBar CSS strategy + hide-mechanism for coarse pointers</decision>
  <context>
    Three viable shapes for the coarse-pointer sticky variant. Each has tradeoffs against z-index conflicts (ChartBindDialog / BatchActionBar removed but old z-index ladder remnants exist), the v50-05-04 long-press contextmenu surface on rows, and last-row tap-target preservation. /ui-ux-pro-max consultation MUST run before this decision locks — invoke `/ui-ux-pro-max` if not already loaded and have it weigh in on the strategy and the visibility primitive (display:none vs visibility:hidden vs aria-hidden+translate).
  </context>
  <options>
    <option id="fixed-bottom">
      <name>Option A: `position: fixed` viewport-pinned</name>
      <pros>
        - Simplest CSS — `fixed bottom-0 left-0 right-0 z-40` only on coarse pointers
        - Works regardless of the SetlistGrid scroll-container hierarchy (current layout is whole-page scroll, no fixed-height container)
        - No layout-shift risk when content height changes
      </pros>
      <cons>
        - Requires explicit bottom-padding spacer on the row-list container (≥ sticky bar height + 8px) to satisfy AC-4
        - May overlap any future absolute-positioned popovers; ChartBindDialog is centered so safe today
        - On iOS Safari with the URL bar showing, `fixed bottom-0` may sit ABOVE the chrome-bottom-bar — verify with Daniel browser-smoke
      </cons>
    </option>
    <option id="sticky-in-scroll-container">
      <name>Option B: `position: sticky bottom-0` within a sized scroll container</name>
      <pros>
        - Auto-respects container width and parent layout (no full-width override)
        - No `position: fixed`-style overflow-into-viewport problems
        - No extra spacer needed if the sticky element is the last flex child of the scroll container
      </pros>
      <cons>
        - SetlistGrid is NOT a fixed-height scroll container today — converting it to one is a structural change (introduces a `height: 100dvh - header` shell and an inner overflow-y scroller) that risks regressing other surfaces (modal positioning, drag-and-drop autoscroll, etc.)
        - Larger LOC delta; more downstream test impact
      </cons>
    </option>
    <option id="floating-fab">
      <name>Option C: Compact FAB-only on coarse pointers (chevron menu folded into a single circular button)</name>
      <pros>
        - Smallest viewport footprint; no spacer needed
        - Common mobile-app pattern (Material FAB)
      </pros>
      <cons>
        - Diverges from v53-03 split-button shape — loses the "+ Song" primary CTA visibility advantage Daniel just got back in v53-03
        - Increases tap-to-add cost (now FAB tap → menu pick instead of one-tap "+ Song")
        - Track A precedent (porting old AddBar shape back) argues against shape divergence
      </cons>
    </option>
  </options>
  <resume-signal>Select: fixed-bottom | sticky-in-scroll-container | floating-fab. Also specify the visibility primitive for AC-3 (display:none | visibility:hidden | translate-off-screen).</resume-signal>
</task>
