<objective>
## Goal
Make Firebase Storage the sole file-serving source. Google Drive becomes intake-only (sync source, metadata, saves). Fix PDF health scanner 429s.

## Purpose
The Storage-first-Drive-fallback pattern causes complexity and 429s when Drive rate limits hit. Since the hourly sync already copies files to Storage, we can remove the fallback entirely — simpler, faster, no 429s.

## Output
- All library files confirmed in Firebase Storage
- file-fetcher serves from Storage only (no Drive fallback)
- PDF health scanner uses Storage-direct checks (no API round-trip)
- Sync engine copies all files per run (no 20-file cap)
</objective>

    2. Keep the DriveClient import removal

    Updated logic:
    ```typescript
    export async function fetchFileById(fileId: string, mimeType?: string): Promise<FetchedFile | null> {
        const storageResult = await downloadFromStorage(fileId, mimeType)
        if (storageResult.success) {
            return {
                buffer: storageResult.data.buffer,
                contentType: storageResult.data.contentType,
                source: 'firebase-storage',
            }
        }
        // No Drive fallback — file must be in Storage (synced from Drive)
        if (storageResult.reason === 'network') {
            logger.warn(`[FileFetcher] Storage error for ${fileId}: ${storageResult.message}`)
        } else {
            logger.warn(`[FileFetcher] File not in Storage: ${fileId} — run a sync to copy from Drive`)
        }
        return null
    }
    ```

    7. Remove the DriveClient import and EXPORTABLE_GOOGLE_TYPES constant
  </action>

<task type="auto">
  <name>Task 3: Fix PDF Health Scanner — Storage-Direct Checks</name>
  <files>src/lib/pdf-health-scanner.ts, src/components/library/PDFHealthScanner.tsx</files>
  <action>
    The health scanner currently fetches each PDF through the browser-side API endpoint, which goes through the rate-limited server. Instead, check Storage directly from the server side.

    **Problem:** The scanner runs client-side (browser). It can't directly access Firebase Storage server SDK.

    **Solution:** Create a new API endpoint `/api/library/health-scan` that:
    1. Accepts a POST with `{ fileIds: string[] }`
    2. Server-side: for each file, calls `downloadFromStorage(fileId)` and attempts pdfjs parse
    3. Returns results array with status per file
    4. Processes sequentially with 100ms delay between files

    **Client-side changes to PDFHealthScanner.tsx:**
    1. Instead of fetching each file via `/api/drive/file/`, POST all file IDs to `/api/library/health-scan`
    2. Use streaming or chunked approach: send batches of 10 file IDs at a time
    3. Update progress based on batch responses

    **Alternative simpler approach:** Keep client-side scanning but add a 200ms delay between fetches. The 429s come from Drive rate limits via the API — once file-fetcher is Storage-only (Task 2), the API no longer hits Drive, so 429s from Drive go away. The only remaining rate limit is the app-level 60 req/min.

    **Go with the simpler approach:**
    1. In `pdf-health-scanner.ts`, add a `await sleep(200)` between sequential file scans
    2. This spaces out 180 files over ~36 seconds instead of rapid-fire
    3. With Storage-only serving (Task 2), no Drive API calls = no Drive 429s
    4. App-level rate limit is 60/min — 200ms delay = ~5/sec which is within limits if using same-origin (rate limiter may exempt same-origin)

    Check: Does the rate limiter apply to same-origin browser fetches? If yes, increase delay to 1100ms (just under 60/min). If no, 200ms is fine.
  </action>
  <verify>npm run build succeeds; scanner source has delay between files</verify>
