## Goal
Close the W2 `updateSetlist` writer surface in `setlist-firebase.ts` against embedded-array writes AND realize the v60-07 "immediate `FieldValue.delete` strip" mandate for the update side. After this plan:

1. **W2 `updateSetlist` defensively strips `tracks` from incoming patches.** Even though no production caller passes `tracks` after v60-07-01 (caller audit confirmed: only `use-add-to-setlist.ts` lines 169/228/297 invoke it, and all three pass denorm-only fields), the service silently drops any `tracks` field from `Partial<Setlist>` patches before they reach Firestore. Defensive guard against future regressions.
2. **W2 emits `tracks: deleteField()` on every update to a hydrated setlist.** Read `remote.hydrated` inside `updateSetlistWithVersion`'s transaction; if `remote.hydrated === true`, append `tracks: deleteField()` to the applied patch. This realizes the v60-07 phase mandate: any legacy setlist that has been migrated (hydrated:true post-v60-06-08 backfill OR post-v60-07-01 first-edit) gets its embedded `tracks` field DELETED on the next legitimate update — no manual cleanup required.
3. **Audit-log action detection updated.** The current `data.tracks !== undefined ? 'tracks_updated' : 'tracks_updated'` branch is dead code post-this-plan. Collapse to the 2 real actions (`'renamed'` when `data.name`, otherwise `'updated'`) and stop including `trackCount: data.tracks.length` in extras (use `data.trackCount` directly when present).

## Purpose
v60-07-01 + v60-07-02 closed every EMBEDDED-ARRAY WRITE surface in the codebase except W2. The library Add flow (v60-07-01) and the 4 create-style writers (v60-07-02) all stopped writing the embedded `tracks` field. W2 was deferred because it had a different risk profile — high-traffic patch surface used by editor save, reorder, transpose, and other Partial<Setlist> updaters. The caller audit (this plan's research step) revealed those concerns evaporated: editor saves go through the sync engine (`applyEdit`), not through `setlistService.updateSetlist`. The only production callers of W2 are the 3 sites in `use-add-to-setlist.ts`, and all three already pass denorm-only fields.

So the W2 refactor is now small. The bigger value-add of this plan is the **immediate strip realization**: every hydrated setlist that gets touched by any future updateSetlist call gets its embedded `tracks` field deleted. After v60-06-08's 15-setlist backfill `--apply` and the natural drift of weekly editing, the entire setlist corpus migrates to top-level-only without a one-shot migration script. This is the "strip-as-they're-touched" closure of the migration window opened in v50-05.

Once v60-07-03 ships, the remaining writer surface is API routes (W7-W11) — server-side patches via Admin SDK. v60-07-04 will own those. After all 4 v60-07-NN plans land, v60-08 cleanup can drop the embedded-array reader fallback in server-tracks.ts + client-tracks.ts.

               const snap = await tx.get(ref)

               const applied: Record<string, unknown> = { ...patch, updatedAt: serverTimestamp() }
               if (remote.hydrated === true) {

               tx.update(ref, applied)
           })
       }
