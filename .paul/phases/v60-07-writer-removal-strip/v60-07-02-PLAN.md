## Goal
Convert the four create-style writers in `createSetlistService` — W1 `createSetlist`, W3 `duplicateSetlist`, W4 `cloneSetlist`, W6 `saveAsTemplate` — from "embedded `tracks` array in `addDoc` payload" to **engine-path-only seeding**: `addDoc` writes the parent doc WITHOUT the embedded `tracks` field, then a per-track `applyEdit('set', 'tracks', {...})` fanout via `Promise.all` seeds the top-level `tracks/{id}` collection. The parent doc carries `trackCount` + `hydrated: true` as denormalized markers. W5 `cloneForNextWeek` inherits the change for free (thin wrapper around W4). W2 `updateSetlist` is OUT OF SCOPE for this plan — its different shape (high-traffic patch surface, `tracks: FieldValue.delete()` strip mandate) earns its own plan v60-07-03.

## Purpose
v60-07-01 decommissioned the explicit dual-write bridge (`mirrorTracksToTopLevel`) in the library-add hook and established the engine-path writer template. The next-biggest writer surface is the 4 create-style methods in `setlist-firebase.ts` — every "new setlist" path in the app routes through one of these (`createSetlist` from the creation wizard / dashboard / library-add-with-new-setlist; `cloneForNextWeek` from EmptyState; `cloneSetlist` from the clone CTA; `duplicateSetlist` from the dashboard menu; `saveAsTemplate` from the dashboard menu). After this plan, every NEWLY created setlist starts life with top-level `tracks/{id}` rows and ZERO embedded `tracks[]` data — eliminating one entire generation of "future legacy setlists" that would otherwise need a backfill.

Why splitting W1/W3/W4/W6 out from W2:
- **Create vs update have different patterns.** Create-style: `addDoc` payload simply OMITS `tracks`, then seed. Update-style: must strip `tracks` from `Partial<Setlist>` patches arriving from callers AND emit `FieldValue.delete()` to remove stale embedded data on first update. Different ACs, different blast radius.
- **W1/W3/W4/W6 are largely self-contained.** All four callers consume only the returned `id` (verified: `use-setlist-dashboard.ts:150/164/177/252/275/301`, `use-creation-wizard.ts`, `use-add-to-setlist.ts:334` — none read the returned setlist's `.tracks`).
- **W2 has many callers passing `tracks` patches** (editor save flows, reorder, transpose, etc.) — that surface needs its own audit before refactor. v60-07-03 will own it.
- **HFG counter discipline:** Splitting keeps each plan ≤ ~+30 LOC net (v6.0 ceiling per ROADMAP constraint).

After this plan, the v60-08 cleanup can drop `tracks` from `addDoc` converter payloads only after W2 is also done — but the create-side will already be clean.
