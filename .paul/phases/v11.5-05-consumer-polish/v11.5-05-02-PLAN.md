<objective>
## Goal
Two consumer setlist-detail (`/perform/setlist/[id]`) display-correctness items
from the v11.5 design audit:
- **Q5** — chart titles with a stray file extension (".pdf", ".docx") leak to the
  consumer surface (`SetlistRow`). Strip the extension at display time via ONE
  shared helper. Flagged on BOTH tenants (`crc-perform-chart-1180.png` "Oseh
  shalom - Nava tehila.pdf" + `bl-setlist-detail-1180.png` ".docx" titles), so
  this is a shared correctness fix — it INTENTIONALLY changes the CRC render
  (NOT CRC-byte-identical, unlike Q6/Q3).
- **F4** — Brothers Lazaroff setlist rows show no key badges while CRC rows do.
  VERIFY-FIRST confirmed: `SetlistRow`'s `displayKey` returns null iff
  `!track.key` with NO org gate (SetlistRow.tsx:48) → root cause is missing
  `track.key` DATA on BL tracks, not a display gate. Fix = resolve a missing
  `track.key` from `library_index` at SSR read time (the same seam + same
  "musicians/anon have no client library store" rationale as the shipped
  `mimeType` enrichment in `server-tracks.ts`). Display-only; no Firestore write.

## Purpose
Second plan of the LAST v11.5 phase. Tightens the most-used consumer surface
(the setlist a musician opens on an iPad) on both tenants: clean titles + key
badges that actually appear for BL. F4 reuses the exact read-time-enrichment
pattern already trusted for chart-viewer routing, so it reaches anon/musician
viewers (who never hydrate the leader-only `useLibraryStore`).

## Output
- New pure `displayChartTitle()` helper + `SetlistRow` consuming it.
- `server-tracks.ts` enrichment generalized to fill missing `key` (and mimeType)
  from `library_index` in one batched pass.
- A live BL probe findings file documenting whether resolution fixes BL now or
  surfaces an authoring data gap (keys never set in the catalog either).
- Tests for the helper + the key-enrichment path.
</objective>

## Verified facts (probed at plan time — trust these)
- **Q5 leak surface is ONLY `SetlistRow`.** `track.title` (SetlistRow.tsx:118,
  162, 166, aria :204) passes through from Firestore verbatim; `server-tracks.ts`
  does NOT clean it. The public listing renders setlist *names* (user-set, not
  filenames) + song counts — no filename leak. The bind picker
  (`ChartBindPopover`/`ChartBindDialog`) already renders clean Dexie `song.title`
  — NOT in scope (drop the handoff's "bind picker" guess).
- **No shared display-strip helper exists.** ~11 inline `.replace(/\.(pdf|…)$/i,'')`
  sites + a local non-exported `cleanFileName` (use-add-to-setlist.ts:18). The one
  EXPORTED constant `STRIPPABLE_EXTENSION_RE` (`src/lib/mcp/title-specificity.ts`)
  is MCP-namespaced AND lacks `.docx`/`.doc`/`.txt` (which the audit flags on BL) —
  do NOT import the MCP module into a client component; create a small client-safe
  helper instead.
- **F4: `displayKey` has no org gate** — `if (!isSong || !track.key) return null`
  (SetlistRow.tsx:48). Missing badge ⇒ empty `track.key`.
- **`track.key` is NOT enriched at read time.** `server-tracks.ts:getTracksForSetlist`
  maps `tracks/{id}` docs through as-is, then calls `enrichMissingMimeTypes(db, rows)`
  (server-tracks.ts:54) which batch-reads `library_index/{fileId}` and fills ONLY
  `mimeType`. The consumer/anon Perform view renders `initial.tracks` (the SSR frame
  from `fetchInitialFrame`) when Dexie is empty (`use-setlist-performance.ts:167`),
  so server-side enrichment DOES reach them — same as the mimeType fix.
- **`library_index` is the established key-heal source** (MCP `add_track_to_setlist`
  heals key+bpm from library_index; `server-songs` heals missing key/bpm/lead from
  it). So resolving a missing `track.key` from `library_index/{fileId}.key` is the
  consistent choice (and reuses the doc the mimeType pass already fetches → zero
  extra reads).
- `SetlistTrack.key?: string` (models.ts:46); `LocalTrack` (the server row type) is
  the shape `getTracksForSetlist` returns.
- BL bearer for the live probe: `node scripts/mint-throwaway-bl-bearer.mjs --apply`
  (claim-free; revoke with `--revoke <id>`); BL MCP `https://www.brotherslazaroff.live/api/mcp`.
