<objective>
## Goal

Fix Issue 2 (iPad track-name / Notes / setlist-name keyboard not popping) by making `TextCell` enter edit mode **on a single tap** when the pointer is coarse, instead of requiring the desktop-only `onDoubleClick` / Enter / printable-keystroke trigger. Desktop behavior unchanged: button-then-double-click preserves keyboard nav (arrow into cell, Enter to edit, Escape to leave).

## Purpose

v52-02-01 confirmed (AC-4 case ii) that TextCell uses an inline button→input two-state pattern. On iPad there's no path from "focused button" to "editing input" — `onDoubleClick` is unreliable on iOS Safari (tap timing) and Enter / printable keystroke are impossible without a keyboard already on screen. The user is stuck. **Single-tap-to-edit on coarse pointer** is the smallest, most ergonomic delta — it matches iPad expectations (tap = act) and preserves desktop semantics by gating on the `(pointer:coarse)` media query.

Direct PROJECT.md value mapping: "Tablet-first application (band on stage uses iPads; Daniel uses iPad to build setlists)." Daniel's primary daily flow is editing setlist track titles + Notes on iPad. Until this works, the band-onboarding gate stays blocked.

## Output

- TextCell.tsx: button `onClick` becomes `() => (isCoarse ? enterEditMode() : onFocus())` — single tap on coarse goes straight to input; desktop click still just focuses
- New `TextCell.test.tsx` with regression tests: coarse-tap-enters-edit + fine-tap-only-focuses + isCoarse-gate-isolates
- MobileEditSheet read-only investigation (Task 1 step 3) — confirm whether its text inputs are affected by the same pattern OR are plain `<input>` (no fix needed)
- Suite + tsc + next build clean
- Daniel-loop UAT acceptance criterion satisfied on real iPad post-deploy
</objective>
