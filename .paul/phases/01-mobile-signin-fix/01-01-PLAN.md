<task type="auto">
  <name>Task 2: Fix false "Update available" banner on fresh page loads</name>
  <files>src/components/offline/UpdatePrompt.tsx</files>
  <action>
    The bug: The controllerchange listener (line 98-117) fires even on fresh page loads. When auto-activation happens (autoActivated = true, line 61), it sends SKIP_WAITING which triggers controllerchange. But by line 109, autoActivated is reset to false. The problem is a race — the controllerchange event fires asynchronously, and the flag may have been reset.

    Also, the controllerchange listener at line 112-116 sets the banner state even when it should only track for reload purposes.

    Fix approach:
    1. Instead of resetting autoActivated to false in the controllerchange handler (line 109), keep it true permanently once set. It's a one-shot flag for this page load.
    2. Add a small delay (e.g., 5 seconds) after page load before the controllerchange listener starts showing banners. This prevents race conditions where the SW activates during initial page load.
    3. Consider: if a controllerchange happens and the SW is already active (not installed/waiting), just suppress the banner — the user already has fresh content.

    Simpler approach: In the controllerchange handler, check if the page has been loaded for less than 10 seconds. If so, suppress the banner entirely — any SW activation in the first 10 seconds is part of normal page load, not a mid-session update.

    DO NOT change the dismiss logic or the 4-hour cooldown.
    DO NOT remove the interaction tracking — it's correct for the updatefound path.
  </action>
  <verify>
    - TypeScript compiles clean
    - Manual test: fresh page load shows no banner
    - Manual test: if a new deploy happens mid-session, banner should still appear
  </verify>
  <done>AC-2 satisfied: No false update banner on fresh page loads</done>
</task>

    The code at DesktopHeader:170 checks `user?.photoURL`. The Firebase Auth User object should have photoURL populated from Google sign-in. Possible issues:

    1. The photoURL might be an HTTP URL (not HTTPS) — browsers block mixed content
    2. The Google profile photo URL format may have changed or be null for some accounts
    3. The CSP img-src already includes *.googleusercontent.com so that's not the issue

    Fix approach:
    1. Add an onError fallback to the img tag — if the photo fails to load, show the UserCircle icon
    2. Also check cachedUser.photoURL as a fallback (from auth-context localStorage cache)
    3. In both DesktopHeader.tsx and MobileMenuDrawer.tsx, update the avatar rendering to:
       - Use a state variable to track if the image loaded successfully
       - On error, fall back to UserCircle
       - Also try profile?.photoURL (from Firestore) as another source

    Keep it simple — just add onError handler to the existing img tags.

    DO NOT replace the img tag with next/image (intentionally using img for small avatars).
    DO NOT change the dropdown menu content or structure.
