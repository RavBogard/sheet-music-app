<objective>
## Goal
Convert `bulk_add_tracks` per-row errors from bare strings to the structured
`{code, machine_code, message}` rich-error body — achieving parity with the
single-row tools (`add_track_to_setlist` etc.) so an agent can branch on a
machine code instead of regex-matching prose. (BUG-3 from the BL MCP stress-test.)

## Purpose
The MCP surface is Daniel's PRIMARY authoring path. `bulk_add_tracks` (the
weekly-flow N+1 closer — one call to add a whole service) is the only
remaining write tool whose per-row failures emit `error: "<prose>"` while
every sibling emits `error: { code, machine_code, message }`. Bare strings
force agents to string-match ("title is required", "not found") to recover,
which is brittle and breaks the deterministic error contract 03-01 established
for the single-row path.

## Output
- `BulkAddResult.error` becomes a `RichErrorBody` object (was `string`).
- Each per-row failure cause carries a correct machine_code + HTTP-class code:
  song-not-found → `song_not_found` (404), missing title → `title_required`
  (400), atomic-rollback collateral → `batch_rolled_back` (409), internal
  resolver-missing → `server_error` (500).
- Two new rows in `ERROR_CODE_MAP` (`title_required:400`, `batch_rolled_back:409`).
- Emulator test assertions updated from string-match to object-shape.
</objective>

<acceptance_criteria>

## AC-1: Per-row errors are structured with correct codes
```gherkin
Given a bulk_add_tracks call with a row whose songId does not resolve
When the tool returns its per-row results
Then that row's `error` is an object `{code:404, machine_code:"song_not_found", message:<prose naming the songId>}`
And a row missing both title and songId yields `{code:400, machine_code:"title_required", message:<prose containing "title is required">}`
And in atomic mode the surviving (would-have-written) rows yield `{code:409, machine_code:"batch_rolled_back", message:<prose containing "Rolled back">}`
```

## AC-2: Shape parity with single-row tools
```gherkin
Given the single-row tools emit `error: {code, machine_code, message}` (RichErrorBody)
When bulk_add_tracks emits a per-row failure
Then its `error` is the SAME RichErrorBody shape (object with numeric `code`, snake_case `machine_code`, prose `message`)
And `code` is derived via `codeFor(machine_code)` from ERROR_CODE_MAP (single source of truth), not hardcoded per-site
```

## AC-3: Positive controls + top-level envelope unchanged
```gherkin
Given a happy-path bulk_add_tracks call (all rows valid)
When it returns
Then every result row is `{index, ok:true, trackId, order}` with NO `error` field (byte-identical to today)
And the top-level WriteError path (empty_tracks / too_many_tracks) still returns `richError("bulk_add_failed", <string>, …)` unchanged
And bulk_update_tracks per-row error shape is NOT modified (out of scope)
```
