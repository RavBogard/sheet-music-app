<objective>
## Goal
Cut over `/setlists/[id]` from the legacy `SetlistEditorV2` mount to the new `SetlistGrid` (built in v50-05-01), hydrate Dexie from the server-fetched setlist + tracks at mount time, wire `ChartCell` click → library binding popover → `applyEdit('update','tracks',{songId,...})`, then delete the legacy editor surface (~−8,400 LOC) and narrow `setlist-firebase.ts` to its non-editor exports.

## Purpose
The setlist editor is the central authoring surface of v5.0. v50-05-01 built the new editor end-to-end but left it unmounted in production. This plan executes the hard cutover: legacy editor disappears from the route, the spreadsheet-shaped editor takes its place, and the broken/silent save paths v45-01 instrumented (`StaleWriteError`, keepalive flush non-2xx, canEdit early-return, token refresh failure) are deleted at the source. After this lands, the editor is bulletproof-by-construction (every commit goes through `applyEdit` → outbox → engine → Firestore with retry + dead-letter) and Sheets envy dissolves into spreadsheet-shaped reality.

App is intentionally broken-for-band during this phase — band is not in production, hard cutover with no parallel scaffolding is the milestone constraint.

## Output
- One-line route mount swap in `src/app/(main)/setlists/[id]/page.tsx`
- New `SetlistGridHydrator` client component that primes Dexie with server-fetched setlist + tracks idempotently before `SetlistGrid` mounts
- New `ChartBindPopover` component (cmdk + library group, same shape as `AddRowPlaceholder`'s library half) wired to `ChartCell.onClick`
- ~−8,400 LOC of legacy editor surface deleted; `setlist-firebase.ts` narrowed to non-editor exports (`Setlist` type + `createSetlistService`)
- Full test suite green; tsc clean; `next build` clean (route count drops 77 → 76 once `/api/setlist/flush` is gone)

<task type="checkpoint:decision" gate="blocking">
  <decision>Dexie hydration architecture: where does server-fetched data enter Dexie before SetlistGrid's live query reads it?</decision>
  <context>
    SetlistGrid reads tracks from Dexie via useLiveQuery on `tracks.where('setlistId').equals(setlistId).sortBy('order')`. On first visit (or after IDB clear / new device), Dexie has no rows for this setlist — the live query will return [] and the editor will show EmptyState even though the setlist exists in Firestore with N tracks. We must hydrate Dexie before SetlistGrid mounts (or be tolerant of momentary empty state).

    Critical constraint: hydration writes MUST bypass `applyEdit` and write directly via `db.setlists.put(...)` + `db.tracks.bulkPut(...)`. `applyEdit` always enqueues an outbox row, which would re-send authoritative server data back to Firestore on next drain. Server data is not dirty.

    The route is a Server Component; hydration runs client-side after server data is serialized through props.
  </context>
  <options>
    <option id="option-a">
      <name>Option A — Hydrate inside the route's existing client component path; pass `initialServerData` as a prop to a new SetlistGridHydrator wrapper</name>
      <pros>
        - Minimal new components: just one Hydrator that wraps SetlistGrid
        - Server fetch shape ↔ client hydration shape contract is explicit (props)
        - Hydrator can show a 1-frame loading state if needed; deterministic
        - Natural place to put idempotency check (compare server.updatedAt vs local.updatedAt before put)
      </pros>
      <cons>
        - Page route file grows slightly: it now serializes the full track list to props, not just IDs
        - Hydrator runs on every route mount (cheap because of idempotency check, but technically extra Dexie reads)
      </cons>
    </option>
    <option id="option-b">
      <name>Option B — Hydrate via a useEffect in SetlistGrid itself when tracks live-query returns empty AND server hint says non-empty</name>
      <pros>
        - SetlistGridHydrator component not needed; less surface area
        - Hydration is fully colocated with the consumer
      </pros>
      <cons>
        - Conflates read-from-IDB with write-to-IDB inside the same component (separation-of-concerns smell)
        - "Empty live query result" can mean truly-empty OR hydrating-now — race conditions on first visit
        - Couples SetlistGrid to a Firestore SDK call; harder to test in isolation
        - Server-already-fetched-the-data work gets re-done client-side via Firebase Web SDK (extra round trip)
      </cons>
    </option>
  </options>
  <resume-signal>Select: option-a or option-b. Recommended: option-a (cleaner separation, server fetch is already happening in the page Server Component, no double round-trip).</resume-signal>
</task>
