<objective>

## Goal
Land the visible end-to-end image-chart pipeline: musicians can upload PNG / JPEG / HEIC charts via `/api/library/upload`, the chart appears in the library + setlist picker, and opening it in the performance overlay renders the image full-screen with transpose / AI-chord controls disabled and an inline tooltip explaining why. Print pipeline image-embed is **explicitly deferred** to v70-01-02 (any image-chart row is omitted from generated print PDFs in plan 01 with a banner notice in PrintModal — no broken downloads).

## Purpose
v7.0 milestone constraint #11: "Image-chart support = PNG + JPEG + HEIC; AI chord detection + transposition disabled with tooltip." This is **Wave 0 / foundation** for v7.0 — the May 15th Shir Shabbat doc references `dodi li (sher).png`, so v70-05 (Gemini doc-driven setlist creation) cannot canary-pass until image charts are at least uploadable + viewable. Daniel directive 2026-05-13: *"right now it's not letting me take a PNG file or other image file and display it as a chart. I'd like to change that."*

## Output
- `/api/library/upload` accepts `image/png`, `image/jpeg`, `image/heic`, `image/heif` (HEIC server-converted to JPEG at upload time so storage holds a universally-renderable byte stream)
- New `ImageScoreViewer` component (zoom/pan; mirrors `TextScoreViewer` minimal pattern; full-screen `<img>` with object-contain)
- `PDFOverlay` branches on `type === 'image'` → renders `ImageScoreViewer`
- Transpose + AI-chord toolbar controls disabled with explanation tooltip when current item is an image
- PrintModal shows a banner ("Image charts are not yet included in printed packets — coming next phase") and the print pipeline silently skips image-typed tracks (no crash) until v70-01-02 lands
- `.paul/phases/v70-01-image-chart-support/v70-01-01-SUMMARY.md`

</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>HEIC-conversion library: confirm `heic-convert` (pure JS, ~6MB) vs alternatives (`sharp` native, `libheif-js`).</decision>
  <context>
    Three viable choices. Locked default = `heic-convert` because:
    - **Pure JS** — runs in any Node serverless target without native bindings; matches the Vercel deployment we already use (per memory).
    - **No build step** — `sharp` requires platform-specific binaries; previous Vercel deploys have hit issues with sharp's libvips on edge runtimes.
    - **Acceptable size** — bundle stays in serverless function, not client.
    Rejected `sharp`: native dep risk + larger cold-start.
    Rejected `libheif-js`: similar to heic-convert but less battle-tested in serverless contexts.
    Rejected "defer HEIC to v7.1": violates v7.0 constraint #11.
  </context>
  <options>
    <option id="heic-convert">
      <name>heic-convert (LOCKED DEFAULT)</name>
      <pros>Pure JS; serverless-safe; ~6MB; no native build; battle-tested for HEIC→JPEG.</pros>
      <cons>JS decode is ~3× slower than libvips; quality fine-tuning limited; bundle adds to function size.</cons>
    </option>
    <option id="sharp">
      <name>sharp (native libvips)</name>
      <pros>Faster; finer quality controls; already industry-standard.</pros>
      <cons>Native binary risk on Vercel; libvips HEIC support requires libheif compiled in.</cons>
    </option>
    <option id="libheif-js">
      <name>libheif-js (WASM)</name>
      <pros>WASM-based; pure-runtime; works everywhere.</pros>
      <cons>Larger bundle (~15MB); less ergonomic API; fewer downloads / less battle-tested.</cons>
    </option>
  </options>
