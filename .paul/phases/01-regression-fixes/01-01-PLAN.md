<objective>
## Goal
Fix two regressions introduced during v1.3 deployment: (1) PDF viewer fails with worker version mismatch error, and (2) monitor tab fails to load on iPad.

## Purpose
Both features are core to CentralReform.live — musicians need PDFs to read charts and the monitor tab to control their mix during live services. These regressions block production use.

## Output
- PDF worker version mismatch eliminated with build-time assertion
- Worker cache busting prevents stale worker files after deploys
- Monitor connection stable on iPad through auth token refresh cycles and tab suspension
</objective>

<task type="auto">
  <name>Task 2: Stabilize monitor connection for iPad</name>
  <files>src/hooks/use-monitor-connection.ts</files>
  <action>
    **Fix 1: Stabilize useEffect dependency (AC-3)**
    - Change `[user?.uid]` to `[user]` or better: extract `user?.uid` into a stable ref
    - The issue: `user?.uid` is an optional chain that evaluates to `undefined` when user is null. During Firebase token refresh, user briefly becomes null then restores. This causes the effect to fire cleanup → re-run, corrupting refCount.
    - Solution: Use a `userUidRef` pattern. Store `user?.uid` in a ref, and use a separate effect that only triggers connection logic when the uid genuinely changes (null→uid or uid→null→uid with different value), not during transient nulls:
      ```
      const userUid = user?.uid ?? null
      const prevUidRef = useRef<string | null>(null)

      useEffect(() => {
        if (userUid === prevUidRef.current) return  // No genuine change
        prevUidRef.current = userUid
        if (!userUid) return  // User signed out — auth listener handles teardown

        refCount++
        // ... rest of connect logic

        return () => {
          refCount = Math.max(0, refCount - 1)
          // ... teardown debounce
        }
      }, [userUid])
      ```
    - This prevents the effect from re-running during transient null states because the auth listener's 3s debounce already handles that case.

    **Fix 2: Add visibilitychange listener for iOS Safari (AC-4)**
    - iOS Safari doesn't reliably fire `beforeunload`. Tabs get suspended without notice.
    - In `registerTeardownListeners()`, add a `visibilitychange` listener:
      - On `hidden`: No action needed (connection is Firestore-based, survives suspension)
      - On `visible`: If `activeClient` exists but `connectedUserId` is set, verify the connection is still live. If auth.currentUser exists and connectedUserId matches, the Firestore onSnapshot should auto-reconnect. If `activeClient` is null (was torn down during suspension), call `ensureConnected(auth.currentUser.uid)`.
    - This handles the case where iOS tears down the page's network connections during suspension.
    - Guard the refCount: on `visible`, if `refCount > 0` and `!activeClient` and `auth.currentUser`, reconnect.

    **Fix 3: Increase refCount teardown debounce for iPad**
    - Change the 3000ms debounce to 5000ms. iPad tab suspension/restoration takes longer than desktop navigation transitions.
    - Add a comment explaining why 5s (iPad suspension recovery time).
  </action>
