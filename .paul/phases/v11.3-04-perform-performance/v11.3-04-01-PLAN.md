<objective>
## Goal
VERIFY-FIRST characterization of the BUG-2 `/perform` performance regression: decompose the
p75 field numbers (LCP 2600 / FCP 3012–3247 / TTFB 1398–1545 ms; CLS regressed 0.15 → 0.2) into
**cold first-load vs steady-state**, attribute each metric to a concrete cause, and pinpoint the
**CLS layout-shift source** (suspected chart-image reflow after fonts/controls mount). Produce a
ranked, regression-citable fix list that becomes the input to Plan v11.3-04-02. **No production
code changes in this plan** — measurement and analysis only.

## Purpose
`/perform` is the band's primary surface (highest-traffic route) and the band's bar is "ready in
the 7 minutes before service." Fixing perf blind risks chasing the wrong metric: the milestone
constraint mandates VERIFY-FIRST so the fix plan targets the real dominant cause with a healthy
comparator (`/setlists` LCP 1.1 s / CLS 0.02) rather than guessing. Field RUM is real-user data,
but `get_web_vitals_summary` only buckets by `surface` — it cannot tell cold from warm, iPad from
desktop, or which DOM node shifts. This plan supplies exactly those missing dimensions.

## Output
- `scripts/v11-3-04-webvitals-slice.mjs` — admin-SDK probe slicing `webVitalsObservations` by
  surface × navigationType × deviceType → p75 per metric (reuses the firebase-CLI refresh-token
  ADC pattern from `scripts/v11-3-03-library-orphan-sweep.mjs`).
- `.paul/research/PERFORM-PERF-CHARACTERIZATION-2026-06-10.md` — the findings doc: per-slice p75
  table, LCP-element identity, CLS-source attribution, TTFB attribution, and a ranked fix list
  with each proposed fix tagged to the metric it moves + the regression cite it will carry.
</objective>
