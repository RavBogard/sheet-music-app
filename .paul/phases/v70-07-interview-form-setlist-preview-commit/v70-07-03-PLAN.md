## Goal
Close the doc-import pipeline: a `commitDocumentSetlist` lib that flattens a
resolved `{ sections, tracks }` structure + interview metadata into a real
setlist (section headers interleaved, matched charts bound), a thin
`POST /api/setlists/import/commit-document` route over it, and the wiring that
turns ImporterModal's currently-inert "Create Setlist" button into a working
commit. This is the final plan of v70-07.

interview → preview UI but stopped before persistence. This plan connects them:
"Feed a doc, get a setlist" becomes a real, end-to-end action — Daniel uploads
the May 15 Shir Shabbat doc and ends up with a created setlist, charts bound.

<acceptance_criteria>

## AC-1: commitDocumentSetlist flattens a resolved structure and persists it
```gherkin
Given a resolved structure (sections + tracks — some tracks carrying a
  libraryMatch, some flagged missingChart, some with no sectionName) plus
  interview metadata (name, eventDate, serviceType, rabbi)
When commitDocumentSetlist is called with it (plus ownerId / ownerName)
Then it builds a flat ServerSetlistTrackInput list — each section emitted as a
  'header' track followed by its 'song' tracks in document order, ungrouped
  tracks last — where every matched song carries its libraryMatch fileId + name
  as the bound chart and missingChart songs carry no fileId, calls
  createSetlistServerSide, and returns { setlistId, trackCount }
And the setlist doc carries the interview metadata (name, eventDate,
  templateType from serviceType, rabbi)
```

## AC-2: The commit-document route persists for an authenticated band_leader
```gherkin
Given an authenticated band_leader
When they POST a valid { name, eventDate, serviceType, rabbi?, sections, tracks }
  body to /api/setlists/import/commit-document
Then the route delegates to commitDocumentSetlist and responds 201 with
  { success: true, setlistId }
And an invalid body responds 400, and a non-band_leader responds 403
```

## AC-3: The ImporterModal preview commits the setlist
```gherkin
Given the ImporterModal preview step with a resolved setlist and the interview
  values set
When the user clicks "Create Setlist"
Then the modal POSTs the resolved structure + interview values to
  /api/setlists/import/commit-document, the button shows a loading state, and on
  success it toasts, calls onComplete(setlistId), and closes the modal
And on failure it toasts the server error and stays on the preview step
```

  <action>
    Create `src/lib/setlist-import/commit.ts` exporting `commitDocumentSetlist`.

    - Input shape (define + export an interface, e.g. `CommitDocumentInput`):
      `{ name, ownerId, ownerName, eventDate?, serviceType?, rabbi?, sections,
      tracks }` — where `sections: SetlistSection[]` and `tracks:
      ResolvedTrack[]` (import both types from
      `@/lib/setlist-import/resolve` / `./extract-structure`).
    - Flatten `sections` + `tracks` into a `ServerSetlistTrackInput[]` (type
      from `@/lib/setlist-write`):
      - Iterate `sections` sorted by `order`. For each, push a
        `{ type: 'header', title: section.name }`, then its tracks (those whose
        `sectionName === section.name`) sorted by `order`.
      - Tracks with no `sectionName` (or a `sectionName` not matching any
        section) go into an "ungrouped" bucket appended last, in `order`.
      - Map each song: `type: 'song'`, `title`, `key`, `leadMusician` ←
        `track.vocalLead` (the model stores Vocal Lead as `leadMusician` — see
        ServerSetlistTrackInput), `referenceLink`, and — when `track.libraryMatch`
        is present — `fileId: libraryMatch.fileId` + `fileName: libraryMatch.name`
        (bind the matched chart). `missingChart` tracks get no `fileId`.
      - `recordingCandidates` is IGNORED — recording binding is deferred for
        v70-07 (Daniel decision 2026-05-14).
    - Call `createSetlistServerSide({ name, ownerId, ownerName, eventDate,
      serviceType, rabbi, tracks: <flattened> })` and return its
      `{ setlistId, trackCount }` result.
    - The function does not auth or validate — that is the route's job (mirrors
      how setlist-write.ts stays a pure write module).

    Create `src/lib/setlist-import/__tests__/commit.emulator.test.ts` — an
    emulator test (mirror the structure of
    `src/lib/__tests__/setlist-write.emulator.test.ts` from v70-07-01: same
    emulator setup, `npm run test:emulator` harness). Cover: a resolved
    structure with two sections + an ungrouped track, one track with a
    libraryMatch, one missingChart track. Call `commitDocumentSetlist`, then
    read back from the emulator and assert: the `setlists/{id}` doc has the
    metadata (name / eventDate / templateType / rabbi); the `tracks/{id}` docs
    include the section headers interleaved before their songs in `order`; the
    matched song's `fileId`/`fileName` equal its libraryMatch; the missingChart
    song has no `fileId`; the ungrouped track is last.

    Avoid: putting the flatten logic in setlist-write.ts (that module is the
    generic write path — doc-import flattening is setlist-import territory).
    Avoid: a version-precondition or the client applyEdit path — createSetlistServerSide
    is the established server-side write (v70-07-01).
  </action>
