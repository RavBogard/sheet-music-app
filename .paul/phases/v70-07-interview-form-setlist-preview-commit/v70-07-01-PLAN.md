<objective>
## Goal
Extract the server-side setlist-write logic that currently lives inline in
`src/app/api/setlists/import/execute/route.ts` into a reusable, server-callable
module `src/lib/setlist-write.ts` exposing `createSetlistServerSide` (build the
`setlists/{id}` doc + seed top-level `tracks/{id}`) and `updateSetlistServerSide`
(patch a setlist's metadata). Refactor `import/execute` to call it — so there is
ONE server-side setlist-write path, not two.

## Purpose
This is **plan 01 of 3** for v70-07 and the **MCP-workstream coordination point**
(Daniel's handoff 2026-05-14): v70-07's doc-import commit step needs server-side
setlist writes, and so do Daniel's MCP write tools — but today the only
setlist-create logic is either client-SDK-only (`createSetlistService`) or
inline-in-a-route (`import/execute`). A shared module gives both consumers one
proven write path. Signature **approved by Daniel 2026-05-14** (create + update).
v70-07 plans 02 (interview form + ImporterModal "Document" option + preview) and
03 (commit wiring) build on this module.

## Output
- `src/lib/setlist-write.ts` — `createSetlistServerSide` + `updateSetlistServerSide`
  + their input types. firebase-admin-based; server-callable.
- `src/app/api/setlists/import/execute/route.ts` — refactored to call
  `createSetlistServerSide` for the final setlist+tracks write (its
  Drive-download + library_index logic is unchanged).
- `src/lib/__tests__/setlist-write.emulator.test.ts` — emulator coverage (HFG).
- `.paul/phases/v70-07-interview-form-setlist-preview-commit/v70-07-01-SUMMARY.md`.

```gherkin
Given a CreateSetlistInput { name, ownerId, ownerName, eventDate?, serviceType?,
  rabbi?, tracks[] }
```

<task type="auto">
  <name>Task 1: Create the server-callable setlist-write module</name>
  <files>src/lib/setlist-write.ts</files>
  <action>
    Create `src/lib/setlist-write.ts` — a firebase-admin-based, server-callable
    module. Extract the proven write logic currently inline in
    `import/execute/route.ts` (the `setlistPayload` build + the
    `db.batch()` tracks seed). Do NOT extract import/execute's Drive-download /
    library_index-entry logic — that stays in the route (Task 2).

    **Types:**
    ```
    ServerSetlistTrackInput = {
      type: 'song' | 'header'
      title: string
      key?: string
      leadMusician?: string      // "Vocal Lead" (per project terminology)
      referenceLink?: string
      fileId?: string            // bound chart (library_index id)
      fileName?: string
    }
    CreateSetlistInput = {
      name: string
      ownerId: string
      ownerName: string
      eventDate?: Date | string
      serviceType?: Setlist['templateType']   // maps to the `templateType` field
      rabbi?: string
      tracks: ServerSetlistTrackInput[]
    }
    SetlistMetadataPatch = Partial<{
      name: string
      eventDate: Date | string
      serviceType: Setlist['templateType']
      rabbi: string
      serviceNotes: string
    }>
    ```
    Export all of these + the two functions below.

    **`createSetlistServerSide(input): Promise<{ setlistId: string; trackCount: number }>`:**
    - `initAdmin()` + `getFirestore()` (from `@/lib/firebase-admin`) — guard the
      not-ready case by throwing a clear Error (the route maps it; see Task 2).
    - Build the `setlists/{id}` doc mirroring import/execute's `setlistPayload`:
      `id` (crypto.randomUUID()), `name`, `date` + `updatedAt` =
      `FieldValue.serverTimestamp()`, `trackCount` = input.tracks.length,
      `hydrated: true`, `ownerId`, `ownerName`. ADDITIONALLY, when provided:
      `eventDate` (see below), `templateType` = `input.serviceType`, `rabbi`.
    - `eventDate`: when `input.eventDate` is set, write a proper Firestore
      `Timestamp` (`Timestamp.fromDate(new Date(input.eventDate))` from
      `firebase-admin/firestore`) — NOT an ISO string and NOT a plain number
      (firestoreTimestampSchema in schemas.ts accepts Date/{seconds,nanoseconds}/
      string; a server-side Timestamp is the cleanest). When not provided, omit
      the field (do NOT default eventDate to serverTimestamp the way import/execute
      does — that's a CSV-import quirk; the doc-import + MCP callers pass it
      explicitly or leave it genuinely unset).
    - `db.collection('setlists').doc(setlistId).set(setlistPayload)`, then seed
      top-level `tracks/{id}` via `db.batch()` exactly as import/execute does:
      one doc per input track with `{ ...trackFields, id, setlistId, order: i,
      type: t.type ?? 'song' }`. Sequential after the parent `set()` (same
      partial-failure recoverability note import/execute documents).
    - Return `{ setlistId, trackCount: input.tracks.length }`.

    **`updateSetlistServerSide(setlistId: string, patch: SetlistMetadataPatch): Promise<void>`:**
    - `initAdmin()` + `getFirestore()`.
    - Map the patch to setlist doc fields: `name`, `rabbi`, `serviceNotes`
      pass through; `serviceType` → `templateType`; `eventDate` →
      `Timestamp.fromDate(new Date(...))`. Omit any key not present in the patch.
    - `db.collection('setlists').doc(setlistId).update({ ...mapped,
      updatedAt: FieldValue.serverTimestamp() })`.
    - Metadata-ONLY — this function does NOT touch `tracks/{id}` docs,
      `trackCount`, `ownerId`, or `hydrated`. (Server-side track editing is out
      of scope — future work if MCP needs it.)

    Avoid: importing the client Firestore SDK (`@/lib/firebase`) — this is a
    server module, firebase-admin only. Do NOT add version-precondition
    (expectedUpdatedAt) logic — keep update simple; the sole-admin app's
    LWW-on-conflict posture (v6.0 decision) makes server-side preconditions
    unnecessary here.
  </action>
  <verify>npx tsc --noEmit — setlist-write.ts is type-clean; createSetlistServerSide
    + updateSetlistServerSide + the input types exported</verify>
  <done>AC-1 + AC-2 satisfied: the module creates a setlist+tracks and patches
    setlist metadata server-side</done>
</task>
