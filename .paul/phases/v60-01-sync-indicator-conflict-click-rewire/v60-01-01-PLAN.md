<objective>
## Goal
Give the `conflict` SyncIndicator pill an exit, and make manual retry silently last-write-wins instead of looping back into the now-disabled reconciliation modal. After this plan, clicking the pill calls `retryFailedOutboxRows`; if the retry hits `VersionMismatchError` again, the engine forces last-write-wins on that row, fires a Sentry capture, and dispatches `DRAIN_OK` so the FSM returns to `idle` — no modal, no banner, no second click required.

## Purpose
Closes v6.0 design-doc Feature F4 and the user's #1 fatigue surface ("Conflict — review" pill latches with no recovery now that `a0c61cc` force-disabled the reconciliation modal). Orthogonal to the tracks migration spine — ships Wave 1 so Daniel has a working SyncIndicator before any Wave 3 engine-touching phase lands. Encodes locked decision #4 (sole-admin app: silent LWW on retry + Sentry capture).

## Output
- SyncIndicator click handler: conflict and failed states both invoke `retryFailedHandler`.
- `retryFailedOutboxRows` marks reset rows with `forceLwwOnConflict: true`.
- Engine drain handles `VersionMismatchError` on a `forceLwwOnConflict` row by stripping `expectedUpdatedAt`, retrying once with `attempts := attempts + 1`, capturing the conflict-resolution event to Sentry, and dispatching `DRAIN_OK` on success.
- `OutboxRow` gains an optional `forceLwwOnConflict?: boolean` field (additive; no migration).
- Tests cover the click rewire, the cleanup-side flag write, and the engine-side silent-LWW branch.
- `v60-01-01-SUMMARY.md` with browser-smoke evidence appended at phase close.
</objective>

## AC-1: Conflict pill click triggers retry, not modal
```gherkin
Given the SyncEngine is in state 'conflict' (a row failed with VersionMismatchError and no force-flag was set)
And the SyncIndicator renders "Conflict — review"
When the user clicks the SyncIndicator
Then SyncIndicator calls `retryFailedHandler` (which calls `retryFailedOutboxRows`)
And no reconciliation modal opens (the dead `resolveConflictHandler` branch is not taken)
And the reset failed rows carry `forceLwwOnConflict: true`
```

## AC-2: Silent last-write-wins on VersionMismatch when force flag is set
```gherkin
Given an outbox row has `forceLwwOnConflict: true`, `attempts: 0`, and a stale `expectedUpdatedAt`
And the remote document exists with a newer `updatedAt`
When the engine drains the row and the adapter throws `VersionMismatchError` (with `remote!=undefined`)
Then the engine clears `expectedUpdatedAt` on the row, sets `attempts: 1`, clears the flag, and schedules immediate retry
And on the next drain the adapter applies the write unconditionally (last-write-wins) and resolves
And the engine fires `captureSyncFailure` once with `{ feature: 'conflict-resolution', site: 'silent-lww-on-retry' }` carrying the row's `collection`, `docId`, `op`, and pre-retry remote.updatedAt
And the FSM dispatches `DRAIN_OK` (NOT `DRAIN_VERSION_MISMATCH`)
And the SyncIndicator state returns to 'idle'
```

## AC-3: Force flag does not affect first-time writes
```gherkin
Given a freshly enqueued outbox row WITHOUT `forceLwwOnConflict` set
When the engine drains and the adapter throws `VersionMismatchError`
Then the row transitions to `status: 'failed'` per the existing v52-03-01 contract
And the FSM dispatches `DRAIN_VERSION_MISMATCH` (state becomes 'conflict')
And no silent-LWW retry fires (only manual user retry can opt in)
And the existing legacy-stamp self-heal branch (`remote=undefined && attempts === 0`) is preserved unchanged
```


## Browser-smoke checklist (AC-4 — Daniel runs against deployed commit)

This is the v6.0 phase-close discipline per locked decision #8. Vitest green is necessary but not sufficient. The plan only closes PENDING-UAT after this passes.

**Setup:**
1. Open the production app on iPad Safari (or Chrome desktop) — whichever you actually use to publish on Friday afternoons.
2. Open an existing Erev Shabbat or Shabbat morning setlist with at least 5 tracks.

**Induce a conflict (steps 3-5 simulate the "rapid same-doc edit during pending" path):**

3. Tap to edit a TextCell on one track (e.g., the Notes field). Type a few characters — DO NOT commit yet (don't blur the field).
4. With the cell still in edit mode, force a hard reload (Cmd+Shift+R on desktop / pull-to-refresh on iPad).
5. After reload, immediately edit the SAME cell on the SAME track and commit (blur).

**Observe:**

6. ✅ **PASS criterion:** within 10 seconds of the second edit committing, the SyncIndicator returns to the green "Saved" state without any modal popping up, without any banner appearing, and without the "Conflict — review" pill latching.
   - The pill may briefly flash red/conflict during the transition — that's fine, as long as it clears on its own (the retry happens automatically via the engine drain).
   - If you happen to see the pill stuck for more than ~3 seconds, tap it once. After ONE tap, the pill should clear within 10 seconds.
   - **FAIL criterion:** the pill latches indefinitely, OR a reconciliation modal opens, OR you have to tap the pill more than once, OR the cell edit is lost after the final state settles.

**Persistence check:**

7. After the indicator reads "Saved" green, hard-reload the page one more time.
8. ✅ **PASS criterion:** the cell value matches what you typed in step 5 (the last write — LWW worked correctly).
   - **FAIL criterion:** the cell shows the pre-step-5 value (the LWW retry didn't apply).

**Sentry visibility check (optional, if you have Sentry access):**

9. Open Sentry → "Issues" or "Discover" → filter on `feature:conflict-resolution`. You should see exactly one event from the induced retry above (level: warning, with `site:silent-lww-on-retry`, your `collection:tracks`, `docId`, `op:update`).
   - This is informational — not a pass/fail; just confirms the engine fired the capture so we can monitor real-production frequency.
