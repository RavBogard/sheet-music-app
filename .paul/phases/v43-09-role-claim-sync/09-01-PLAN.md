<objective>
## Goal
Eliminate the latent drift between `users/{uid}.role` (Firestore) and `request.auth.token.role` (Firebase Auth custom claim). On every sign-in / token refresh, the server canonicalizes the claim to match Firestore so that any Firestore rule depending on `token.role` (`isMember()`, `isMusician()`, `isBandLeader()`) reliably evaluates correctly for every user.

## Purpose
Surfaced during 04-03 rollout: musicians whose role exists only in `users/{uid}.role` (legacy data; never promoted via `/api/admin/set-role`) have no custom claim, so any rule depending on `token.role` silently locks them out. We hotfix-relaxed `/setlists` to `isSignedIn()` — this plan lets us restore the principled `isMember()` / role-gated rules and prevents a recurrence.

## Output
- `POST /api/auth/sync-claims` — idempotent, self-service: the authenticated user asks the server to canonicalize their own claim from their Firestore profile
- Client integration in `auth-context.tsx`: on sign-in, detect claim/profile drift and call the sync route; force token refresh when the server updates the claim
- Unit tests covering: drift detection, no-op on match, token-refresh trigger, legacy-pending (no role in Firestore) path, non-authenticated rejection
- (Optional follow-up, separate plan) Restore `allow read: if isMember()` on `/setlists` once claim-sync has been live for at least a session cycle
</objective>

<acceptance_criteria>

## AC-1: Authenticated user with drift gets their claim fixed
```gherkin
Given an authenticated user whose users/{uid}.role = 'musician'
And whose auth custom claim token.role is undefined (drift)
When POST /api/auth/sync-claims is called by that user
Then the server calls setCustomUserClaims(uid, { ...existing, role: 'musician' })
And bumps users/{uid}.claimsUpdatedAt so the client picks up the refresh
And the response is { synced: true, role: 'musician' }
```

## AC-2: No-op when claim already matches profile
```gherkin
Given an authenticated user with token.role == users/{uid}.role
When the route is called
Then setCustomUserClaims is NOT called
And claimsUpdatedAt is NOT bumped
And the response is { synced: false, role: <current> }
```

## AC-3: Pending users (no Firestore role) are not touched
```gherkin
Given a user whose users/{uid}.role is 'pending' or missing
When the route is called
Then no claim change is made
And the response is { synced: false, role: 'pending' | null }
```

## AC-4: Unauthenticated requests rejected
```gherkin
Given no Authorization bearer
When POST /api/auth/sync-claims is called
Then the response is 401
```

## AC-5: Client auto-syncs on sign-in and after token refresh
```gherkin
Given a signed-in user
When onAuthStateChanged fires with currentUser
Then the client compares currentUser.getIdTokenResult().claims.role to profile.role
And if they differ (or claim is missing and profile.role is not 'pending')
Then the client calls POST /api/auth/sync-claims
And on success, force-refreshes the ID token so the new claim takes effect in this session
```

## AC-6: Idempotent — safe to call multiple times
```gherkin
Given the claim is already in sync
When the route is called repeatedly
Then no writes occur on any call after the first
And no rate-limit concerns for normal auth traffic (shares 'api' tier)
```

  <name>Task 1: Implement POST /api/auth/sync-claims</name>
  <files>src/app/api/auth/sync-claims/route.ts</files>
  <action>
    Use `createApiHandler(..., { role: undefined })` (any authenticated user, no role gate — that's the whole point).

    Flow:
      1. `const uid = ctx.auth!.uid`
      2. `const userDoc = await db.collection('users').doc(uid).get()`
      3. `const profileRole = userDoc.data()?.role` (can be undefined / 'pending')
      4. `const authUser = await getAuth().getUser(uid)`
      5. `const claimRole = authUser.customClaims?.role`
      6. If `profileRole === claimRole` → return `{ synced: false, role: profileRole ?? null }`
      7. If `!profileRole || profileRole === 'pending'` → return `{ synced: false, role: profileRole ?? null }` (AC-3)
      8. Otherwise drift:
         - `setCustomUserClaims(uid, { ...(authUser.customClaims ?? {}), role: profileRole })`
         - `db.collection('users').doc(uid).update({ claimsUpdatedAt: FieldValue.serverTimestamp() })`
         - Log info: `[sync-claims] uid=${uid} ${claimRole ?? 'none'} → ${profileRole}`
         - Return `{ synced: true, role: profileRole }`

    Rate-limit: `checkRateLimit(ctx.req, 'api')`.

    Avoid:
      - Trusting client-sent role (never accept a role param; always read from Firestore)
      - Overwriting unrelated claims (`soundEngineer`, future claims) — spread existing
      - Clearing the claim when Firestore says 'pending' (leave last-known alone; downgrade is the admin's explicit action via set-role)
  </action>
  <verify>`npx tsc --noEmit` clean; `npm run build` picks up the route</verify>
  <done>AC-1, AC-2, AC-3, AC-4, AC-6 satisfied server-side</done>
