<objective>
## Goal
Make the session cookie an authoritative source of truth for role by reading it directly from Firestore at cookie-mint time — not by trusting whatever the client's ID token happens to carry. Once the cookie is trustworthy, restore the proxy's role gate (removed in the `945478b` hotfix) so the edge fast-fails again and leader routes stay genuinely gated.

## Purpose
The `945478b` hotfix stripped the proxy's `!role || role === 'pending'` redirect because the session cookie could lag behind Firestore (freshly-approved musician → admin sets claim server-side → musician's cached ID token predates it → `createSessionCookie(idToken)` mints a session with no role → proxy bounces them to `/`). That hotfix fixed the loop but made the proxy toothless: pending users can now reach non-leader routes, and the same staleness class of bug could hide a future leader-promotion mis-gate.

This plan makes the server the authoritative role source at session-mint time and adds a refresh endpoint the client can hit when it detects drift. Then the proxy's gate is restored — it can trust the cookie.

## Output
- `POST /api/auth/session` reads `users/{uid}.role` from Firestore and stamps it into a companion `__session_role` HTTP-only cookie (server-signed or HMAC'd so the client can't forge it)
- Same route keeps minting the Firebase `__session` cookie (unchanged audience) — the companion cookie is strictly additive
- `POST /api/auth/refresh-session` — authenticated re-mint endpoint the client drift handler calls when `profile.role !== cookie role`
- Proxy reads `__session_role` (if present, authoritative) and falls back to Firebase session cookie role — gate restored for `!role || role === 'pending'` on non-public, non-leader routes
- Auth-context drift handler calls `refresh-session` alongside the existing ID-token refresh
- Unit tests covering: fresh mint with Firestore role, refresh with updated role, tampered cookie rejection, missing profile path
- `09-02-SUMMARY.md`
</objective>

## AC-1: Session mint reads role from Firestore
```gherkin
Given a newly-signed-in user whose ID token has no role claim
And whose Firestore users/{uid}.role is 'musician'
When the client POSTs /api/auth/session with that idToken
Then the Firebase __session cookie is minted as today
And a companion __session_role cookie is set with a signed payload containing role='musician'
And the response status is 200
```

## AC-2: Refresh endpoint updates the companion cookie
```gherkin
Given an authenticated user with an existing __session_role cookie
When the client POSTs /api/auth/refresh-session
Then the server re-reads users/{uid}.role from Firestore
And re-mints __session_role with the current value
And the response is 200 { role: <current> }
```

## AC-3: Tampered companion cookie is rejected
```gherkin
Given a client sends a __session_role cookie whose signature does not verify
When the proxy evaluates role
Then that cookie is ignored (treated as absent)
And the proxy falls back to the Firebase session cookie role
```

## AC-4: Proxy gate restored — authoritative cookie preferred
```gherkin
Given a signed-in user with session cookie role='pending' but __session_role signed role='musician'
When they access /setlists
Then the proxy admits the request (the signed companion cookie wins)
And Firestore rules enforce data-level gating
```

## AC-5: Pending users correctly blocked from non-leader secure routes
```gherkin
Given a user whose Firestore role is 'pending' (or missing)
When they access /setlists
Then the proxy redirects to '/' with detectRedirectLoop
And the app lands them on a 'waiting for approval' state at '/'
```

## AC-6: Drift handler re-syncs session cookie
```gherkin
Given a signed-in musician whose __session_role cookie is stale (pre-admin-promotion)
And whose Firestore profile is 'musician'
When the profile subscription fires and detects drift
Then the client calls /api/auth/refresh-session in addition to sync-claims + getIdToken(true)
And the next navigation passes the proxy gate
```

## AC-7: Missing Firestore profile leaves no role
```gherkin
Given a user whose Firestore users/{uid} doc doesn't exist yet (first-login race)
When /api/auth/session is called
Then __session_role is set with role=null (or not set at all)
And the proxy treats this as 'pending' — i.e., bounces to '/'
And the client drift handler will fire refresh-session once the profile write lands
```

<task type="auto">
  <name>Task 1: Mint + sign companion __session_role cookie in /api/auth/session</name>
  <files>src/app/api/auth/session/route.ts</files>
  <action>
    1. After verifying the idToken and creating the Firebase session cookie, also read `users/{uid}.role` via Admin SDK.

    2. Sign a compact payload `{ uid, role, iat, exp }` using HMAC-SHA256 with `SESSION_ROLE_SECRET` env var (add to env.mjs as required server-side string; fail fast with a clear error if missing).
       - Use Node's `crypto` module — `createHmac('sha256', secret).update(payload).digest('base64url')`
       - Payload format: `base64url({json}).<sig>` — simple, no new deps
       - Include `exp = iat + 14 days` matching SESSION_MAX_AGE

    3. Set the cookie alongside `__session`:
         response.cookies.set('__session_role', signed, {
             maxAge: SESSION_MAX_AGE,
             httpOnly: true,
             secure: production,
             path: '/',
             sameSite: 'lax',
         })

    4. Gracefully degrade: if the Firestore read fails or the user has no profile/role, set the payload with `role: null` — don't crash the sign-in flow.

    Export two small helpers in the same file (or a tiny `src/lib/session-role.ts` module):
      - `signRoleCookie(uid: string, role: string | null): string`
      - `verifyRoleCookie(raw: string): { uid: string; role: string | null } | null`

    Do NOT:
      - Trust the client to supply the role
      - Put the role into __session itself (that's a Firebase-minted cookie we can't modify)
      - Omit the uid from the signed payload (verifier must compare against auth uid later)
  </action>
  <verify>`npx tsc --noEmit` clean; `npm run build` picks up the route</verify>
  <done>AC-1, AC-7 satisfied</done>
