<objective>
## Goal
Plan 01 of Phase 2 — Save reliability. Two shippable items out of the Phase 2 ROADMAP line:

1. **"Saved Ns ago" indicator** — replace the tooltip-only save dot in `SetlistTopBar` with a live, visible, ticking text indicator driven by `lastSaved`.
2. **`beforeunload` / `pagehide` dropped-promise fix** — currently the unload handler calls `performSaveRef.current()` (an async Firestore write) fire-and-forget; the page unloads before the SDK request flushes. Fix: on unload, serialize pending state and `navigator.sendBeacon()` (with `fetch keepalive` fallback) to a new `/api/setlist/flush` Admin-SDK route.

**Deferred from ROADMAP Phase 2:** "Immediate save after clone" reduces to this same unload-flush fix once it lands — `cloneForNextWeek` already atomically persists the new doc via `addDoc`, so no additional clone-specific work is needed. Confirming-in-plan via a regression-guard assertion.

## Purpose
The band lead clones last week's setlist, tweaks ~3 songs, and often closes the laptop before the 1 s auto-save debounce fires. Today that can silently lose the tweak. Fixing the dropped promise before onboarding the band is the single highest-value reliability fix in Phase 2.

## Output
- New `/api/setlist/flush` POST route (Admin SDK, role-gated to doc owner / band_leader / admin, runs the same `StaleWriteError`-safe `expectedUpdatedAt` precondition as the in-page save)
- `use-setlist-logic.ts`: unload handler posts pending state via `sendBeacon` (or `fetch keepalive` fallback); in-page save path unchanged
- `SetlistTopBar.tsx`: visible "Saved Ns ago" text with a 10-second re-render ticker, replacing the tooltip-only dot
- Firestore rules: allow the new server-side update path (it already goes through admin SDK, so no rule change expected — flagged to confirm in Task 1)
- New test file asserting unload-flush invokes sendBeacon/keepalive and does not depend on Firebase SDK promise resolution


    - Do NOT accept `ownerId`, `createdAt`, `updatedAt`, `rev`, or `published*` fields from the client body — strip them at the schema level.
    - Body size guard: reject > 512 KB to avoid a beacon-size blowup.

  <decision>How to rate-limit the unload-flush endpoint</decision>
  <context>
    `/api/setlist/flush` is called exactly once on unload. Using the general `api` tier (60/min) is fine for normal use, but a mis-behaving client that re-fires pagehide in a loop could burn through rate-limit budget shared with other calls the user is making. Two reasonable approaches:
  </context>
  <options>
    <option id="shared-api">
      <name>Reuse the `api` tier (60/min)</name>
      <pros>Zero new infra; flush shares the normal per-user budget; consistent with Phase 1.3 pattern</pros>
      <cons>A pagehide loop could starve other calls in the same minute</cons>
    </option>
    <option id="dedicated-flush">
      <name>New `flushSave` tier (e.g. 20/min)</name>
      <pros>Isolates flush from other traffic; cap sized for realistic editor sessions (each edit debounce ≈ 1 s, so a human hits this far less)</pros>
      <cons>One more limiter; more to maintain; probably overkill</cons>
    </option>
  </options>

    **2a. `use-setlist-logic.ts` — fix the dropped-promise unload path (lines 372–401):**

    Split the current single flushSave into two handlers:

    ```
    // Tab-switch / visibility hidden → in-page save is fine (page still alive)
    const flushViaSDK = () => {
      if (hasPendingSave.current && saveTimeoutRef.current) {
        clearTimeout(saveTimeoutRef.current)
        saveTimeoutRef.current = null
        hasPendingSave.current = false
        performSaveRef.current()
      }
    }

    // True unload (pagehide/beforeunload) → SDK promise will be killed. Beacon-only.
    const flushViaBeacon = () => {
      if (!hasPendingSave.current) return
      const { setlistId: id, name: n, tracks: t, eventDate: ed, rabbi: rab, serviceNotes: sn, musicians: mus } = latestRef.current
      if (!id || !n || !canEdit) return
      const payload = {
        setlistId: id,
        expectedUpdatedAt: lastSeenUpdatedAtRef.current,
        data: {
          name: n,
          tracks: t,
          trackCount: t.length,
          eventDate: serializeDate(ed),  // hoist serializeDate to module scope
          rabbi: rab,
          serviceNotes: sn?.trim() || undefined,
          musicians: mus.length > 0 ? mus : undefined,
        },
      }
      const blob = new Blob([JSON.stringify(payload)], { type: 'application/json' })
      const ok = typeof navigator !== 'undefined' && navigator.sendBeacon
        ? navigator.sendBeacon('/api/setlist/flush', blob)
        : false
      if (!ok) {
        // keepalive fetch fallback (Safari < 13 etc.)
        fetch('/api/setlist/flush', { method: 'POST', body: blob, keepalive: true, headers: { 'Content-Type': 'application/json' } }).catch(() => {})
      }
      // Clear local pending flag so React unmount doesn't try to re-fire
      hasPendingSave.current = false
      if (saveTimeoutRef.current) { clearTimeout(saveTimeoutRef.current); saveTimeoutRef.current = null }
    }

    document.addEventListener('visibilitychange', () => { if (document.visibilityState === 'hidden') flushViaSDK() })
    window.addEventListener('beforeunload', flushViaBeacon)
    window.addEventListener('pagehide', flushViaBeacon)
    ```

    Notes:
    - Hoist `serializeDate` from inside `performSave` to module scope (or a nearby helper) so both paths use identical date serialization. Do NOT duplicate the logic.
    - The beacon payload includes NO auth header. Auth is via the ambient session cookie / Bearer header the browser already attaches. Confirm `/api/setlist/flush`'s `createApiHandler` reads auth from cookies (look at `withAuth` — if it requires Bearer in header, document the gap and fall back to `fetch keepalive` which CAN set headers). If the app uses cookie-session auth for Firebase, beacon works natively; if it uses header-Bearer only, use the `fetch keepalive` path unconditionally and skip sendBeacon.
    - Keep the existing in-page `performSave` path completely untouched — only the unload listener changes.

    **2b. `SetlistTopBar.tsx` — replace dot+tooltip with visible ticker (lines 77–88):**

    ```tsx
    const [, forceTick] = useState(0)
    useEffect(() => {
      if (!lastSaved) return
      const id = setInterval(() => forceTick(n => n + 1), 10_000)
      return () => clearInterval(id)
    }, [lastSaved])

    function formatSince(d: Date) {
      const s = Math.round((Date.now() - d.getTime()) / 1000)
      if (s < 5) return 'Saved just now'
      if (s < 60) return `Saved ${s}s ago`
      const m = Math.round(s / 60)
      if (m < 60) return `Saved ${m}m ago`
      const h = Math.round(m / 60)
      return `Saved ${h}h ago`
    }

    // in render:
    {saving ? <span className="text-xs text-muted-foreground">Saving…</span>
      : lastSaved ? <span className="text-xs text-muted-foreground">{formatSince(lastSaved)}</span>
      : <span className="text-xs text-muted-foreground/70">Not saved</span>}
    ```

    - Keep the existing dot-color semantics as a secondary cue (green/pulse/gray) OR replace them with the text-only treatment. `/ui-ux-pro-max` picks which.
    - Do NOT introduce a new prop — keep reading `lastSaved`/`saving` from the existing hook output.
    - Ensure the ticker interval clears on unmount (hence the `useEffect` return).
