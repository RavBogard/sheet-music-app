<objective>
## Goal
Build the complete data layer for Live Setlist Sync: Firestore types, security rules, permission model, song group system, swap function, and API routes. After this plan, all backend infrastructure is in place for the UI layer (Plan 02) to consume.

## Purpose
Musicians need real-time song swapping during live worship services. This plan establishes the foundational data model, permission system, and server-side infrastructure that all swap UI components will build on.

## Output
- New TypeScript types for song groups and swap history
- Extended LiveState with lastSwap metadata for receiver toasts
- canLiveSwap permission (custom claim + profile field + auth context)
- useLiveSwapAccess and useSongGroups hooks
- swapLiveTrack() atomic swap function
- API routes: set-live-swap, song-groups CRUD, seed-song-groups
- Firestore security rules for canLiveSwap, songGroups config, swapHistory
</objective>

## AC-1: Song group types and config document
```gherkin
Given the app has no song grouping concept
When the new types and config/songGroups Firestore doc are deployed
Then SongGroup, SongGroupEntry, and SongGroupsConfig TypeScript interfaces exist
And config/songGroups can store groups with labels, aliases, songs, and sortOrder

```

## AC-2: canLiveSwap permission model
```gherkin
Given a user with canLiveSwap: true on their profile
When they are authenticated
Then useAuth() returns canLiveSwap: true
And useLiveSwapAccess() returns canSwap: true
And admin/band_leader users also get canSwap: true (via role hierarchy)
And the /api/admin/set-live-swap endpoint can toggle the flag (Firestore + custom claims)
```

## AC-3: Firestore security rules enforce swap permissions
```gherkin
Given a setlist with liveState.enabled: true
When a user with canLiveSwap custom claim calls updateDoc with tracks + liveState fields
Then the write succeeds
And writes to other fields (name, rabbi, serviceNotes) are rejected via affectedKeys().hasOnly()
And writes when liveState.enabled: false are rejected
And writes faster than 2 seconds apart are rejected via isNotTooFrequent()
```

## AC-4: swapLiveTrack function performs atomic swap
```gherkin
Given a live setlist with tracks and a song group with alternatives
When swapLiveTrack() is called with a track index and replacement track
Then the tracks array is updated with the new track at that index
And liveState.lastSwap is set with swap metadata (previous/new title, swapId, timestamp)
And a swapHistory subcollection entry is written (fire-and-forget)
And the write is a single atomic updateDoc call
```

## AC-5: Song groups CRUD and seeding API routes
```gherkin
Given an admin or band_leader user
When they call GET /api/admin/song-groups
Then all song groups from config/songGroups are returned
When they call PUT /api/admin/song-groups with a group definition
Then that group is upserted in config/songGroups
When they call POST /api/admin/seed-song-groups
Then song groups are auto-populated from liturgical template slot labels and library matches
```

## AC-6: useSongGroups hook provides group lookups
```gherkin
Given config/songGroups has been populated with song groups
When useSongGroups() is called in a component
Then it returns real-time group data via onSnapshot
And getAlternatives(liturgicalSlot, currentFileId) returns other songs in that group
And hasAlternatives(liturgicalSlot, currentFileId) returns boolean for swap eligibility
```

## AC-7: Build and type-check pass
```gherkin
Given all new types, hooks, and API routes are implemented
When running tsc --noEmit and next build
Then there are zero type errors
And the build completes successfully
```
