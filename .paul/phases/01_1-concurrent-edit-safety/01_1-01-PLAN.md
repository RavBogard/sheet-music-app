<objective>
**Goal:** Prevent concurrent edits from silently destroying each other's work on `setlists/{id}`. Every `tracks`-touching write goes through a Firestore transaction with an `updatedAt` precondition, and the editor subscribes to the setlist doc so remote changes are visible immediately.

**Purpose:** Wave 2 research confirmed: today every `tracks` write is a full-array replace with no transaction, no version check, and the editor hook doesn't subscribe to incoming changes. Two devices editing the same setlist (or Rabbi + Randy both editing before a service) will silently overwrite each other. This is the #1 blocker for band onboarding.

**Output:** Editing-concurrency is race-free. If a stale write is detected, the editor surfaces a "Setlist changed — merge?" banner instead of silently losing data. A one-shot migration stamps every existing setlist with a starting `updatedAt`.
</objective>

<acceptance_criteria>

**AC-1: All `tracks`-touching writes use a transaction with an `updatedAt` precondition.**
- Given a setlist doc with `updatedAt = T0` and a client holding a stale `expectedUpdatedAt = T0 - δ`
- When the client calls `updateSetlist` / `swapTrack` / `performSave` / any other write path
- Then the transaction throws a `STALE_WRITE` error; no mutation occurs.

**AC-2: Non-stale writes advance `updatedAt` to a new server timestamp.**
- Given a valid write
- When it commits
- Then `updatedAt` becomes a fresh server timestamp (via `serverTimestamp()`).

**AC-3: Editor subscribes to the setlist doc and merges remote changes.**
- Given the editor is open with local state
- When another device (or tab) commits a successful write
- Then the editor's local `tracks`/`name`/`rabbi`/etc. reflect the remote state (merged, see merge rules below) within ~2 seconds.

**AC-4: Stale writes surface a merge banner instead of silently dropping.**
- Given a write that fails with `STALE_WRITE`
- When the editor receives the error
- Then a dismissible banner appears: "Setlist changed on another device. Refresh to see latest." with a "Refresh" action that replaces local state with remote. The user's unsaved edits, if any, are preserved in a local diff panel they can re-apply after refresh.

**AC-5: Every existing setlist doc has an `updatedAt` after the migration.**
- Given the production `setlists` collection before the migration
- When `scripts/backfill-setlist-rev.ts` runs
- Then every doc without `updatedAt` is stamped with a server timestamp. Re-running touches 0 docs.

**AC-6: Typecheck + tests green.**
- `npx tsc --noEmit` → exit 0
- `npx vitest run` → all tests pass

**AC-7: Production smoke test.**
- Given production post-deploy + migration
- When I open the same setlist in two tabs and edit both within a ~3-second window
- Then the later write fails with the banner; no data is silently lost.

**Task 2 — Service layer: wrap every `tracks` write in a transaction with precondition.**
- File: `src/lib/setlist-firebase.ts`
- Action:
  - Introduce a helper `async function updateSetlistWithVersion(ref, expectedUpdatedAt: Timestamp | null, patch: Record<string, unknown>)` that:
    1. `runTransaction(db, async tx => { const snap = await tx.get(ref); ...})`
    2. Reads the doc's current `updatedAt`.
    3. If `expectedUpdatedAt` is non-null and doesn't match (compare as Timestamps), throw `new Error('STALE_WRITE')` with a typed sentinel.
    4. If `expectedUpdatedAt` is null (legacy docs with no `updatedAt`), allow the write and stamp `updatedAt`.
    5. Apply the patch + `updatedAt: serverTimestamp()`.
  - Rewire `updateSetlist(id, data, expectedUpdatedAt)` → uses the helper. Pass through `expectedUpdatedAt` from callers.
  - Rewire `swapTrack` to use a transaction directly: read current `tracks`, mutate index, call helper with the patch.
  - Leave `createSetlist`, `deleteSetlist`, `duplicateSetlist`, `cloneForNextWeek`, `saveAsTemplate` alone (they're not concurrent-edit cases).
- Verify:
  - Unit tests in `setlist-firebase.test.ts` for: (1) non-stale write succeeds, (2) stale write throws `STALE_WRITE`, (3) null `expectedUpdatedAt` acts as skip-check.

**Task 3 — Editor hook: subscribe to remote changes + track `expectedUpdatedAt`.**
- File: `src/hooks/use-setlist-logic.ts`
- Action:
  - In the editor-mount effect, call `subscribeToSetlist(setlistId, callback)`. Store the most recent remote `updatedAt` in a ref (`lastSeenUpdatedAtRef`).
  - When a remote snapshot arrives AND the local `hasPendingSave` flag is false AND no local edits are unsaved, merge remote state into local state silently (user is reading).
  - When a remote snapshot arrives AND the user has unsaved edits OR a save is in flight, do **not** auto-merge; instead store the remote snapshot in a `pendingRemoteSnapshotRef` and surface a banner (AC-4).
  - `performSave` now passes `lastSeenUpdatedAtRef.current` as `expectedUpdatedAt` to `updateSetlist`.
  - On `STALE_WRITE`, cancel the save, do NOT toast-error, set a `setlistStaleDetected` state that the banner reads.
  - Cleanup: unsubscribe on unmount.
- Verify: mocked Firestore test — two in-flight "writes" with staggered `updatedAt`, the second one throws.
- Done: AC-3 (subscribe + auto-merge), AC-4 (staleness detection).

<boundaries>

**DO NOT CHANGE:**
- `createSetlist`, `deleteSetlist`, `duplicateSetlist`, `cloneForNextWeek`, `saveAsTemplate` — they aren't concurrent-edit sensitive.
- Publish's core semantic (`publishedAt` / `publishedSnapshot` / notification fan-out). Only add `updatedAt` to the writes.
- Firestore security rules (rules don't need to know about `updatedAt` precondition — it's a client+server convention).
- The UI of any other phase's scope (wizard, OverflowMenu, etc.).

**SCOPE LIMITS:**
- **Minimum viable merge UX.** Banner + "Take remote" + "Keep my changes" is enough. No visual diff, no per-field merge, no operational transform. Can upgrade in a later milestone if we ever hit real multi-leader simultaneous editing.
- Do NOT convert to per-track subdocuments. We keep the `tracks` array shape.
- Do NOT introduce a CRDT or Yjs dependency.
- Do NOT chase the P1 `beforeunload` dropped-promise item here (that's Phase 2).

</boundaries>
