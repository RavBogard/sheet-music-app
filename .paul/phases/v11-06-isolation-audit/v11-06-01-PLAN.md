<objective>
## Goal
Close the rules-layer axis of the v11-06 cross-tenant isolation security audit (the milestone close gate):
1. **Close the one known deferred read gap** — `getCongregationContext`'s `leadHistory` calls `getAllSetlists()` cross-tenant, so a BL author's congregation-context call returns CRC service history. Scope it to the caller's org.
2. **Adversarial Firestore-rules audit** — prove (emulator-backed, BLOCKING) that a client authenticated as one tenant CANNOT read or write another tenant's docs across the v11-05 collections (`setlistTemplates`, `users`, `scheduling_assignments`, the `config/congregation` singleton). Characterize each collection's enforcement layer (rules vs application-only); where a client can directly read another tenant's data and the wall must hold, harden `firestore.rules` until the adversarial test fails-closed.

## Purpose
Cross-tenant isolation is security-critical (ROADMAP constraint 3: "a mis-tagged backfill row or unscoped MCP tool is a data-leak class bug"; constraint 4: hard wall ACROSS tenants). v11-02/05 scoped MCP (admin-SDK, server-side) and the in-app read paths (in-memory `rowOrg` filters), but a malicious or buggy CLIENT can hit Firestore directly — and `scheduling_assignments` IS read client-side (`subscribeToAllUpcomingAssignments`). The rules layer is the only wall that survives an app-layer-filter bypass. This plan proves that wall holds for the v11-05 collections and closes the last known deferred cross-tenant read.

## Output
- `getCongregationContext` passes the caller org to `getAllSetlists` (leadHistory is tenant-scoped); regression test added.
- `firestore-rules-orgscope.emulator.test.ts` extended with adversarial cross-tenant cases for the four v11-05 collections.
- `firestore.rules` hardened iff a real client-readable cross-tenant leak is found (then deployed).
- `v11-06-01-SUMMARY.md` recording the per-collection enforcement-layer findings (feeds the v11-06-03 AUDIT.md report).
