<objective>
## Goal
Close audit finding **D01** — setlist delete must cascade to `scheduling_assignments`, sub-collections (`history`, `emailEvents`, `tasks`), and (per AC-6 path selected in Task 1) user `notifications` referencing the deleted setlist. Today `deleteSetlist()` only drops the parent doc; everything pointing at it lingers forever.

## Purpose
Orphan assignments create phantom tasks/notifications for musicians. Orphan sub-collections bloat Firestore billing. Both erode "bulletproof and easy and intuitive" — the band-onboarding quality bar. This is the **last remaining v4.3 P0**; closing it takes the milestone to 10/10.

## AC-1: Authorized cascade delete removes setlist + dependents
```gherkin
Given an admin or band_leader
And a setlist with scheduling_assignments, history, emailEvents, tasks, and any other sub-collections
When POST /api/setlist/delete with { setlistId } is called
Then the setlist doc, all matching scheduling_assignments, and all sub-collection docs are deleted
And the response is 200 with { deleted: { setlist, assignments, tasks, subcollections? } }
```

## AC-2: Non-band-leader users cannot cascade delete
```gherkin
Given an authenticated user without admin/band_leader role
When POST /api/setlist/delete is called
Then the response is 403 (createApiHandler role gate)
And no documents are deleted
```

## AC-3: Unknown setlistId returns 404 without side effects
```gherkin
Given a setlistId that does not exist
When POST /api/setlist/delete is called by an admin
Then 404 is returned
And no cascading deletes run
```

## AC-4: Partial-failure tolerance
```gherkin
Given the setlist exists and one phase (e.g., assignment cleanup) fails mid-way
When the route runs
Then the parent setlist is still deleted (idempotent retry is safe because re-delete is a no-op)
And the response body documents which phases succeeded and which failed
```

## AC-5: Client call-site unchanged
```gherkin
Given existing UI callers of deleteSetlist(id)
When they invoke the rewired function
Then it completes without signature or error-shape changes
And existing toast/error handling behaves identically
```

## AC-6: Notifications cascade (path decided in Task 1)
```gherkin
Given user notifications referencing the deleted setlist
When the cascade runs
Then either:
  (a) notifications with payload.setlistId == id are batch-deleted via collectionGroup query (requires composite index — ship index in same commit), OR
  (b) notifications are left untouched because query requires an index we don't want to create; scope limit documented in SUMMARY (dead-link notifications render as "(deleted)" in NotificationBell — tolerable)
```

  <name>Task 2: Implement POST /api/setlist/delete with Admin SDK cascade</name>
  <files>src/app/api/setlist/delete/route.ts</files>
  <action>
    Use `createApiHandler(async (ctx) => {...}, { role: 'band_leader' })`.

    Validate body: `z.object({ setlistId: z.string().min(1) }).strict()` (rejects passthrough per v4.2 P4 D02 pattern).

    Cascade order (retry-safe — parent last so failure of a phase still leaves the setlist removable on retry ... BUT recursiveDelete + client rules mean best ordering is):
      1. Check parent exists → 404 if not (AC-3)
      2. Batch-delete `scheduling_assignments` where `setlistId == id`:
         - Query, chunk at ≤500 docs per WriteBatch, commit
         - Collect count; errors → log + continue (best-effort per-phase)
      3. Batch-delete `tasks` where `setlistId == id` — same pattern
      4. (If AC-6 path (a)) collectionGroup('notifications') where `setlistId == id` — batch delete; errors → log + continue
      5. `firestore.recursiveDelete(setlistRef)` — removes parent + history + emailEvents + any other subcollection in one server-side traversal

    Response shape:
      { deleted: { setlist: 1, assignments: N, tasks: N, notifications: N|null },
        errors: string[] (empty on full success) }

    Rate-limit: share `api` tier (consistent with bulk write ops).

    Avoid:
      - Doing the recursiveDelete before the flat-collection cleanup (if recursiveDelete fails, we want the dependents already gone so the state is consistently "deleted" on retry)
      - Swallowing errors silently — every phase-error logs + accumulates into `errors[]`
      - Deleting shared resources (users, library files, congregation docs)
  </action>
