<objective>
## Goal
Close D03 from the v4.3 audit: eliminate the read-then-write race on `setlist.musicians` + `assignedUids` in `POST /api/scheduling/assign` by wrapping the sync step in a Firestore `runTransaction`.

## Purpose
Today, after creating individual `scheduling_assignments`, the route re-fetches the setlist, computes merged musicians, and `update`s with the merged array (`src/app/api/scheduling/assign/route.ts:192-220`). Two concurrent calls (two band leaders assigning at once) can both read the same "before" state, merge their additions independently against that stale baseline, and one final write overwrites the other — silently dropping musicians.

`runTransaction` gives us optimistic concurrency: Firestore re-reads and retries the closure if the doc changed during the transaction, so both assignments land.

## Output
- The "sync setlist musicians" block runs inside `db.runTransaction`
- `scheduling_assignments` document creation remains outside the transaction (those are per-musician writes that already succeed/fail independently)
- No other behavior change (error messages, success shape, FCM push flow untouched)
- Regression test that simulates two concurrent assigns with Firestore emulator-style mocks and verifies no musician is lost
</objective>

  <files>src/app/api/scheduling/assign/route.ts</files>
  <action>
    Replace lines ~192-220 (the "Also update the setlist's musicians array to keep it in sync" block) with:
    ```ts
    // D03 fix: read + write under a transaction so concurrent assigns can't
    // both merge against the same stale baseline and drop each other's writes.
    try {
        const setlistRef = db.collection('setlists').doc(setlistId)
        await db.runTransaction(async (tx) => {
            const setlistDoc = await tx.get(setlistRef)
            if (!setlistDoc.exists) return
            const existingMusicians = (setlistDoc.data()?.musicians || []) as Array<{ uid?: string; name: string; email: string; instrument?: string }>
            const existingUids = new Set(existingMusicians.map(m => m.uid).filter(Boolean))
            const newMusicians = musicians
                .filter(m => !existingUids.has(m.uid))
                .map(m => ({ uid: m.uid, name: m.name, email: m.email, instrument: m.instrument || null }))
            if (newMusicians.length === 0) return
            const mergedMusicians = [...existingMusicians, ...newMusicians]
            tx.update(setlistRef, {
                musicians: mergedMusicians,
                assignedUids: mergedMusicians.map(m => m.uid).filter(Boolean),
            })
        })
    } catch (e) {
        logger.warn('[Scheduling] Failed to sync setlist musicians array:', e)
    }
    ```
    Do NOT move the individual `scheduling_assignments` creation loop into the transaction — those are independent per-musician writes that already handle per-row failure via the `errors` array.
    Keep the surrounding `try/catch` with `logger.warn` so a transaction failure doesn't 500 the whole assign response.
  </action>
