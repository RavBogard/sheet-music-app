<objective>
## Goal
Close D02 from the v4.3 audit at the correct scope: tighten the write-boundary zod schemas in `POST /api/setlist/flush` so clients can no longer inject arbitrary fields into `setlists[*].tracks[*]` or `setlists[*].musicians[*]` via a permissive `.passthrough()`.

## Purpose
`trackSchema = z.object({}).passthrough()` and `musicianSchema = ...passthrough()` (both in `src/app/api/setlist/flush/route.ts`) let a client post any shape as long as the named required fields exist. The route then writes `data.tracks` + `data.musicians` straight into Firestore via `patch.tracks = data.tracks`. Although the top-level `patch` is an explicit allowlist, the inner track/musician objects are NOT — so a malicious client can inject `role: 'admin'`, `_backdoor: true`, or overwrite server-managed booleans on individual entries.

Read-path schemas in `src/types/schemas.ts` keep `.passthrough()` — they need to tolerate schema evolution + legacy Firestore docs. Don't touch them.

The print route's `.passthrough()` is a non-issue (no Firestore write) — leave as-is with a `// NOTE: print route — no Firestore write, passthrough acceptable` comment so a future audit doesn't re-flag.

## Output
- Strict write-boundary track + musician schemas in flush/route.ts
- Unknown fields on tracks / musicians return 400 via zod's `.strict()` rejection
- `src/lib/__tests__/flush-schema.test.ts` with regression coverage: known fields pass, unknown fields reject, existing happy-path body still passes
- Non-Firestore-write `.passthrough()` in print/route.ts annotated
- tsc clean, full suite green, next build green
</objective>
