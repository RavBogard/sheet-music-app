<objective>
## Goal
Org-scope the `scheduling_assignments` collection READ + WRITE so a BL caller/host
sees only Brothers Lazaroff assignments and a CRC caller/host sees only CRC — with
CRC provably unchanged. The org is **denormalized from each assignment's parent
setlist** (already org-stamped since v11-02-03 / v11-04): stamp `orgId` at create,
backfill legacy rows from their setlist, and filter every genuinely cross-tenant
caller-facing read in-memory (`rowOrg(doc.orgId) === callerOrg`, missing → `'crc'`).

## Purpose
v11-02 walled MCP setlist/song reads+writes and v11-04 closed the consumer web read
surface; `scheduling_assignments` was explicitly deferred. It is the last large
roster-side collection feeding band-leader views (upcoming-assignments dashboard,
suggest-band ranking, history analytics, pending lists). Closing it is a prerequisite
for the v11-06 cross-tenant isolation audit (the milestone close gate). Data-isolation
work → emulator-backed scoping tests are mandatory (quality floor).

## Output
- `SchedulingAssignment.orgId` written at create (denormalized from the setlist).
- Every cross-tenant caller-facing assignment read filtered to the caller/host org.
- An idempotent, dry-run-first backfill stamping legacy assignments' `orgId` from
  their parent setlist (CRC-safe even un-run, like v11-05-02).
- Emulator-backed org-scoping cases in the proven `mcp-roster` harness.
- `v11-05-03-SUMMARY.md`.
</objective>

<acceptance_criteria>

## AC-1: Assignment carries its setlist's org at create
```gherkin
Given a setlist stamped orgId='brotherslazaroff'
When a musician is assigned to it via assignMusiciansService (HTTP /assign or MCP assign_musicians)
Then the new scheduling_assignments doc is written with orgId='brotherslazaroff'
And assigning to a CRC setlist (or a setlist with no orgId) writes orgId='crc'
```

## AC-2: Cross-tenant assignment reads are org-scoped
```gherkin
Given CRC and BL each have confirmed/pending assignments
When a BL caller/host invokes subscribeToAllUpcomingAssignments / suggest-band /
     history / remind(all) / listPendingAssignments / list_musicians_on_date /
     suggestBand / list_service_personnel
Then only BL assignments (orgId='brotherslazaroff', or crc-default if unstamped+BL setlist) appear
And no CRC musicianName / count / setlistName leaks into the BL result
And the symmetric CRC call returns byte-identical results to pre-change (crc default holds with zero backfill)
```

## AC-3: Inheriting + intentional reads are unchanged
```gherkin
Given the setlistId/musicianUid-scoped reads and the all-tenant cron
When they run after this change
Then their behavior and results are identical to pre-change (no org param threaded, no filter added)
And the SUMMARY documents each with its inherit/intentional rationale
```

## AC-4: Backfill is dry-run-first, idempotent, CRC-safe, reversible
```gherkin
Given legacy scheduling_assignments docs without orgId
When scripts/backfill-assignment-orgids.mjs runs WITHOUT --apply
Then it reports per-org counts derived from each doc's parent setlist and writes nothing
When it runs WITH --apply
Then each doc is stamped orgId = its parent setlist's org (default 'crc' if the setlist is missing/unstamped),
     guarded by an idempotency marker, and a rollback path is documented
And because reads default missing→'crc', CRC stays fully visible even if the backfill never runs
```
