<objective>
## Goal
Fix **H3** — make served audio **seekable**. The two routes that serve audio bytes —
`/api/drive/file/[fileId]` (what `AudioViewer` actually plays, `AudioViewer.tsx:60`) and
`/api/recordings/file/[id]` — return a plain `200` with the full body and **no `Accept-Ranges`,
no `Range` handling, no `206`**. iPad WebKit therefore disables the scrubber / can't seek a
streamed recording. Add HTTP Range support so the native `<audio>` element can seek.

## Purpose
Recordings on the iPad Perform surface are a core band affordance (run-3 B-11 + the wishlist
"audio/recordings awkward"). "Bulletproof performance" includes being able to scrub to the bridge
of a reference track mid-rehearsal — today you can only play from 0:00. Pure serving-layer fix; no
UI restyle (the `<audio controls>` stays native per `AudioViewer.tsx`).

## Output
- A pure, unit-tested `byteRangeResponse` helper that turns an in-memory buffer + content-type +
  base headers into the correct `200` (with `Accept-Ranges` + `Content-Length`), `206`
  (`Content-Range` + sliced body), or `416` response based on the request's `Range` header.
- Both audio-serving routes wired through it — seeking works, full-file GETs unchanged (backward
  compatible), all existing auth gates / CORS / Cache-Control / `Content-Type` / `X-Served-From`
  headers preserved.
</objective>

<acceptance_criteria>

## AC-1: a Range request returns 206 with the correct slice
```gherkin
Given a request to /api/drive/file/<audioId> (or /api/recordings/file/<id>) with header `Range: bytes=100-199`
When the route serves the bytes
Then it responds 206 Partial Content with `Content-Range: bytes 100-199/<total>`, `Content-Length: 100`,
  `Accept-Ranges: bytes`, and a body equal to bytes 100–199 of the file
```

## AC-2: a normal (no-Range) GET still returns the whole file, now advertising Range
```gherkin
Given a request with NO `Range` header
When the route serves the bytes
Then it responds 200 with the full body, the existing Content-Type / Cache-Control / CORS / X-Served-From
  headers UNCHANGED, plus `Accept-Ranges: bytes` and a correct `Content-Length`
And an open-ended `Range: bytes=500-` returns 206 from byte 500 to EOF
```

## AC-3: an unsatisfiable Range is rejected, and auth/not-found gates are unchanged
```gherkin
Given a `Range: bytes=999999999-` beyond the file size (or a malformed range)
When the route serves the bytes
Then a beyond-EOF range returns 416 with `Content-Range: bytes */<total>` (malformed/multi-range falls back to a normal 200)
And the existing 401 (untrusted) / 404 (missing) / 502 gates fire exactly as before — Range only affects the success path
```

  <name>Task 1: pure byteRangeResponse helper + unit tests</name>
  <files>src/lib/http/byte-range.ts, src/lib/http/__tests__/byte-range.test.ts</files>
  <action>
    Create `src/lib/http/byte-range.ts` exporting a pure helper (no firebase, no next/server side
    effects beyond constructing a NextResponse) — e.g.
    `byteRangeResponse(body: Uint8Array, opts: { contentType: string; rangeHeader: string | null; status?: number; headers?: Record<string,string> }): NextResponse`:
    - Parse a single `bytes=start-end` range (RFC 7233 subset): `start-end`, `start-` (open end → EOF),
      `-suffix` (last N bytes). Ignore multi-range (comma) + non-`bytes` units → treat as no range.
    - No/!range → 200: body as `new Uint8Array(body)`, merge caller `headers`, ADD `Accept-Ranges: bytes`
      and `Content-Length: <total>`.
    - Valid range → clamp end to `total-1`; 206 with sliced body, `Content-Range: bytes start-end/total`,
      `Content-Length: <chunk>`, `Accept-Ranges: bytes`, merged caller headers.
    - Unsatisfiable (start ≥ total, or start>end) → 416 with `Content-Range: bytes */total` + caller headers.
    - Always preserve caller-supplied `Content-Type` + extra headers (CORS, Cache-Control, X-Served-From).
    Unit-test every branch (no header / closed range / open `500-` / suffix `-100` / beyond-EOF 416 /
    malformed `bytes=abc` → 200 / multi-range `0-1,2-3` → 200). Assert status, Content-Range, Content-Length,
    Accept-Ranges, and that a passed-in custom header survives.
    Avoid: streaming/partial origin fetch (out of scope — bytes are already fully in memory in both
    callers; we slice in-process, which is what enables WebKit seeking). No new deps.
  </action>
  <verify>SKIP_ENV_VALIDATION=1 npx vitest run src/lib/http/__tests__/byte-range.test.ts (all branches green); tsc clean</verify>
  <done>AC-1/AC-2/AC-3 logic proven at the unit level on the shared helper.</done>
