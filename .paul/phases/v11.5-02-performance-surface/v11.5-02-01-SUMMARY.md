# Phase v11.5-02 Plan 01: H3 seekable audio (HTTP Range) Summary

**Both audio-serving routes — `/api/drive/file/[fileId]` (what `AudioViewer` plays) and `/api/recordings/file/[id]` — returned a plain `200` with the full body and no `Accept-Ranges`/`Range`/`206`, so iPad WebKit disabled the `<audio>` scrubber (play-from-0:00-only). Added a pure, unit-tested `byteRangeResponse` helper and wired both routes' success path through it: a `Range` request now gets a correct `206` slice, no-Range GETs stay byte-identical (plus `Accept-Ranges`), and an unsatisfiable range returns `416`. All auth / rate-limit / 404 / 502 gates are untouched — Range governs only the success response.**
