    Create `scripts/bootstrap-songs.ts` following the SAME shape as `scripts/migrate-v50.ts`:
    - Re-use the `MigrationFirestore` abstract interface (or import it directly from migrate-v50.ts and re-export)
    - CLI flags: `--dry-run` (default), `--apply`, `--rollback`, `--force`, `--no-backstitch`, `--help`
    - Marker doc path: `system/v54SongsBootstrap` (2-segment doc per the v50-07-01 audit fix; do NOT use a 3-segment collection path)
    - Marker shape: `{ appliedAt: number (ms), count: number, includedBackstitch: boolean }`
    - dotenv config from `.env.local` for the firebase-admin entry point (mirror migrate-v50.ts header)

    Core algorithm:
    1. If `--rollback`: enter `rollback()` (delete bootstrap-created docs that have no defaults/recent; delete marker; see AC-4).
    2. Idempotency check: read marker doc; if exists AND not `--force`, log "Already applied at <ts>" and exit early.
    3. Read `library_index` collection, filter `status !== 'archived'` and require `name` truthy. Each row contributes ONE candidate.
    4. For every candidate `L`:
       - Read existing `songs/{L}` (may exist from prior sticky-memory propagation against a same-id songId, though this should be rare in practice).
       - Compute the bootstrap payload: `{ id: L, title: name, normalizedTitle: name.toLowerCase().trim(), fileId: L }`. PRESERVE existing `defaults`, `recent`, `updatedAt`, `createdAt` if they exist on the doc — merge instead of overwrite.
       - In `--dry-run`: log a sample of 3, log total count, do NOT write.
       - In `--apply`: write via `setDoc('songs/{L}', merged)` (full set, not partial update — matches migrate-v50.ts setDoc pattern).
    5. Back-stitch (default ON; `--no-backstitch` disables):
       - List `setlists/*`, walk every embedded `tracks[]`, AND list `tracks/*` (top-level — populated by v50-07-03 lazy hydration).
       - For each track: if `track.fileId` is set AND `track.songId` is NOT set AND `songs/{fileId}` exists → write `track.songId = fileId` via `updateDoc`.
       - Embedded tracks live inside the parent setlist doc — for those, accumulate updates per-setlist and write the whole setlist with the patched tracks[] in one `updateDoc('setlists/{id}', { tracks: ... })` call.
       - Top-level tracks/* — one `updateDoc('tracks/{id}', { songId: fileId })` per row.
       - Log back-stitch count separately from songs-written count.
    6. Write marker doc with `appliedAt`, `count` (songs written + skipped-already-current), `includedBackstitch`.

    CLI entry point: at the bottom of the file, if `require.main === module`, read `process.argv`, instantiate firebase-admin (mirror migrate-v50.ts initialization — same patterns for `serviceAccountKey` env vars), wrap with the production `MigrationFirestore` adapter, call `runBootstrap()`. Log to stdout.

    Tests in `scripts/__tests__/bootstrap-songs.test.ts`:
    - Use the same in-memory `MigrationFirestore` fake pattern as `scripts/__tests__/migrate-v50.test.ts` (look there first; reuse the helper or copy verbatim).
    - Cases (one `it()` per AC, plus edge cases):
      * dry-run with N seeded library_index docs → reports correct count, writes nothing, no marker created
      * apply with mix of active + archived → archived rows skipped; only active rows written
      * apply preserves pre-existing defaults/recent on a song that already has memory
      * apply twice without --force → second run skips; with --force → idempotent (no diff)
      * back-stitch sets songId on tracks where fileId matches and songId was unset
      * back-stitch leaves track.songId untouched when already set
      * --no-backstitch flag skips the back-stitch loop entirely
      * rollback deletes ONLY bootstrap-created docs without defaults/recent (preserves sticky-memory rows; deletes marker)
      * normalizedTitle equals title.toLowerCase().trim() (no fancy unicode normalization here — match what `prime.ts` writes today: `title.toLowerCase()`)

    Avoid: changing migrate-v50.ts shape; introducing snapshot listeners; touching Dexie or sync-engine code; writing through `applyEdit` (admin script bypasses the engine — same pattern as migrate-v50.ts).

  <decision>Which thead repair path to lock in for Task 3?</decision>
  <context>
    The `overflow-x-auto` wrapper at `src/components/setlist/grid/SetlistGrid.tsx:1610` was added in v53-02-01 to give the sticky-right Chart cell something to pin against. By spec, that wrapper IS a CSS scroll container, so `<thead>`'s `position: sticky; top: 3.25rem` pins relative to the wrapper's scrollport, not the viewport — which is what's producing the visual stack with the first body row. Plus topbar real height (~60px) ≠ thead `top-[3.25rem]` (52px), violating v51-02-01-DESIGN-CONTRACT.md:18 lockstep rule.

    /ui-ux-pro-max consultation REQUIRED before this checkpoint resolves (skill is BLOCKING per SPECIAL-FLOWS.md; this is the BEFORE invocation point). The two candidate paths:
  </context>
  <options>
    <option id="path-a-sticky-th-td">
      <name>(a) Drop overflow-x-auto; sticky-right via position:sticky on the chart `<th>`/`<td>` directly</name>
      <pros>
        - Smallest change (~10 LOC) — just remove the wrapper div, keep the existing sticky right-0 on chart cells
        - Restores `<thead>` sticky-against-viewport behavior immediately
        - Native HTML table semantics preserved (matters for accessibility tests in `SetlistGrid.a11y.test.tsx`)
      </pros>
      <cons>
        - At very narrow viewports (e.g. iPhone portrait < 480px) the table content can horizontally overflow the page → relies on body scroll instead of an inner scroll container
        - May need a viewport-width breakpoint where chart-col sticky is disabled (or the column hides) on extra-small screens
        - Need to verify sticky-right `<td>` works within `border-collapse: collapse` (Safari quirk historically)
      </cons>
    </option>
    <option id="path-b-display-grid">
      <name>(b) Replace `<table>` with `display: grid` so header + body share one scroll container with full control</name>
      <pros>
        - Decouples sticky behavior from table semantics — full control over sticky offsets and z-index
        - Easier to enforce the topbar/thead lockstep via a single `--editor-topbar-height` CSS custom property
        - Better foundation for any future column-resize / virtualization work
      </pros>
      <cons>
        - Larger change (~150-300 LOC across SetlistGrid + every cell that assumes `<td>` parentage)
        - Risk of breaking jest-axe + role="grid" assertions in `SetlistGrid.a11y.test.tsx` and `SetlistGrid.read.test.tsx` — need explicit ARIA grid roles on every div
        - Higher Harness Fidelity Gate exposure (touches more of the v50-05 substrate); counter could move from 1/3 to 2/3
        - Bigger blast radius vs. a hotfix's "smallest change that works" intent
      </cons>
    </option>
