<objective>
## Goal
Fix the two critical auth regressions identified in Phase 1 audit: (1) session cookie race condition causing middleware redirects before cookie exists, and (2) buggy login popup/redirect cascade with no user feedback on mobile.

## Purpose
Users currently get redirected away from protected pages after fresh login, and mobile users experience a confusing silent popup failure before redirect kicks in. These are the two highest-severity findings from the audit. Fixing them makes "login once, everything works" the reality.

## Output
Modified `src/lib/auth-context.tsx` and `src/app/login/page.tsx` with stable session management and platform-aware login flow.
</objective>

<acceptance_criteria>

## AC-1: Session Cookie Exists Before Post-Login Navigation
```gherkin
Given a user completes Google sign-in (popup or redirect)
When onAuthStateChanged fires and the user is set
Then the __session cookie is confirmed set (or timed out with error) BEFORE loading is set to false
And middleware will find the cookie on the next navigation request
```

## AC-2: Mobile Login Uses Redirect Directly
```gherkin
Given a user is on a mobile browser (iOS Safari, Android Chrome)
When they tap "Sign in with Google"
Then signInWithRedirect is used directly (no popup attempt)
And the button shows "Redirecting to Google..." feedback
```

## AC-3: Desktop Login Uses Popup with Proper Fallback
```gherkin
Given a user is on a desktop browser
When they click "Sign in with Google"
Then signInWithPopup is attempted first
And if popup is blocked, signInWithRedirect fires with "Redirecting..." feedback
And the user is never left in a confusing intermediate state
```

## AC-4: Post-Login Redirect Target Is Consistent
```gherkin
Given a user successfully signs in from the login page
When the session cookie is set and auth loading completes
Then they are redirected to "/setlists" (matching middleware behavior)
And not to "/" which is the public homepage
```

  <action>
    In the onAuthStateChanged handler (line ~90), replace the fire-and-forget session sync with an awaited version:

    1. Create an async helper function `syncSessionCookie(user: User): Promise<boolean>`:
       - Call `user.getIdToken(true)` to get fresh token
       - POST to `/api/auth/session` with the idToken
       - Return true on success, false on failure
       - Add a 5-second timeout via AbortController so it doesn't hang forever
       - Log warnings on failure (non-fatal — client-side auth still works)

    2. In the onAuthStateChanged callback (when currentUser is truthy):
       - Call `await syncSessionCookie(currentUser)` BEFORE the profile subscription sets loading=false
       - The session cookie MUST be set before any navigation can occur
       - Keep the profile subscription starting immediately (don't block on session)
       - But do NOT call `setLoading(false)` until BOTH:
         a. Session cookie sync completes (success or timeout)
         b. Profile subscription fires first callback
       - Use a simple ref or local variable to track both conditions

    3. Preserve existing behavior:
       - `ensureUserProfile()` stays fire-and-forget (non-critical)
       - Profile subscription stays real-time (no change)
       - Claims refresh detection stays the same
       - LocalStorage caching stays the same

    Avoid: Making session failure block the UI forever — the 5s timeout ensures degraded-but-functional state.
    Avoid: Changing the signOut function or any other part of auth-context.
