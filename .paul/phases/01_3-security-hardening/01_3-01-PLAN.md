<objective>
## Goal
Close three independent security gaps identified in FINDINGS.md §P1-x/y/z:
1. Version-controlled Firebase Storage rules with membership gate + CI dry-run.
2. Higher-entropy bridge setup code + dedicated (stricter) rate-limit tier.
3. Rate limits on `/api/nudge-admin` and `/api/scheduling/calendar-feed/[token]`.

## Purpose
Backend hardening before the band is onboarded. Currently Storage rules live only in the Firebase Console (invisible to review), the bridge credential-exchange endpoint leaks service-account keys to anyone with a 6-char code (~30 bits of entropy under the general 60/min limit), and two public endpoints have no rate limit at all. These are pre-onboarding must-fixes per PROJECT.md ("bulletproof before band onboards").

## Output
- `storage.rules` committed and wired into `firebase.json`
- Bridge setup code: 10-char alphanumeric (50+ bits) + `bridgeSetup` tier (5/min) applied
- `checkRateLimit(req, 'api')` applied to nudge-admin + calendar-feed
- One new unit test per new rate-limit tier
- SUMMARY.md in phase dir
</objective>

  <name>Task 1: Commit storage.rules mirroring Firestore membership gate</name>
  <files>sheet-music-app/storage.rules, sheet-music-app/firebase.json</files>
  <action>
    Create `sheet-music-app/storage.rules` with `rules_version = '2';` and a single
    `match /b/{bucket}/o` block.

    Rules to encode (match the Firestore `isMember()` semantics):
      - `match /library/{allPaths=**}`:
          - `allow read: if isMember();`
          - `allow write: if false;` (uploads go through the admin-SDK API route)
      - Catch-all: `match /{allPaths=**}` → `allow read, write: if false;`

    Define `isMember()` in terms of custom claims only (Storage rules cannot call
    Firestore, so the `config/admins` fallback used in firestore.rules does not apply):
      ```
      function isMember() {
        return request.auth != null
            && request.auth.token.role in ['member','musician','band_leader','admin'];
      }
      ```

    Update `sheet-music-app/firebase.json` to add a `storage` key alongside the
    existing `firestore` key:
      ```
      "storage": { "rules": "storage.rules" }
      ```

    Do NOT deploy from this task — deployment is a separate manual step via Vercel/CI.
    Do NOT modify firestore.rules.
    Avoid referencing Firestore from Storage rules (unsupported).
  </action>

        (otherwise document this as the manual verification step in SUMMARY.md)
  </verify>
