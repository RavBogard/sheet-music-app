<objective>
## Goal
Close the MCP **write-side** cross-tenant hole: deny any caller from mutating
another org's setlist/track/song/chart by id, and stamp the caller's org on
every MCP create path — so a Brothers Lazaroff (BL) bearer can never read,
modify, OR create-into CRC's data, and BL-authored docs are tagged BL (not
silently defaulted to crc).

## Purpose
MCP write tools run on the Admin SDK, which **bypasses Firestore rules** — the
v11-01-04 rules do NOT backstop MCP writes. The application layer is the ONLY
control. v11-02-02 closed the read leak; this is its matching write wall and is
the security-critical core of the multi-tenant milestone. Without it, the moment
David's BL bearer is issued (v11-02-04) a BL caller could `update_setlist`/
`delete_setlist`/`update_song` a CRC doc by id, and BL creates would pollute
CRC's listings.

## Output
- `org` threaded through every setlist/clone/song/chart MCP write wrapper (default
  `crc`, MCP route passes explicit `orgFrom(extra)` — mirrors v11-02-02 reads).
- A single cross-tenant guard at `loadEditableSetlist` (covers 8 setlist-write
  tools) + per-tool guards on `delete_setlist`, `clone_setlist`,
  `recompute_setlist_track_count`, `update_song`, `delete_chart`.
- Caller-org stamping on `create_setlist`, `clone_setlist`,
  `clone_setlist_from_template`, and the 3 chart-create tools (`upload_chart`,
  `import_chart_from_drive`, `save_scraped_chart`).
- New `org-scope-writes.emulator.test.ts` proving denial + create-stamping.
- tsc clean; full unit suite green (3272/0 baseline); CRC behavior unchanged.
</objective>

<acceptance_criteria>

## AC-1: Cross-tenant setlist mutation is denied (not-found wall)
```gherkin
Given a CRC setlist S and a caller whose resolved org is "brotherslazaroff"
When the BL caller invokes any of update_setlist / add_track_to_setlist /
  update_track / swap_chart / bulk_update_tracks / bulk_add_tracks /
  reorder_setlist / remove_track / delete_setlist / recompute_setlist_track_count
  targeting S (by id)
Then the call returns the standard `setlist_not_found` rich envelope,
  NO write lands on S or its tracks, and the response does not reveal that S exists
```

## AC-2: Cross-tenant clone source is denied
```gherkin
Given a CRC setlist S and a BL caller
When the BL caller invokes clone_setlist({ sourceSetlistId: S })
Then it returns `setlist_not_found` and no new setlist is created
```

## AC-3: MCP creates stamp the caller's org
```gherkin
Given a BL caller
When the BL caller create_setlist / clone_setlist (of a BL source) /
  clone_setlist_from_template / upload_chart / import_chart_from_drive /
  save_scraped_chart
Then every new doc written (setlists/{id}, its tracks/{id}, library_index/{id},
  songs/{id}) carries orgId = "brotherslazaroff"
And the v11-02-02 read tools surface those docs to the BL caller and hide them
  from a CRC caller
```

## AC-4: Cross-tenant chart/song mutation is denied
```gherkin
Given a CRC chart C (library_index/{C} + songs/{C}, orgId "crc") and a BL caller
When the BL caller invokes update_song({ id: C }) or delete_chart({ fileId: C })
Then it returns `song_not_found` / `chart_not_found` respectively, and neither
  the songs/{C} nor library_index/{C} doc is modified or deleted
```

## AC-5: CRC behavior is unchanged (no regression)
```gherkin
Given a CRC caller (the default org) acting on CRC data
When any write tool runs
Then behavior is byte-for-byte unchanged from pre-plan: own-org writes succeed,
  the full unit suite stays 3272 passed / 0 failed, and no new Firestore index
  is required
```
