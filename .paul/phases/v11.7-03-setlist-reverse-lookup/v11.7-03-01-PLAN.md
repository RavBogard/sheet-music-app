<objective>
## Goal
Ship two P1 Asymmetry-Principle setlist read tools:
**`find_setlists_referencing_chart({ fileId?, songId? })`** — surfaces the
reverse-index walk `delete_chart` already does internally (which LIVE setlists
bond a given chart) — and **`search_setlists({ trackTitle?, leadMusician?,
templateType? })`** — app-side content search over the tenant's setlists.

## Purpose
The write/act side already knows chart→setlist linkage (`delete_chart` refuses
on it via `library-upload.ts:787–846`) but there is NO read tool to ask "which
setlists use chart X?" — the agent brute-forces by enumerating every setlist.
Likewise there is no way to find setlists by a track's title / vocal-lead /
service type. These are the read partners that complete the asymmetry for the
setlist surface, mirroring v11.7-02's `find_user`.

## Output
- `findSetlistsReferencingChart` + `searchSetlists` resolvers in `setlists.ts`.
- Both registered as MCP tools in `index.ts` (after `get_setlist`).
- Emulator-backed tests (real `tracks`/`setlists` docs) covering the reference
  walk, dangling-track exclusion, content filters, and the cross-tenant wall.
</objective>

<acceptance_criteria>

## AC-1: find_setlists_referencing_chart returns live setlists bonding a chart
```gherkin
Given a chart fileId bonded by a track in setlist S (S exists/live) and also by
  a track in setlist D (D deleted → dangling track)
When an authenticated caller calls find_setlists_referencing_chart({ fileId })
Then the result is { ok: true, setlists: [...], count, danglingTracksIgnored }
  AND S is present (id, name, date/eventDate, trackId, trackTitle)
  AND D is NOT present (dangling parent excluded, mirroring delete_chart)
  AND danglingTracksIgnored >= 1
```

## AC-2: find_setlists_referencing_chart supports songId and validates input
```gherkin
Given tracks bonded by songId Y across live setlists
When a caller calls find_setlists_referencing_chart({ songId: Y })
Then matching live setlists are returned

Given a caller calls find_setlists_referencing_chart({}) with neither fileId nor songId
Then it returns the rich invalid_argument envelope (ok:false), not a full dump
```

## AC-3: search_setlists filters by track content and service type (app-side)
```gherkin
Given the caller-org has setlists with various tracks + templateTypes
When a caller calls search_setlists({ trackTitle: "shalom" })
Then only setlists with a track whose title contains "shalom" (case-insensitive)
  are returned, each carrying its matchedTracks

When a caller calls search_setlists({ leadMusician: "randy" })
Then only setlists with a track whose leadMusician matches are returned

When a caller calls search_setlists({ templateType: "friday_night" })
Then only setlists with that templateType are returned (no track read needed)

Given search_setlists({}) with no filter
Then it returns the rich invalid_argument envelope (ok:false)
```

## AC-4: both tools enforce the cross-tenant wall
```gherkin
Given a chart/track + setlist in org broslaz and another in org crc
When a CRC caller (org resolves to 'crc' via orgFrom) calls either tool
Then only CRC setlists are returned; broslaz setlists never leak
  (rowOrg wall, matching list_setlists/get_setlist)
```

## AC-5: gating matches the sibling setlist reads (not over-gated)
```gherkin
Given list_setlists / get_setlist are ungated authenticated reads (public-by-design)
When find_setlists_referencing_chart / search_setlists are registered
Then they are NOT assertEditor-gated — any authenticated MCP caller may call them,
  scoped to their org (consistent with the existing public setlist read surface)
```
