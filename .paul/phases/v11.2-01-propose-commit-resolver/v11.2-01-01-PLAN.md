<objective>
## Goal
Fix BUG-1 (P0): `propose_setlist_changes` returns `404 setlist_not_found` for any setlist owned by a non-CRC tenant (e.g. Brothers Lazaroff), making the server-mandated stage→confirm→commit authoring workflow non-functional for that tenant. Thread the caller's org through `propose_setlist_changes` AND `commit_staged_changes` so both org-scope the target setlist identically to every other by-id setlist write tool.

## Purpose
Daniel authors weekly setlists via Claude + MCP ([[user_mcp_is_primary_author_workflow]]); the W-01 propose→confirm→commit lifecycle is the server's standing safety policy. Right now it is dead for the Brothers Lazaroff tenant — `create_setlist`/`get_setlist`/`update_setlist`/`add_track_to_setlist` all work, but the moment the agent tries to stage a change it 404s. This blocks the entire authoring flow on the 2nd live tenant.

## Output
- `propose-changes.ts`: both exported functions accept and apply an `org` parameter.
- `index.ts`: both tool registrations pass `orgFrom(extra)` (the established caller-org seam).
- A new emulator regression test proving the BL happy path works and the cross-tenant wall holds for both tools.
</objective>

## ROOT CAUSE (verified against deployed origin/master 2026-06-09 — corrects the report's hypothesis)
The stress-test report (BUG-1) suspected an **id-shape divergence** (UUID vs Firestore-auto-id, a divergent `where()` resolver). **That hypothesis is wrong.** Both tools resolve the setlist by direct `.doc(setlistId).get()` via the shared `loadEditableSetlist`/transaction read — UUID ids resolve fine. The actual cause is the **v11-02-03 cross-tenant org wall**:

- `loadEditableSetlist(db, setlistId, uid, org = DEFAULT_ORG_ID)` (`server-tracks-write.ts:132-167`) returns `setlist_not_found` when `rowOrg(data.orgId) !== org`. `org` defaults to `crc`.
- EVERY other by-id write tool passes `orgFrom(extra)` as the 3rd arg in `index.ts` (createSetlist/updateSetlist/addTrackToSetlist/bulkAdd/reorder/remove/delete/updateTrack/swapChart/recompute — all confirmed).
- **`propose_setlist_changes` (`index.ts:1331`) calls `proposeSetlistChanges(uidFrom(extra), args)` with NO `orgFrom(extra)`** → `proposeSetlistChanges(uid, args)` (`propose-changes.ts:141`) calls `loadEditableSetlist(db, args.setlistId, uid)` with NO org → org defaults to `crc` → a Brothers Lazaroff setlist fails `rowOrg !== "crc"` → `setlist_not_found`. Exact match to the deterministic 404 repro.
- **`commit_staged_changes` (`index.ts:1352`)** likewise passes no org; `commitStagedChanges(uid, args)` (`propose-changes.ts:255`) reads `setlists/{stage.setlistId}` directly inside its transaction (`:331`) with **no org check at all** — a latent cross-tenant isolation gap that must be closed in the same fix for symmetry with v11-06-02.

This is why only these two tools broke while all sibling tools worked: they are the two that never got the v11-02-03 org-threading.
</context>
