<objective>
## Goal
Close the P2 leg of the MCP Asymmetry Principle sweep: add two read/resolve-id
tools — `find_setlists_from_template` (which setlists were cloned from a given
template) and `find_contact` (find a saved contact by email/name) — mirroring the
v11.7-02/03 resolver pattern. Backend/MCP only, no UI, **no new Firestore index,
no deploy.**

## Purpose
Every write/act-by-id surface should have a reverse read. `clone_setlist_from_template`
stamps `sourceTemplateId` on each clone (templates.ts:878) but nothing reads it back —
an agent can't answer "which services came from the Randy Shabbat template?".
`create_contact`/`delete_contact` act by id, but the only read is the full
`list_contacts` dump — no lookup by email/name. These two resolvers complete the
asymmetry inventory's cheap P2 items (P4/P5 deferred → v11.8, infra-blocked).

## Output
- `find_setlists_from_template({templateId})` resolver in `setlists.ts` + registered in `index.ts`
- `find_contact({email?, nameContains?})` resolver in `contacts.ts` + registered in `index.ts`
- Emulator cases extending `mcp-setlists-reverse.emulator.test.ts` + `mcp-contacts.emulator.test.ts`
- SUMMARY at `.paul/phases/v11.7-04-reverse-index-sweep/v11.7-04-01-SUMMARY.md`
</objective>

## AC-1: find_setlists_from_template returns the caller-org clones of a template
```gherkin
Given the caller's org has 2 setlists cloned from template T (sourceTemplateId == T)
  and another org has 1 setlist also referencing some template
When the caller invokes find_setlists_from_template({templateId: T})
Then the result lists exactly the caller-org's 2 setlists (id, name, date, eventDate)
  And it returns { ok: true, templateId: T, setlists: [...], count: 2 }
```

## AC-2: find_setlists_from_template enforces the cross-tenant wall
```gherkin
Given a setlist in org B has sourceTemplateId == T
When a caller scoped to org A invokes find_setlists_from_template({templateId: T})
Then org B's setlist is NEVER included (filtered by in-memory rowOrg, no new index)
  And a templateId with zero in-tenant clones returns { ok: true, count: 0, setlists: [] }
```

## AC-3: find_setlists_from_template validates input
```gherkin
Given the caller invokes find_setlists_from_template with no templateId (or blank)
When the resolver runs
Then it returns a richError("invalid_argument", ...) with isError prose, not a throw
```

## AC-4: find_contact looks up saved contacts by email or name, org-scoped + gated
```gherkin
Given the caller's org has a contact { name: "Jane Cohen", email: "jane@x.org" }
When an editor caller invokes find_contact({email: "JANE@X.ORG"})
Then it returns that contact (case-insensitive email match), org-scoped
  And find_contact({nameContains: "cohen"}) returns it (case-insensitive substring)
  And a non-editor caller is refused via assertEditor (isError)
  And another org's contact with the same email is NEVER returned
```

## AC-5: find_contact validates input
```gherkin

When the resolver runs

```

## DECISION (baked — recorded per autonomy directive, no checkpoint)
**Index-free design (NO `(orgId, sourceTemplateId)` composite, NO deploy).** The
v11.7-01 audit spec proposed a composite index, but the deployed v11.7-03 sibling
(`findSetlistsReferencingChart`) established the project's actual idiom: single-field
query + in-memory `rowOrg` cross-tenant wall. A `sourceTemplateId` is a unique template
doc-id and `clone_setlist_from_template` stamps the clone's `orgId` to the cloning org
(templates.ts:878), so a given templateId only ever appears in ONE org's setlists —
cross-tenant collision is impossible and the in-memory wall is the hard safety net.
This removes the only prod-infra touch, keeps the phase byte-consistent with 02/03,
and makes it a STOP-gate-free pure-backend phase. Recorded here + to be restated in SUMMARY.
