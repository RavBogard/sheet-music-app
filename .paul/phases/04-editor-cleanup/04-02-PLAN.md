<objective>
## Goal
Stop network calls from hanging forever. Add default timeout + abort-on-unmount to `apiFetch` and the PDFViewer's direct PDF fetch — the two primitives every API and chart call flows through.

## Purpose
Today a stalled Firebase Storage / Drive / Functions response leaves the app stuck at a spinner with no recourse. Musicians tapping a chart on a flaky venue network get "Loading…" forever and no retry prompt. Tightening the two places all callers funnel through is the highest-leverage, lowest-surface-area fix available.

The adjacent item from the Phase 4 roadmap — "memoize `useSafeFirestoreSync` refs to kill listener churn" — is already satisfied: an audit of the 5 non-test callers (`MusicianPicker`, `use-setlist-performance`, `AccessAuditLog`, `use-monitor-access`, `SoundSystemSection`) confirms every ref is already wrapped in `useMemo`. Skipping that task keeps this plan tight.

## Output
- `apiFetch` grows an opt-out `timeout` option (default 30s) and abort-on-unmount support via caller-supplied `signal`.
- `PDFViewer.fetchPdf` uses an `AbortController` with a 60s timeout and aborts on unmount/URL change.
- Regression tests pin both behaviours.
</objective>

## AC-1: apiFetch default timeout + abort behaviour
```gherkin
Given a call to apiFetch('/api/slow') with no options
When the fetch does not resolve within the default timeout (30s)
Then the returned promise rejects with an error whose name is 'AbortError' (or equivalent DOMException 'AbortError')
 And the in-flight request was aborted (the underlying fetch saw an abort signal)

Given a caller that passes its own signal via `apiFetch('/api/x', { signal: controller.signal })`
When the caller aborts via controller.abort()
Then the request is aborted (caller's signal is respected alongside the internal timeout)

Given a caller that passes `apiFetch('/api/x', { timeout: 0 })`
When the fetch runs indefinitely
Then no timeout abort fires (opt-out is honoured)
 And if the caller also provides no `signal`, the promise stays pending until the network resolves

Given an authenticated call
When apiFetch resolves normally before the timeout
Then the Authorization Bearer header is still attached (existing behaviour preserved)
 And the internal timeout is cleared (no dangling timer firing post-completion)
```

## AC-2: PDFViewer aborts the chart fetch on unmount and on URL change
```gherkin
Given a PDFViewer mounted with url A
When the component unmounts before the fetch resolves
Then the in-flight request is aborted (AbortController.abort was called)
 And setLoading/setError/setSource are NOT called after unmount

Given a PDFViewer mounted with url A
When the url prop changes to url B before url A's fetch resolves
Then url A's fetch is aborted
 And only url B's outcome is reflected in state

Given a PDF fetch that hangs longer than 60 seconds
When the timer elapses
Then the fetch is aborted and the user sees the existing error UI with a message reflecting the timeout
```
