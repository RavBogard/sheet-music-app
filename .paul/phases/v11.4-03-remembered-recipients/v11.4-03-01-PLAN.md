<objective>
## Goal
Let a leader REMEMBER an ad-hoc recipient (a person the system doesn't have an account for —
name + email and/or phone) as a reusable **contact**, on the MCP authoring surface where Daniel
actually works. Ad-hoc *sending* already works today (MCP `publish_setlist` accepts email-only
`recipients[]`); this phase adds the persistence + reuse loop (D8 item 3).

## Purpose
D8 item 3 closes the "I want to email someone who isn't a band member, and not retype them every
week" gap. The browser PublishDialog picker is currently orphaned (mounted nowhere) and Daniel
authors via Claude+MCP, so per the ratified surface decision (2026-06-11) this ships as MCP
contacts — NOT browser UI. A new org-scoped `contacts` address book + `list/create/delete_contact`
tools + surfacing saved contacts in `preview_publish` give the agent everything to say "want me to
save Jane for next time?" and, next week, "you have Jane saved — include her?".

## Output
- `contacts` Firestore collection (org-scoped, leader/admin only) + rules + emulator rules test.
- `Contact` type.
- `src/lib/mcp/tools/contacts.ts`: `listContacts` / `createContact` / `deleteContact` (org-scoped,
  leader-gated), registered as MCP tools.
- `preview_publish` returns `savedContacts[]` (the caller-org address book) so the agent can offer
  them as recipients.
</objective>

<acceptance_criteria>

## AC-1: a leader can create + list + delete org-scoped contacts via MCP
```gherkin
Given an authorized leader (admin/band_leader) on org X
When they call create_contact({name, email?/phone?}) then list_contacts() then delete_contact({id})
Then the contact is stored with orgId=X and createdBy=caller; list_contacts returns only org-X
  contacts; delete removes it; a non-leader caller is refused at the editor gate
```

## AC-2: contacts are tenant-isolated (cross-org wall)
```gherkin
Given a contact saved under org X
When a caller resolved to org Y calls list_contacts (or delete_contact on X's id)
Then they never see X's contact; delete on a cross-org id returns contact_not_found (no existence
  leak); Firestore rules deny a client read/write of another org's contact doc
```

## AC-3: create_contact requires a deliverable handle and is idempotent-friendly
```gherkin
Given create_contact with neither email nor phone (or a blank name)
When it runs
Then it returns a rich validation error (no write); given a name + at least email OR phone it
  succeeds; a duplicate email within the same org returns the existing contact (no dupe row)
```

## AC-4: preview_publish surfaces the org's saved contacts
```gherkin
Given an org with saved contacts
When the leader calls preview_publish for one of that org's setlists
Then the result includes savedContacts[] ({id, name, email, phone}) for that org (and ONLY that
  org) so the agent can offer them as recipients — the recommendation gate is unchanged
```
