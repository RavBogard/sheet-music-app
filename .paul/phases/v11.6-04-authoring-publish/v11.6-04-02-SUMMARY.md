# Phase v11.6-04 Plan 02: WS-21 QR approval claim-lag remedy Summary

**`PUT /api/auth/qr` now approves a shared-iPad sign-in for a band member whose role lives in their Firestore user doc even if the `role` claim hasn't propagated to their ID token — closing the claim-lag false-403 without widening who may approve.**

## Accomplishments

- WS-21 (P2) closed: the QR approval gate resolves an **effective role** = the `role` claim if it's an allowed band role, else the caller's `users/{uid}.role` Firestore field (the established MCP idiom). A recently-approved/role-changed member (incl. `set-role` with `claimsUpdated=false`) can now device-approve before their token refreshes.
- Allowed set held exactly `{musician, band_leader, admin}` — this fixes a false negative, it does not expand access. Non-members still 403.
- Regression coverage: 4 WS-21 cases added to the existing `auth/qr/__tests__/route.test.ts` (18/18 total).

## Decisions Made

| Decision | Rationale | Impact |
|----------|-----------|--------|
| Fallback only when claim absent/not-allowed | Keep AC-3 happy path identical, zero extra latency/reads for the common case | Short-circuit; CRC byte-identical for claim-bearing users |
| Read failure → 403, not 500 | A Firestore blip must not mask the gate or leak an error path | Gate stays closed-by-default on failure |
| No org/tenancy check | QR is a role-gated band surface, deployed handler has none; adding it risks a CRC/BL lockout | Stays in scope; err-public unaffected |
