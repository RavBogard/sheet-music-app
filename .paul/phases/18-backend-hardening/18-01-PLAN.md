<objective>
## Goal
Harden the backend: wrap admin operations in Firestore transactions, add rate limiting to unprotected admin routes, standardize error response shape across all API routes, add CRON_SECRET to env validation, and move the hardcoded super-admin UID from firestore.rules to a Firestore config document.

## Purpose
Data integrity and API consistency. Admin routes currently have non-atomic multi-step operations that can leave inconsistent state on partial failure. Error responses vary in shape across routes. CRON_SECRET is used but not validated at build time.

## Output
- 5 admin routes with rate limiting
- delete-user and set-role with Firestore transaction wrapping
- Consistent `ApiErrorResponse` type enforced by createApiHandler
- CRON_SECRET + SUPER_ADMIN_UID in env.mjs
- firestore.rules using config/admins document instead of hardcoded UID
</objective>

<acceptance_criteria>

## AC-1: Admin operations are atomic
```gherkin
Given a delete-user request where Auth delete succeeds but Firestore delete fails
When the handler executes
Then the Firestore user doc delete and audit log are in the same batch/transaction so they either both succeed or both fail
And the Auth delete is attempted only after Firestore operations succeed
```

## AC-2: set-role operations are transactional
```gherkin
Given a set-role request
When the handler executes
Then the Firestore user doc update, audit log write, and demotion setlist locking happen in a single Firestore transaction
And Auth custom claims update happens only after the transaction succeeds
```

## AC-3: All admin routes are rate-limited
```gherkin
Given any of the 5 admin routes (delete-user, set-role, set-upload-permission, set-sound-engineer, migrations)
When more than 60 requests per minute are made by the same user
Then requests return 429 with standard rate limit headers
```

## AC-4: Consistent error response shape
```gherkin
Given any API route returning an error
When the error is a 400 validation error, 401 auth error, 403 forbidden, or 500 internal error
Then the response body always includes { error: string } at minimum
And optionally { code?: string, details?: unknown }
And no other top-level keys exist in error responses
```

## AC-5: CRON_SECRET validated at build time
```gherkin
Given the env.mjs schema
When the app builds
Then CRON_SECRET is validated as an optional string (present in production)
And cron routes import from env.mjs instead of reading process.env.CRON_SECRET directly
```

## AC-6: Super-admin UID configurable
```gherkin
Given the firestore.rules file
When the isAdmin() function evaluates
Then it checks request.auth.token.role == 'admin' OR the UID exists in the /config/admins Firestore document
And no hardcoded UID string appears in firestore.rules
```

    **delete-user/route.ts:**
    - Reorder operations: Firestore first, then Auth
    - Use a Firestore WriteBatch to atomically delete the user doc AND write the audit log
    - After batch.commit() succeeds, attempt Auth deleteUser (external service, can't be in Firestore transaction)
    - If Auth delete fails, log error but don't roll back Firestore (user doc already deleted is the safe state)
    - Add `import { checkRateLimit } from "@/lib/rate-limit"` and call `checkRateLimit(ctx.req, 'api')` at handler start, returning the response if rate limited

    **set-role/route.ts:**
    - Use `db.runTransaction()` to wrap: (1) read user doc, (2) update user doc with new role, (3) write audit log, (4) query and lock public setlists on demotion
    - After transaction succeeds, update Auth custom claims (external, can't be in Firestore txn)
    - If Auth claims update fails after Firestore transaction, log error (Firestore is source of truth for UI; claims will be stale until next set-role call)
    - Add rate limiting same as delete-user

    **set-upload-permission/route.ts:**
    - Add rate limiting (`checkRateLimit(ctx.req, 'api')`)
    - No transaction needed (single doc update or batch migration already uses WriteBatch)

    **set-sound-engineer/route.ts:**
    - Add rate limiting (`checkRateLimit(ctx.req, 'api')`)
    - No transaction needed (Firestore + Auth claims are separate concerns; if claims fail, it's already logged as warning)

    **migrations/route.ts:**
    - Add rate limiting (`checkRateLimit(ctx.req, 'api')`)

    Avoid: Don't try to include Firebase Auth operations in Firestore transactions — they're different services. Don't change the response shape in this task (Task 2 handles that).
