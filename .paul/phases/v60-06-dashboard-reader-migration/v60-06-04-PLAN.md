<objective>
## Goal
Migrate the two remaining title-aware dashboard read surfaces (`PrepRecommendations` recommendation rows, `UpcomingTimeline.ExpandedTrackList` per-track display) off `setlist.tracks[]` and onto a new bulk Dexie hook `useDexieTracksForSetlists(setlistIds)` that reuses the existing `useLiveQuery` + `getTracksForSetlistClient` 3-branch pattern from `useSetlistPerformance`. The architectural choice is **locked at PLAN time** (Option B — bulk Dexie hook, NOT Option A denormalize titles or Option C per-render fetch) — see Decision Rationale below.

## Purpose
v60-06-03 closed every dashboard reader that only needs fileIds + counts. v60-06-04 closes the readers that need per-track titles (and key, for the timeline) — without polluting the parent setlist doc with denormalized strings that would stale on song rename. With this plan, every dashboard read site for "what's in this setlist" routes through canonical sources: top-level `tracks/{id}` via Dexie for hydrated setlists, embedded array fallback for legacy. This is the last v60-06 plan before the routine surface migrations (v60-06-05 SetlistDrawer, v60-06-06 TemplatesSection, v60-06-07 matrix/route.ts) and the backfill script (v60-06-08).

## Output

- New test file with ≥4 unit tests for the hook (empty input, single setlist, multi-setlist, sort-by-order).
- `useUpcomingPrep` augments `UpcomingSetlistWithPrep` with `localTracks: SetlistTrack[]` (per-setlist via `getTracksForSetlistClient`).

## Decision Rationale (LOCKED at PLAN time — no checkpoint:decision required)

Three options surfaced in v60-06-03 SUMMARY:

| Option | Mechanism | Pros | Cons |
|--------|-----------|------|------|
| **A — Denormalize titles** | New field `setlist.songEntries: { fileId, title, key? }[]` written by reconciler | Single read site (parent doc only); no Dexie subscription per dashboard render | Titles stale on song rename until reconciler converges; large per-doc growth (≤50 entries × ~3 strings ≈ 150 fields); writes-per-rename-fanout (one rename touches every setlist with that song); over-engineering for a low-traffic surface |
| **B — Bulk Dexie hook** *(LOCKED)* | New hook `useDexieTracksForSetlists(setlistIds)` does `useLiveQuery(getDb().tracks.where("setlistId").anyOf(setlistIds).sortBy("order"))`; returns `Map<setlistId, LocalTrack[]>`; consumers map through `getTracksForSetlistClient` per-setlist | Reuses existing canonical 3-branch logic (no new client-tracks code); auto-reactive to song renames (Dexie cross-tab sync); ZERO new Firestore writes / reconciler / types / migrations; aligns precisely with v60-05-01 `useSetlistPerformance` pattern; ~80-100 LOC net | One extra Dexie subscription per dashboard mount (cheap; ≤15 setlists × ≤50 tracks scan); prop-shape change in ExpandedTrackList |
| **C — Per-render fetch** | Each render of PrepRecommendations / ExpandedTrackList calls `getDocs` or `getTracksForSetlistClient` per setlist inside the render path | Smallest immediate diff | Mixes useLiveQuery with iteration scopes badly; re-fetches on every render; no shared subscription across siblings; React-render-model unfriendly |

**Locked decision: Option B.** Rationale:
1. **Pattern symmetry.** `useSetlistPerformance` already uses `useLiveQuery → getTracksForSetlistClient` for single-setlist perf-view tracks. The bulk hook is the same shape, just with `.anyOf([...])` instead of `.equals(id)`. No new architecture introduced — the architecture is already there for one setlist; this generalizes to N.
2. **No new Firestore writes.** Option A multiplies write fanout on every song rename (one rename → up to 15 setlist parent-doc writes). The whole point of v6.0 is single-source-of-truth at `tracks/{id}` — Option A re-introduces denormalized duplication right when v60-07 is about to strip the original embedded duplication.
3. **Auto-reactive titles.** Daniel renames a song in the library → all upcoming-dashboard renderings update on the next paint via Dexie's BroadcastChannel-aware liveQuery. Option A would require either accepting stale titles or building an explicit rename-fanout job.
4. **Bounded scope.** ≤15 upcoming setlists × ≤50 tracks = 750 row scan per dashboard mount. Dexie `where("setlistId").anyOf(...)` is index-backed (setlistId is indexed in the schema; see existing single-setlist hook). One subscription, one re-render on Dexie change.
5. **Reusable.** Future v60-06-05 (SetlistDrawer nav queue) and v60-06-06 (TemplatesSection) will face the same problem. The bulk hook is the canonical answer; this plan invests once.

Documenting per autonomous mandate + v53-02 / v60-06-02 precedent (architectural decisions pre-locked at PLAN, validated at UAT).

    ```ts
    "use client"

    import { useLiveQuery } from "dexie-react-hooks"
    import { getDb } from "@/lib/local/schema"
    import type { LocalTrack } from "@/lib/local/types"

    /**
     * Bulk version of the single-setlist Dexie subscription pattern used by
     * useSetlistPerformance. Returns a Map<setlistId, LocalTrack[]> keyed by
     * setlistId, each value sorted by order. Returns `undefined` while in flight
     * (matches useLiveQuery loading semantics). Short-circuits to an empty Map
     * for empty input — no Dexie call.
     *
     * Caller maps Map entries through getTracksForSetlistClient(localTracks,
     * setlistData) to apply the canonical 3-branch hydrated/legacy fallback.
     *
     * v60-06-04: introduced to power dashboard surfaces that need per-track
     * data (title + key) for multiple setlists without polluting the parent
     * setlist doc with denormalized strings.
     */
    export function useDexieTracksForSetlists(
        setlistIds: string[],
    ): Map<string, LocalTrack[]> | undefined {
        // Stable key for deps: ids may arrive in arbitrary order from upstream,
        // but useLiveQuery deps must be primitive-comparable.
        const key = setlistIds.slice().sort().join(",")

        return useLiveQuery<Map<string, LocalTrack[]> | undefined>(
            async () => {
                if (setlistIds.length === 0) return new Map()
                const rows = await getDb()
                    .tracks
                    .where("setlistId")
                    .anyOf(setlistIds)
                    .sortBy("order")
                const map = new Map<string, LocalTrack[]>()
                for (const t of rows) {
                    const arr = map.get(t.setlistId) ?? []
                    arr.push(t)
                    map.set(t.setlistId, arr)
                }
                return map
            },
            [key],
        )
    }
    ```
