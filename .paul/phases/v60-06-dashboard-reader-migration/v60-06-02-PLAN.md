<objective>
## Goal
Extend the v54-01-03 trackCount reconciler in `SetlistGridHydrator.tsx` with two new denormalized fields — `setlist.songCount` and `setlist.fileIds` — maintained via the same useLiveQuery + debounced applyEdit pattern. Migrate three dashboard surfaces (HeroCard fileIds, NextServiceCard songCount, PublicSetlistListing songCount) to read the denormalized fields with embedded-array fallback for legacy setlists.

## Purpose
v60-06-01 closed the total-count surfaces using the existing `trackCount` field. Filtered counts (song-typed) and fileIds collections require their own denormalized fields. Daniel's clarification — "historical counts don't matter and don't need preserved" — eliminates the drift concern that would have pushed us toward a Cloud Function trigger architecture (option D in design discussion). The client reconciler (option B) is sufficient because every track-mutating handler funnels through `SetlistGridHydrator` (sole-admin-app + single-write-path topology), so the reconciler observes every future write while the user is in the editor.

## Output
- `Setlist` type extended with `songCount?: number` and `fileIds?: string[]` (both optional; legacy setlists don't have them).
- `SetlistGridHydrator.tsx` reconciler block extended with two new useLiveQuery subscriptions + two new lastWritten refs + integrated into existing fanOut seed write.
- Three dashboard reads migrated to denormalized fields with embedded-array fallback.
- Single combined commit per established v60-XX precedent.
- /ui-ux-pro-max gate satisfied (already loaded earlier in session).

**Net production source target:** ~+45 LOC. Slightly over the typical ≤30 budget — justified by tight coupling: shipping reconciler extension without consumer migration leaves denormalized fields unused; shipping consumer migration without reconciler leaves consumers reading undefined-then-fallback for every new write. Bundle preserves single-commit revertibility (one revert restores trackCount-only behavior + embedded reads).
</objective>
