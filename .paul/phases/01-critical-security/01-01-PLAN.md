<task type="auto">
  <name>Task 1: Authenticate session DELETE endpoint</name>
  <files>src/app/api/auth/session/route.ts</files>
  <action>
    The DELETE handler currently clears the __session cookie for ANY request, even unauthenticated ones.
    
    Fix: Before clearing the cookie, verify the request has a valid __session cookie. Import initAdmin + getAuth from firebase-admin and verify the session cookie. If invalid/missing, return 401.
    
    Pattern:
    1. Read the __session cookie from the request
    2. If no cookie present, return 401
    3. Call getAuth().verifySessionCookie(cookie) — if it throws, return 401
    4. Only then clear the cookie and return 200
    
    This prevents an attacker from crafting DELETE requests to disrupt sessions.
    Keep the existing cookie clearing logic; just gate it behind verification.
  </action>
  <verify>npx tsc --noEmit (type-check passes); grep for "verifySessionCookie" in the file</verify>
  <done>AC-1 satisfied: DELETE requires valid session cookie before clearing</done>
</task>

<task type="auto">
  <name>Task 2: Fix timing-attack-vulnerable cron auth on 3 routes</name>
  <files>src/app/api/cron/scheduling-reminder/route.ts, src/app/api/cron/enrich/route.ts, src/app/api/cron/sync/route.ts</files>
  <action>
    Three cron routes use `authHeader !== 'Bearer ${cronSecret}'` (direct string comparison) which is vulnerable to timing attacks. The backup route already has the correct pattern.
    
    For each of the 3 files:
    1. Import `timingSafeEqual` from `crypto` (already available in Node.js)
    2. Add the same `safeCompare` helper used in cron/backup/route.ts:
       ```
       function safeCompare(a: string, b: string): boolean {
           if (a.length !== b.length) return false
           return timingSafeEqual(Buffer.from(a), Buffer.from(b))
       }
       ```
    3. Replace the `authHeader !== 'Bearer ${cronSecret}'` check with:
       `!cronSecret || !authHeader || !safeCompare(authHeader, 'Bearer ${cronSecret}')`
    
    This exactly matches the pattern already used in cron/backup/route.ts.
    Do NOT extract the safeCompare function to a shared util — keep it inline per file to match existing patterns and minimize blast radius.
  </action>
  <verify>grep -rn "timingSafeEqual" src/app/api/cron/ should show all 4 cron routes; grep -rn "authHeader !==" src/app/api/cron/ should return zero matches</verify>
  <done>AC-2 satisfied: All cron routes use constant-time comparison</done>
</task>

<task type="auto">
  <name>Task 3: Add Firestore transactions to scheduling routes</name>
  <files>src/app/api/scheduling/assign/route.ts, src/app/api/scheduling/unassign/route.ts, src/app/api/scheduling/respond/route.ts</files>
  <action>
    **assign/route.ts** — The duplicate-check (query + add) is a race condition. Two concurrent requests can both see "no existing assignment" and both create one.
    
    Fix the per-musician loop: wrap the "check existing + create assignment" in a Firestore transaction.
    - Use `db.runTransaction()` around the existing query + add logic for each musician
    - Inside the transaction: query for existing assignment, if found return early, else create
    - Note: Firestore transactions require all reads before writes. The existing `.where().limit(1).get()` query works in a transaction.
    - Keep notification sends (email/SMS/push) OUTSIDE the transaction — they are fire-and-forget
    - Keep the setlist musicians array sync OUTSIDE the transaction (separate concern)
    
    **unassign/route.ts** — The status update + setlist sync is a TOCTOU race.
    
    Fix: Wrap the assignment fetch + status update in a transaction.
    - `db.runTransaction()` around: read assignment → verify exists → update status to 'cancelled'
    - Keep notifications and setlist sync outside the transaction
    
    **respond/route.ts** — The status check + update is a race condition. Two concurrent respond calls can both see 'pending'.
    
    Fix: Wrap the assignment fetch + status guard + update in a transaction.
    - `db.runTransaction()` around: read assignment → verify musicianUid matches → verify status is 'pending' → update status
    - Keep notification sends outside the transaction
    - Keep the setlist musicians array removal outside the transaction
    
    For all 3 files: If the transaction fails due to contention, Firestore automatically retries up to 5 times. No custom retry logic needed.
  </action>
  <verify>npx tsc --noEmit; grep -rn "runTransaction" src/app/api/scheduling/ should show all 3 files</verify>
  <done>AC-3, AC-4, AC-5 satisfied: All scheduling mutations are transactional</done>
</task>
