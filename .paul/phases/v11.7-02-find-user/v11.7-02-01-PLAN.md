<objective>
## Goal
Ship the MCP **`find_user`** resolver — a tenant-scoped user-directory query
(`{email?, nameContains?, role?, includeProfileless?}`) over the `users`
collection that surfaces EVERY band member, including instrument-less ones —
and add the cheap `includeProfileless` interim flag to `list_musicians`. This
is the v11.7 **Asymmetry Principle** headline and the "David-is-invisible" fix.

## Purpose
Today the only enumerate-people tool is `list_musicians`, which drops anyone
without `musicianProfile.instrument` (`roster.ts:114–126`, `buildMusicianRow`
returns `null`). David Lazaroff (2nd band_leader) has no instrument set, so he
is invisible to the agent — you cannot resolve his uid to assign him, bus him,
or inspect him, and `suggest_musicians`/`suggest_band` silently omit him from
their pool. Write/act-by-id tools (`assign_musician`, `assign_monitor_bus`,
`get_musician_profile`) all take a uid the agent currently has no read path to
discover by name/email. `find_user` closes that asymmetry: every act-by-uid
tool gets a discover-by-attribute partner.

## Output
- `find_user` resolver exported from `roster.ts` + registered in `index.ts`.
- `buildMusicianRow` gains an opt-in `{ allowProfileless }` mode (existing
  callers unchanged → `suggest_*` and the default `list_musicians` keep
  dropping profileless users; no behavior change for them).
- `includeProfileless?: boolean` added to `list_musicians` (interim unblock).
- Emulator-backed tests covering find-by-email/name/role, profileless
  inclusion, the cross-tenant wall, and the `assertEditor` gate.
</objective>

<acceptance_criteria>

## AC-1: find_user surfaces instrument-less users (the David fix)
```gherkin
Given a CRC user "David Lazaroff" with role band_leader, orgIds ['crc'],
  email david@example.com, and NO musicianProfile.instrument
When an editor calls find_user({ nameContains: "lazaroff" })
  (or find_user({ email: "david@example.com" }), or find_user({ role: "band_leader" }))
Then the result is { ok: true, users: [...], count >= 1 }
  AND David's row is present with instrument: null (not dropped)
  AND the row carries uid, displayName, email, role, schedulingTier
```

## AC-2: find_user is tenant-scoped (cross-tenant hard wall)
```gherkin
Given a broslaz-only user (orgIds ['broslaz']) whose name/email would match
When a CRC editor (org resolves to 'crc' via orgFrom) calls find_user with a
  filter that would match that user
Then the broslaz user is NOT in the result (rowOrgIds wall, no leakage)
  AND a user with orgIds ['crc','broslaz'] IS visible to the CRC caller
```

## AC-3: find_user requires editor tier and validates input
```gherkin
Given a caller whose role is plain "musician" (not admin|band_leader)
When they call find_user
Then the result is the rich forbidden_role envelope (assertEditor refusal),
  matching list_musicians' gate

Given an editor calls find_user with NO filter args at all ({})
Then it returns the full org directory (every in-org user, profileless included),
  sorted by displayName — i.e. an empty filter is "list everyone", not an error
```

## AC-4: list_musicians includeProfileless interim
```gherkin
Given an org with one instrument-bearing musician and one profileless user
When an editor calls list_musicians({})            // default
Then only the instrument-bearing musician is returned (UNCHANGED behavior)
When an editor calls list_musicians({ includeProfileless: true })
Then both users are returned, the profileless one with instrument: null
```

## AC-5: suggest_* pool is unchanged
```gherkin
Given the buildMusicianRow refactor adds an optional allowProfileless flag
When suggest_musicians / suggest_band run (they call buildMusicianRow with no flag)
Then they still exclude profileless users (instrument-gated pool intact)
  AND the existing roster emulator suite passes with no regressions
```
