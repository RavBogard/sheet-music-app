<objective>
## Goal
Make the New Setlist wizard date-aware. When the user picks a date, infer the service type via the existing `getServiceContext()` helper, then surface three offers in priority order: **Clone last matching service** (default; primary CTA when a prior match exists), **Choose a template**, **Start from scratch**. Verify that v50-04 sticky song memory propagates through the clone path so a cloned setlist's per-song defaults (key, bpm, vocal lead) reflect the latest sticky values, not the source setlist's stale snapshot.

## Purpose
90% of weekly use is "clone last week's Erev Shabbat and tweak a few songs" (per project memory). Daniel currently picks a date manually and starts from scratch or a template — there's no path that says "clone the most recent matching service". This phase removes the friction from the dominant flow. Unlocks the band-onboarding gate alongside v51-02 by making setlist creation feel like the app understands the cadence (Friday evening + Saturday morning, NOT Sunday — Reform Jewish synagogue).

## Output
- New `findLastMatchingService(serviceType, beforeDate?)` helper in setlist-firebase.ts that returns the most recent setlist of the same inferred service-type (`templateType` field if set, else fallback to inferring from `eventDate` day-of-week)
- Date-aware three-offer mode in CreationWizard.tsx: pre-form offer strip that appears once a date is picked; primary CTA = Clone with the matched setlist's name + date; secondary = Template dropdown (existing); tertiary = Start from scratch (existing default)
- Edge-case handling: no matching prior → Clone option shown disabled with tooltip "No prior {service-name} to clone"
- Sticky-memory verification: cloned setlist's tracks with `songId` pull latest defaults via existing `seedTrackFromSong` path on next mount (NO new propagation needed since v50-04 already handles it; verify with a focused test)
- Telemetry tag (creation_mode: 'clone' | 'template' | 'scratch') captured in toast message + optional Sentry breadcrumb
</objective>
