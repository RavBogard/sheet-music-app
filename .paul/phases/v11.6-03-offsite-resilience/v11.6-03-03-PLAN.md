<objective>
## Goal
Make offline MusicXML rendering work by resolving score bytes **IDB-first**
(`offline-idb getFile(fileId)` → Blob) before any network `fetch`, mirroring
the already-shipped `TextScoreViewer` / `AudioViewer` / `PDFViewer` pattern.
Closes WS-10.

## Purpose
`SmartScoreViewer.tsx:251-253` is the last viewer still doing a bare
`fetch(contentToLoad)` for its source — the exact non-IDB-first path the PDF,
Text, and Audio viewers were rebuilt away from. Offline (or on the WebKit
`fetch(blob:)` race) it falls into the "Failed to load music XML." error
state. MusicXML is the project's strategic preferred chart format
([[project_musicxml_goal]]); when it ships to the band's iPads it must read
off-line on flaky camp wifi like every other chart type. Forward-risk this
weekend (no MusicXML in the 3 Camp Sabra sets) but it's the format we're
steering toward, so the offline path must be airtight before adoption.

## Output
- `SmartScoreViewer` takes a `fileId` prop and self-resolves bytes IDB-first
  (Blob API read, no `fetch(blob:)`), network-fallback to `/api/drive/file/<id>`.
- PDFOverlay's musicxml branch hands `fileId` (not the `fileUrl` blob pipe).
- Test coverage for IDB-hit / network-fallback / compressed-.mxl branches.
- SUMMARY.md.
</objective>

<acceptance_criteria>

## AC-1: Offline MusicXML renders from the IDB cache
```gherkin
Given a MusicXML track whose bytes are cached in offline-idb (fileId present)
  And the device is offline (navigator.onLine === false / network unavailable)
When the musician opens that chart in Perform
Then SmartScoreViewer reads the cached bytes via getFile(fileId) (Blob API,
     no fetch(blob:) round-trip) and OSMD renders the score
  And the "Failed to load music XML." error state is NOT shown
```

## AC-2: Online, uncached MusicXML still renders via the network (parity)
```gherkin
Given a MusicXML track NOT present in offline-idb (getFile → null)
  And the device is online
When the chart is opened
Then SmartScoreViewer fetches /api/drive/file/<fileId> and OSMD renders the
     score, exactly as it does today
```

## AC-3: Both plain MusicXML (.xml/.musicxml) and compressed (.mxl) load
```gherkin
Given resolved bytes that are either UTF-8 MusicXML text (starts with <?xml /
      <score-partwise / <!DOCTYPE) or a compressed .mxl binary
When SmartScoreViewer hands them to osmd.load
Then the existing XML-vs-binary sniff is preserved — XML text is passed as a
     string, binary is passed as a Blob — so both formats render
  And the MusicXML key-signature heal (Q-DETECT-1) still runs unchanged
```

           future IDB change can't strand the viewer (fall through to the

    4. Keep EVERYTHING after `await osmd.load(finalContent)` byte-identical:
       the sleep/yield, fit-zoom computation, the Q-DETECT-1 key-heal +
       setMusicXmlKey, the try/catch error → setError("Failed to load music
