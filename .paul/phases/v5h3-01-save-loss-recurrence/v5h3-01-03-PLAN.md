<objective>
## Goal

Fix the H-SL-7 single-user phantom-VersionMismatch save-loss bug. When the engine writes back a server-stamped `updatedAt` after a successful commit, it must ALSO thread that new `updatedAt` into any PENDING outbox rows for the same `(collection, docId)` so subsequent rapid same-doc edits don't trip the precondition with a stale baseline.

## Purpose

Daniel's mid-session UAT (2026-05-02): *"the bug seems to be related to the 'keep mine' vs 'take theirs' things… EVEN THOUGH I AM THE ONLY ONE USING THE SETLIST. Super terrible bug. this has to get fixed."* Reconciliation modal fires only on `VersionMismatchError` (engine.ts:309-316). Single-user reconciliation = phantom conflict from rapid same-doc edits where Edit 2's `expectedUpdatedAt` was captured at editor-render-time before Edit 1's writeback re-rendered useLiveQuery. The engine's own writeback is correctly bumping `local.updatedAt`, but pending outbox rows still hold the stale baseline. Threading the new updatedAt into pending rows closes the race by construction.

This is a v5h-01-class bug (silent or modal-popup save-loss in single-user editing) that the v5h-01 fix didn't cover because v5h-01 was about missing firestore.rules + listener clobbering, not about expectedUpdatedAt threading. v50-06-02 reconciliation was designed for genuine multi-writer conflicts; firing it for single-user races is a contract violation.

## Output

- `engine.ts` modification: inside the writeback transaction (existing line 259-282), after updating the entity row's updatedAt, ALSO update any pending outbox rows for the same `(collection, docId)` to set `expectedUpdatedAt = result.updatedAt`. Atomic with the existing writeback.
- New regression test in `property-failures.test.ts`: rapid same-doc edits (2-3 sequential applyEdit calls before any pump completes) drain successfully without VersionMismatch firing.
- Suite + tsc + next build verification.
