<objective>
## Goal
Fix data integrity issues in setlist publish notifications (silent fire-and-forget failures) and harden the monitor client throttle pattern to guarantee latest-value delivery.

## Purpose
Setlist publish is the most critical user-facing flow — musicians depend on notifications to know about upcoming services. The monitor mixer is used live during services — dropped fader commands cause audible problems.

## Output
Patched publish route with notification tracking. Hardened monitor throttle with guaranteed latest-value delivery.
</objective>


```gherkin
Given rapid fader changes on the same parameter (e.g., bus_master_0)
When the throttle window expires

```

<task type="auto">
  <name>Task 1: Add notification result tracking to setlist publish</name>
  <files>src/app/api/setlist/publish/route.ts</files>
  <action>
    The publish route currently fires notifications as fire-and-forget with `.catch()` that
    silently swallow errors. The fix is to track results per channel WITHOUT blocking the
    publish operation.

    Changes:
    1. Track in-app notification batch results: wrap each `batch.commit()` in a tracked
       promise instead of fire-and-forget. Collect results.
    2. Track push notification result: await `sendPushToUsers` result (it already returns
       a result object).
    3. Track SMS results: collect per-musician SMS results.
    4. Track audit log: no change needed (already fire-and-forget, non-critical).

    Add a `notificationResults` object to the response:
    ```typescript
    notificationResults: {
        inApp: { sent: number, failed: number },
        push: { sent: number, failed: number },
        email: { sent: number, failed: number },
        sms: { sent: number, failed: number },
    }
    ```

    Implementation approach:
    - Convert fire-and-forget `.catch()` calls to tracked promises
    - Use `Promise.allSettled()` to await all notification promises
    - Extract success/failure counts from settled results
    - Return counts in response (alongside existing fields for backward compat)
    - Keep audit log and cache revalidation as fire-and-forget (non-critical)

    IMPORTANT: Do NOT make notifications blocking. The publish must succeed even if all
    notifications fail. The tracking is informational, not transactional.
  </action>

  <done>AC-1 satisfied: Notification results tracked per-channel in publish response</done>

<task type="auto">
  <name>Task 2: Harden monitor client throttle pattern</name>
  <files>src/lib/firestore-monitor-client.ts</files>
  <action>
    The existing throttle pattern in `sendCommand()` (lines 253-276) is actually close to
    correct — it sends immediately on first call, then coalesces subsequent values. The timer
    fires and sends the latest if it differs from the original.

    However, there's a subtle issue: if the user stops dragging exactly when the throttle window
    expires, and `latest.data !== data` is false (because no new value arrived), the cleanup
    happens correctly. But if `sendCommandImmediate` fails silently (which it does — the catch
    just logs), the latest value is lost.

    Hardening:
    1. In the timer callback, always send the latest value if it differs from what was
       originally sent — regardless of whether the send succeeds. This is already the behavior,
       but add a comment clarifying the design.
    2. Add error tracking: if `sendCommandImmediate` fails, set a `_lastCommandError` timestamp
       so the UI can show a brief "command failed" indicator.
    3. Ensure `disconnect()` sends any pending throttled commands before clearing the map
       (currently it just clears, potentially losing the last fader position).

    In `disconnect()`, before clearing throttleMap:
    ```typescript
    // Flush any pending throttled commands before disconnecting
    for (const [key, throttled] of this.throttleMap) {
        clearTimeout(throttled.timer)
        // Send the latest value — best-effort, don't await
        this.sendCommandImmediate(throttled.data).catch(() => {})
    }
    this.throttleMap.clear()
    ```
  </action>
  <verify>npm test -- --reporter=verbose 2>&1 | tail -5</verify>
  <done>AC-2 satisfied: Monitor throttle flushes pending commands on disconnect, latest value always delivered</done>
</task>
