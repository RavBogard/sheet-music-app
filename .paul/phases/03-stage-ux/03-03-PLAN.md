<objective>
## Goal
Make the "Setlist updated" notification actually fire, and give musicians a live toast when a leader swaps a track during performance.

## Purpose
Two bugs block the stage-UX readiness gate:
1. `notifySetlistUpdated` runs on the client and queries the full `users` collection. Firestore rules only allow that read for `admin` / `band_leader` / self — so the moment a musician-editor (or any edge case) hits the save path, it silently fails. Today the function is fire-and-forget and the failure is invisible; musicians miss "Setlist updated" pings they should be getting.
2. Live swaps (Phase 3 core flow) write straight to `setlists/{id}.tracks` but show no feedback to musicians looking at the performance view on their own device. They only notice a song changed if they happen to glance at the active row.

## Output
- Server-side `/api/setlists/notify-updated` route that broadcasts `setlist_updated` notifications via Admin SDK (no client-side `users` read).
- Client `notifySetlistUpdated` becomes a thin `fetch` wrapper — same signature, no behavior change at call sites.
- Musician-facing "Setlist updated — <old> → <new>" toast on the `/perform/setlist/[id]` page whenever the subscribed tracks array changes for reasons other than the viewer's own swap.
- Regression test coverage for the swap-detection diff logic and the client wrapper.
</objective>

<acceptance_criteria>

## AC-1: Server-side broadcast replaces client users-query
```gherkin
Given a signed-in band_leader or admin edits a setlist and track count changes past the 5-minute throttle
When the save completes
Then the client calls POST /api/setlists/notify-updated with { setlistId, setlistName, trackCount }
 And the server (admin SDK) fetches active member UIDs and writes notification docs for each
 And no client-side query to the users collection is issued from notifySetlistUpdated
 And the call is fire-and-forget — a 4xx/5xx response never blocks or toasts the editor
```

## AC-2: Route is authenticated + rate-limited
```gherkin
Given an unauthenticated request to /api/setlists/notify-updated
When it POSTs a valid body
Then the route returns 401 via the standard createApiHandler auth gate

Given a caller without admin / band_leader role
When it POSTs a valid body
Then the route returns 403 (only privileged roles can fan out broadcast notifications, matching v2.5 P14 decision)

Given >30 requests/min from the same user
When the rate limit trips
Then the route returns 429 using the shared `api` tier
```

## AC-3: Musician sees a toast when a swap lands
```gherkin
Given a musician is viewing /perform/setlist/[id]
 And the leader swaps track N from "Song A" to "Song B"
When the Firestore subscription delivers the new tracks array
Then a toast appears reading 'Setlist updated — "Song A" → "Song B"'
 And the toast auto-dismisses after ~4s
 And the viewer who performed the swap themselves does NOT see the toast (lastOwnSwapRef already tracks this)
 And rapid successive swaps collapse into at most one visible toast at a time (replace, not stack)
```

## AC-4: Diff detection is title-based, not index-based
```gherkin
Given a reorder that moves track 2 to track 0 without changing any titles
When the subscription fires
Then no toast is shown (reorders are not swaps)

Given a track's fileId changes but the title string is identical (re-link to same song)
When the subscription fires
Then no toast is shown

Given a header/liturgical item changes
When the subscription fires
Then no toast is shown (only type === 'song' triggers)
```
