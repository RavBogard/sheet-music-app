<objective>
## Goal
Fix BUG-9 (P1, CONFIRMED cross-tenant leak): `publish_setlist` (and its `preview_publish` wrapper) derive notification recipients from the ENTIRE `users` collection with no org filter, so publishing a Brothers Lazaroff setlist would notify CRC's roster (in-app + push + email + SMS). Scope the recipient set to the setlist's org, matching the v11-05-02 roster pattern, and add the caller-org wall the publish path is missing.

## Purpose
Publish is the load-bearing weekly action AND the only MCP tool that blasts real humans across 4 channels. An unscoped audience on a multi-tenant deployment is a cross-tenant-leak class bug — the exact hard wall the v11.0 isolation work established (err-public holds WITHIN a tenant; hard wall ACROSS tenants). Until this lands, a BL leader cannot safely publish.

## Output
- `setlist-publish.ts`: `publishSetlist` accepts caller `org`; adds a caller-org not-found wall; filters default + uid-override recipients to the setlist's org.
- `preview-publish.ts`: `previewPublish` accepts + forwards `org`.
- `index.ts`: both registrations pass `orgFrom(extra)`.
- Emulator test proving the audience is org-scoped, the caller wall holds, and dryRun never dispatches.
</objective>

## CONFIRMED ROOT CAUSE (verified vs deployed origin/master 2026-06-09 — BUG-9 is REAL, not just suspected)
- `resolveDefaultRecipients` (`setlist-publish.ts:202-250`) runs `db.collection("users").where("role","in",[admin,band_leader,musician]).get()` over the **entire** users collection — **NO org filter**. A BL setlist publish therefore derives the CRC-dominant global roster (the report's `audience.count:17` = CRC roster size).
- Neither `publishSetlist(callerUid, args)` nor `previewPublish(callerUid, args)` accepts a caller org; `index.ts:1188` + `:1371` pass only `uidFrom(extra)`. So publish is entirely org-blind.
- `publishSetlist` also loads the setlist via a direct `.doc().get()` with NO org check (`:339-348`) — the same latent cross-tenant gap closed for `commit_staged_changes` in v11.2-01. A BL caller could publish a CRC setlist (and vice-versa).

## THE FIX PATTERN ALREADY EXISTS (v11-05-02, roster.ts:218-229)
`list_musicians` solved this exact "who belongs to org X" problem: keep the `where("role","in",[...])` query, then filter in-memory:
`if (!rowOrgIds(d.data().orgIds).includes(org)) continue`
`rowOrgIds` (from `@/lib/org/membership`) maps a missing/empty `orgIds` → `['crc']` (CRC-safety default — legacy CRC users with no orgIds stay in CRC's audience with NO backfill). This plan applies the identical predicate to the publish recipient paths. Recipient org = the **setlist's** org (`rowOrg(setlist.orgId)`), i.e. notify the band that owns the setlist.

## STOP-GATE (constraint #6, verify-first phase)
This plan SURFACES the confirmed leak + the proposed filter before any change (done above). APPLY is emulator-only and uses `dryRun`/mocked channels — it NEVER dispatches a real notification. No live publish will be triggered at any point.
