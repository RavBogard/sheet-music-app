<objective>
## Goal
Enhance `createApiHandler` with standardized error responses, improve Firebase Storage error discrimination, and migrate the highest-value non-`createApiHandler` routes to the centralized pattern.

## Purpose
4 different error response shapes and 4 different auth patterns create maintenance burden and inconsistent client-side error handling. Musicians see unhelpful "Internal Server Error" messages or raw JSON when things go wrong. Standardizing reduces bugs and improves user experience.

## Output
- Enhanced `createApiHandler` with standardized error response format
- Firebase Storage functions returning discriminated error results
- Improved error context on 500 responses (route-specific messages)
- CORS domains moved to env var
</objective>

<acceptance_criteria>

## AC-1: Standardized Error Responses
```gherkin
Given any API route returns an error
When the client receives the response
Then the body shape is always { error: string, details?: object }
And the createApiHandler catch block includes the route method and URL in the log
And the response error message is route-specific (not generic "Internal Server Error")
```

## AC-2: Firebase Storage Error Discrimination
```gherkin
Given a Firebase Storage operation fails
When the caller receives the result
Then the result distinguishes between "not_found", "network_error", and "invalid_input"
And callers can make informed retry/fallback decisions
```

## AC-3: CORS Env Var
```gherkin
Given the drive file route needs CORS domains
When the route checks allowed origins
Then it reads from ALLOWED_ORIGINS env var (comma-separated)
And falls back to the current hardcoded domains if env var is not set
```

<task type="auto">
  <name>Task 1: Enhance createApiHandler error format and add Firebase Storage error discrimination</name>
  <files>src/lib/api-wrapper.ts, src/lib/firebase-storage.ts</files>
  <action>
    **api-wrapper.ts:**
    - Update the catch block error response from generic "Internal Server Error" to include route context:
      `{ error: "Internal server error", details: { route: \`\${req.method} \${new URL(req.url).pathname}\` } }`
    - This is the standardized shape all routes should converge on: `{ error: string, details?: object }`
    - Do NOT change the function signature or how handlers are called
    - Do NOT migrate routes in this task — just improve the wrapper itself

    **firebase-storage.ts:**
    - Add a `StorageResult` discriminated union type:
      ```
      type StorageError = { success: false; reason: 'not_found' | 'network' | 'invalid_input'; message: string }
      type StorageSuccess<T> = { success: true; data: T }
      export type StorageResult<T> = StorageSuccess<T> | StorageError
      ```
    - Update `fileExistsInStorage` to return `StorageResult<boolean>` — catch blocks return `{ success: false, reason: 'network', message }` instead of bare `false`
    - Update `downloadFromStorage` to return `StorageResult<{ buffer: Buffer; contentType: string }>` — return reason-specific errors
    - Update `getStorageUrl` to return `StorageResult<string>` — distinguish not_found from network error
    - Keep `uploadToStorage` throwing on error (callers already handle throws)
    - Update all callers of these functions (search for imports) to handle the new return type

    Avoid: Breaking the uploadToStorage API. Changing any function names.
  </action>
  <verify>npx tsc --noEmit && npm test</verify>
  <done>AC-1 partially satisfied (wrapper improved), AC-2 fully satisfied (storage discrimination)</done>
</task>
