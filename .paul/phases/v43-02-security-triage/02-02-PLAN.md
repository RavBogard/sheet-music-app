<objective>
## Goal
Close S03 from the v4.3 audit: tighten the `/api/drive/file/[fileId]` browser-request heuristic by removing the two weakest signals (Referer and Accept-header) and requiring `Sec-Fetch-Site: same-origin|same-site` OR a Bearer token. Log every rejected attempt for observability.

## Purpose
Today `isTrustedBrowserRequest()` accepts any request that presents *either* `Sec-Fetch-Site: same-origin`, OR `Sec-Fetch-Dest != empty`, OR a Referer matching our domain, OR an `Accept` header containing `image/` / `text/html` / `application/pdf`. The last two signals are trivially client-controlled (curl can set any header), so a motivated attacker with a guessed/leaked file ID can bypass the Bearer requirement. Tightening to the `Sec-Fetch-*` signals only is browser-enforced in practice (all modern browsers auto-send these on all fetches; curl/postman do not by default). This is not a cryptographic boundary — a real fix is a signed Firebase session cookie, deferred to Phase 3+ — but it meaningfully narrows casual attacker surface without breaking the current chart-embed/audio/prefetch flow.

## Output
- `isTrustedBrowserRequest` narrowed to `Sec-Fetch-Site: same-origin|same-site` or `Sec-Fetch-Dest` present + not `empty`
- Comment at function site marks it as defense-in-depth, not a boundary, with a link to the follow-up (session cookie)
- Every 401 log includes: `secFetchSite`, `secFetchDest`, `referer`, `userAgent`, `ip`
- Regression tests: forged Referer → 401; `Accept: image/png`-only → 401; `Sec-Fetch-Site: same-origin` → passes; Bearer-only → passes
- tsc clean, suite green, pushed to prod
</objective>

       function hasBrowserFetchMetadata(req: NextRequest): boolean {
           const site = req.headers.get('sec-fetch-site')
           if (site === 'same-origin' || site === 'same-site') return true
           const dest = req.headers.get('sec-fetch-dest')
           if (dest && dest !== 'empty') return true
           return false
       }
