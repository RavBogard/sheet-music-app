<objective>
## Goal
Introduce a single shared `getTracksForSetlist(db, setlistId, setlistData)` helper that performs the hydration-aware read (top-level `tracks/{id}` when `setlistData.hydrated === true`, embedded `setlist.tracks[]` legacy fallback otherwise), reroute the SSR setlist editor page through it, and migrate the publish API route as the first server-side consumer. Helper is covered by emulator-backed tests against real Firestore semantics (rides the v60-03 HFG harness).

## Purpose
v6.0 Wave 3 entry. Every server-side read of "the live track list" must route through one place, or each surface keeps re-inventing the hydration ternary (currently inlined only in `page.tsx`, while `publish` / `print` / `email` routes still read `setlist.tracks` blindly). The publish route is the loudest leaked surface: it stamps `publishedSnapshot` + sends emails + records song usage off the embedded array, which has been stale for any hydrated setlist since v50-05 (resurrection class — same root cause `c9e92a5` fixed for SSR).

Routing through one helper unlocks v60-04-02..04 (per-surface migrations) and v60-07 (writer strip) — those phases stop being "find every server read site" and become "delete the legacy branch from one helper plus drop the embedded-array writer."

## Output
- New module `src/lib/server-tracks.ts` (admin-SDK only; flat-prefix path matches `server-auth.ts` / `server-library.ts` / `server-setlists.ts`).
- `page.tsx` inline `fetchTopLevelTracks` removed; SSR ternary inlined at call-site (page.tsx:155) replaced with single `await getTracksForSetlist(db, id, serialized)` call.
- `publish/route.ts` reads tracks via helper instead of `setlist.tracks || []`.
- Emulator-backed test file proving hydrated vs unhydrated branching on real Firestore.
- Single combined commit per v60-01/02/03 precedent.
</objective>
