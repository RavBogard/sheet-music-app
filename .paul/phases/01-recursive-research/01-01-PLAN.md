<objective>
**Goal:** Produce a ranked (P0 / P1 / P2) findings document covering bugs, missing UI pieces, errors & failure modes, pain points, and inconsistencies across the whole app.

**Purpose:** v4.2's subsequent phases (2–5) already have a hand-walked scope. This phase exists to catch what hand-walking missed. <acceptance_criteria>

**AC-1: Findings document exists and is ranked.**
- Given `sheet-music-app/.paul/phases/01-recursive-research/FINDINGS.md`
- When I read it
- Then every item has a severity (P0 / P1 / P2), a category (bug / missing UI / error / pain point / inconsistency), a `file_path:line_number` citation, and a one-line "why it matters."

**AC-2: Coverage is broad, not just setlists.**
- The findings span at least: dashboard/home, setlist creation + editing, performance view, library, schedule, admin, bridge/monitor, auth, Firestore rules, and API routes.

**AC-3: At least two research waves ran.**
- Wave 1 is parallel + orthogonal (different angles). Wave 2 is informed by Wave 1 — it drills into areas where Wave 1 flagged uncertainty or found early hits.

**AC-4: Roadmap routing decisions are explicit.**
- Every P0 has a proposed resolution: insert as new decimal phase (e.g. 1.1) ahead of Phase 2, or fold into an existing phase (name it).
- Every P1 is routed to one of Phases 2–5.
- P2s are listed but explicitly deferred.

**AC-5: No false alarms.**
- Each item has been sanity-checked — if an item depends on a code path, the path still exists at the cited line. Stale memories from prior conversations don't count.

</acceptance_criteria>

<tasks>

**Task 1 — Wave 1: parallel orthogonal research dispatch.**
- Spawn 4–6 `Explore` subagents in a **single message, parallel** (per CARL rule 3).
- Each agent covers a different angle. Proposed angles (adjust as needed):
  1. **Bugs & race conditions** — Firestore write races, null-crash risks, stale cache, debounce/cleanup bugs, memory leaks in listeners, unresolved promises.
  2. **Missing UI pieces / dead ends** — buttons with no handlers, forms with no submit path, features half-built, referenced-but-missing components, copy that names a feature that doesn't exist.
  3. **Error & failure modes** — silent `.catch(() => {})`, swallowed errors, unhandled rejections, API routes missing error responses, client paths without offline fallback.
  4. **Pain points (tap count / scroll)** — flows over N taps, scroll-locked containers, missing autofocus/enter-key handlers, gesture conflicts, desktop/tablet/phone regressions.
  5. **Inconsistencies** — duplicate components, hardcoded values that should be data-driven, copy drift ("Gig Packet" vs "Print" vs "Share"), two paths to the same action.
  6. **Security / data / rules** — Firestore rules audit, unauthenticated endpoints, missing role checks, rate-limit gaps, cron auth, bridge setup codes. (Lighter pass; Rabbi deploys straight to prod and is the only admin today, so this is lower-priority but worth a quick sweep.)
- Each agent writes a section of findings to `sheet-music-app/.paul/phases/01-recursive-research/WAVE-1-{angle}.md` with `file_path:line` citations and a severity suggestion.
- Agents do NOT write code. Research-only.

**Task 2 — Wave 1 synthesis + gap identification.**
- Read all Wave-1 files.
- Cluster findings into themes; deduplicate cross-agent overlaps.
- Identify **gaps / uncertainties** — findings that look important but need deeper investigation. These feed Wave 2.
- Write `sheet-music-app/.paul/phases/01-recursive-research/WAVE-1-SYNTHESIS.md`.

**Task 3 — Wave 2: targeted drill-downs.**
- Spawn 2–3 `Explore` agents in parallel, each probing one gap from Wave 1.
- Typical Wave 2 targets: reproducibility of a suspected race, feasibility of a fix, full trace of a flow that Wave 1 sampled, sibling-file comparison to confirm a pattern.
- Output: `sheet-music-app/.paul/phases/01-recursive-research/WAVE-2-{topic}.md`.

**Task 4 — Final FINDINGS.md.**
- Merge Wave 1 + Wave 1 synthesis + Wave 2 into a single ranked document at `sheet-music-app/.paul/phases/01-recursive-research/FINDINGS.md`.
- Format:
  - **P0 (blocks band onboarding)** — numbered list, each with: category, `file:line`, what's wrong, why it matters, proposed routing.
  - **P1 (painful but workable)** — same format, routed to an existing Phase 2–5.
  - **P2 (polish / deferred)** — brief list, no routing required.
- End the file with a **"Roadmap delta"** section: which decimal phases to insert (if any), and which existing phase scopes need to expand.

**Task 5 — Roadmap delta review with user (CHECKPOINT: human-verify).**
- Surface the "Roadmap delta" section to Rabbi Daniel.
- He approves / tweaks.
- If approved: update `.paul/ROADMAP.md` with any new decimal phases and expanded scopes. Update `.paul/STATE.md`.
- No code changes in this phase. Execution of findings happens in Phases 2–5.

</tasks>
