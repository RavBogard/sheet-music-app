<objective>
## Goal
Make anon deep links to Storage-backed (`upload-*`) charts render, closing **BUG-5**.
An anon `GET /api/library/file/<id>` for an `upload-*` (Firebase Storage) chart currently
returns `401 missing_bearer`, while the sibling `GET /api/drive/file/<id>` returns `200` for
the same anon caller. New uploads are Storage-backed, so anon deep links to *recent* charts
are dead — a direct violation of the oracle's anon chart-deep-link cell and the err-public
prime directive.

## Purpose
The oracle (`docs/ACCESS-POLICY.md` v0.3) read-surface row "Chart via deep link
(`/perform/[fileId]`, `/api/drive/file/[id]`, `/api/library/file/[id]`)" is **✅ for Anon**
(implied by D1). Prime directive: *err on the side of letting someone see a chart.* A texted
deep link to a new chart must render for a signed-out visitor on a cold device. This is the
P1 headline of v11.3.

## Output
- `/api/library/file/[id]/route.ts` reworked to mirror its working sibling `/api/drive/file/[fileId]`:
  public (`requireAuth:false`), `isTrusted` browser-metadata/bearer gate, `chart` rate-limit
  tier, and serving of `upload-*` / UUID (Storage) ids via the shared `fetchFileById` resolver
  (keeping the legacy `db-*` `digitized_charts` xmlContent path, now also anon-public).
- A route test (`route.test.ts`) proving the anon-access contract.
- (Conditional) a client-routing fix in `parseFileId` only if Task 1 finds a live path that
  sends `upload-*` ids to `/api/library/file`.
</objective>

<acceptance_criteria>

## AC-1: Anon deep link to a Storage-backed (`upload-*`) chart serves bytes
```gherkin
Given an anon visitor (no Firebase session, no MCP bearer) on a cold device
And a real `upload-*` chart id that exists in library_index / Storage
When the browser issues GET /api/library/file/upload-<id> carrying same-origin Sec-Fetch-* metadata
Then the response is 200 with the chart's Content-Type (application/pdf or musicxml) and the chart bytes
And it is NOT 401 missing_bearer
```

## AC-2: Legacy `db-*` MusicXML deep links are also anon-public (err-public regression closed)
```gherkin
Given an anon visitor with browser fetch metadata
And a `db-*` id present in digitized_charts with xmlContent
When the browser issues GET /api/library/file/db-<id>
Then the response is 200 application/vnd.recordare.musicxml+xml with the xml content
And anon no longer receives 401 for legacy charts
```

## AC-3: Bare unauthenticated access (no browser metadata, no bearer) stays gated — parity with the sibling
```gherkin
Given a bare HTTP client with neither a Bearer token nor Sec-Fetch-* metadata
When it requests GET /api/library/file/<id> for an existing id
Then the response is 401 unauthenticated (defense-in-depth identical to /api/drive/file)
And for a non-existent id the response is 404 file_not_found BEFORE the auth gate
```

## AC-4: The fix introduces no new cross-tenant or write exposure
```gherkin
Given the chart-byte serving change
When CRC and broslaz charts are deep-linked by anon
Then both serve (cross-tenant direct deep links are allowed per D3) and NO write/control surface is exposed
And CRC behavior for authed/in-app callers is unchanged
```
