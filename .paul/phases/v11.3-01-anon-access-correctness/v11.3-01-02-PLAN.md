Make anon transpose work in Perform mode, closing **BUG-4**. Per **D-Q2** (ratified
2026-06-10) anon transpose/AI-scan is OPEN with abuse protection. Today an anon visitor
who taps Transpose dead-ends on "Waiting for scan…": `GET /api/library/chord-cache`
(page + meta) and `POST /api/ai/transposer/scan` both return `401 missing_bearer` because
they use `createApiHandler`'s default auth gate. Authed musicians transpose fine.

(D-Q2: OPEN to anon, with abuse rate-limits)" = **✅ Anon**. Transpose is a core Perform
tool (Pass B exercises it). err-public prime directive: don't gate a Perform tool from a
signed-out visitor. The only legitimate constraint is AI-spend abuse — addressed with an
anon-scoped rate-limit on the (currently unlimited) scan endpoint.

<acceptance_criteria>

## AC-1: Anon can read the chord cache
```gherkin
Given an anon visitor (no Firebase token)
When the client GETs /api/library/chord-cache?fileId=…&page=N (or &meta=true)
Then the response is 200 with the cache payload (cached:true/false), NOT 401 missing_bearer
```

## AC-2: Anon can run an AI chord-scan, rate-limited for abuse
```gherkin
Given an anon visitor in Perform transpose
When the client POSTs /api/ai/transposer/scan with a page image
Then the response is 200 with detected chords (not 401)
And repeated anon scans beyond the `ai` tier (20/min per IP) return 429 (abuse protection)
```

## AC-3: Anon scan results persist to the cache (cost control)
```gherkin
Given an anon visitor whose scan returned chords
When the client POSTs /api/library/chord-cache to save them
Then the write succeeds (200) so the NEXT visitor (anon or authed) gets a cache hit and no re-scan
```

## AC-4: Authed transpose is not regressed; write-metadata stays gated
```gherkin
Given a signed-in musician
When they scan/transpose
Then behavior is unchanged — the scan endpoint applies NO rate-limit to authed callers (it was unlimited)
And PATCH (native key / verification) stays role:musician and DELETE stays role:band_leader
```
