<objective>
## Goal
Establish the tenant ("org"/band) domain primitives the entire v11.0 multi-tenant
milestone hangs on, WITHOUT changing any runtime behavior for the existing CRC tenant:
(1) an `Org` type + a static tenant registry (crc + brotherslazaroff, keyed by domain),
(2) an OPTIONAL `orgId` field on the core doc types, and (3) a custom-claims membership
envelope (`orgIds`) + pure server helpers to read/gate it — with a backward-compat default
so every existing CRC user/doc keeps working before any backfill or rules change lands.

## Purpose
This is the spine of v11.0 (give David Lazaroff a separate Brothers Lazaroff instance on
brotherslazaroff.live). Phase v11-02 (org-scoped Firestore rules) and v11-03 (host→tenant
routing) both consume the registry + membership helpers built here; Phase v11-02 (MCP
org-scoping) reads the same membership model from the bearer. Everything must be ADDITIVE
and OPTIONAL so it deploys with zero CRC impact ahead of the backfill (v11-01-03) and rules
(v11-01-02) plans.

## Output
- New `src/lib/org/` module: `types.ts`, `registry.ts`, `membership.ts` + unit tests.
- `orgId?: string` added (optional) to `Setlist`, `SetlistTrack`, `Recording` in models.ts.
- `set-role` route additively writes an `orgIds` claim alongside the existing `role` claim.
</objective>

## AC-1: orgId is an additive, optional field on the core doc types
```gherkin
Given the existing Setlist / SetlistTrack / Recording TypeScript interfaces
When `orgId?: string` is added to each
Then `npx tsc --noEmit` passes with zero new errors
And no existing call site is required to supply orgId (field is optional)
And no runtime behavior changes (purely a type addition)
```

## AC-2: the tenant registry resolves domains to org ids with a safe default
```gherkin
Given the static ORGS registry (crc → centralreform.live, brotherslazaroff → brotherslazaroff.live)
When resolveOrgIdByDomain(host) is called
Then "centralreform.live" (and "www.centralreform.live") resolve to "crc"
And "brotherslazaroff.live" (and "www.brotherslazaroff.live") resolve to "brotherslazaroff"
And any unknown / undefined / localhost host resolves to DEFAULT_ORG_ID ("crc")
And getOrg(orgId) returns the org metadata, isKnownOrg(orgId) is true for both seeded orgs
```

## AC-3: membership helpers read org claims with a CRC-default fallback, and set-role writes them additively
```gherkin
Given a user's decoded custom claims
When getOrgIdsFromClaims(claims) is called and the claims have NO orgIds field
Then it returns ["crc"] (DEFAULT_ORG_ID) — existing CRC users keep access with no migration
When the claims DO carry orgIds: ["brotherslazaroff"]
Then getOrgIdsFromClaims returns ["brotherslazaroff"] and userInOrg(claims, "brotherslazaroff") is true and userInOrg(claims, "crc") is false
Given an admin sets a role via the set-role route with an orgIds payload
Then the route writes orgIds into the custom claims WITHOUT dropping the existing role claim (spreads existing claims first)
And omitting orgIds in the payload leaves any existing orgIds claim untouched
```
