## Goal
Add org-scoped Firestore security rules that enforce CROSS-TENANT WRITE ISOLATION on the
tenant collections (setlists, tracks, songs, recordings) and add a rules block for the new
`orgs` collection — WITHOUT changing any read rule and WITHOUT requiring orgId presence on
writes (which would lock out CRC). Prove with mandatory emulator rules tests, then deploy.

## Purpose
Security-critical close of phase v11-01. Both preconditions are now met (v11-01-02: new
writes stamp orgId; v11-01-03: all existing data stamped orgId="crc"), so the rules can
safely enforce that a write cannot place/move a doc into a tenant the caller doesn't belong
to. This is what makes Brothers Lazaroff data isolation real once BL users get an `orgIds`
claim in v11-02.

## Output
Updated firestore.rules (write-isolation + orgs block), a blocking emulator rules-test suite,
and a prod `firebase deploy --only firestore:rules` — gated behind the tests passing.

## Key design decisions (baked in — engineering calls within ratified scope)
- **WRITE-ISOLATION, NOT write-requirement.** The phase intent ("writes must carry a valid
  orgId") is implemented as isolation, because a hard orgId-required rule would LOCK OUT CRC:
  the in-app CLIENT write paths (src/lib/client-tracks.ts, setlist-firebase.ts,
  sync/track-count-sync.ts) write setlists/tracks via the Web SDK and do NOT stamp orgId
  (v11-01-02 only touched server modules). So the rule allows orgId-absent writes
  (back-compat) but DENIES a write whose orgId names a tenant the caller doesn't belong to,
  and makes orgId immutable across tenants on update.
- **Default-crc in rules.** CRC users carry NO `orgIds` claim (membership.ts contract). The
  rule's caller-orgs helper mirrors getOrgIdsFromClaims: `request.auth.token.orgIds` when it's
  a non-empty list, else `['crc']`. So existing CRC users keep full access with no claim.
- **READS UNCHANGED (err-public).** setlists + tracks stay public-read (`if true`, /perform);
  songs + recordings stay `isMember()`. NO new read gating — cross-tenant filtering of the
  public surfaces is the app's query job (host→orgId, v11-03), not the rules layer. This is
  the err-public invariant + the no-lock-out mandate.
- **orgs/{orgId}:** read `if true` (non-sensitive id/name/domain, needed for host routing),
  write `if false` (seeded via Admin SDK in v11-01-03).
- **library_index stays server-only** (`if false`) — Admin SDK bypasses rules, so orgId
  enforcement there is moot; untouched.
- **Deploy via firebase CLI** (already logged in) — `firebase deploy --only firestore:rules`,
  ONLY after the emulator rules tests pass (the lock-out safety gate).

When they create one with orgId="brotherslazaroff"
Then it SUCCEEDS
Given an existing setlist with orgId="crc"
When a non-admin updates it changing orgId to "brotherslazaroff"
Then the update FAILS (orgId immutable across tenants); an admin CAN override

  <name>Task 1: Add org-scope write-isolation + orgs block to firestore.rules</name>
  <files>firestore.rules</files>
  <action>
    Add a helper near isBandLeader():
      function callerOrgs() {
        return request.auth.token.orgIds is list && request.auth.token.orgIds.size() > 0
          ? request.auth.token.orgIds : ['crc'];
      }
      // A write may set orgId only to a tenant the caller belongs to (admins exempt).
      function orgCreateOk() {
        return !('orgId' in request.resource.data)
          || request.resource.data.orgId in callerOrgs() || isAdmin();
      }
      // orgId is immutable across tenants on update (admins exempt).
      function orgUpdateOk() {
        return !('orgId' in request.resource.data)
          || !('orgId' in resource.data)
          || request.resource.data.orgId == resource.data.orgId || isAdmin();
      }
    Append `&& orgCreateOk()` to the CREATE rule and `&& orgUpdateOk()` to the UPDATE rule of:
    setlists, tracks, songs, recordings. For setlists CREATE (currently `isSignedIn() &&
