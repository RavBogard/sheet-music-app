<objective>
## Goal
Add a per-track recording affordance to the setlist row card: an icon in
`MobileRowCard` that opens a popover (analogous to `ChartBindPopover`) listing the
reference recordings linked to the row's song, playing them inline via `<audio>`,
and — for band-leaders/admins — uploading a new recording for that song. Builds on
the v70-02 recordings data model.

## Purpose
v7.0 adds a NEW data domain — recordings — so the band can attach reference audio
to songs. v70-02 shipped the `recordings/{id}` collection, the `Recording` type,
the `recordings/{id}.{ext}` Storage convention, security rules, and the
`songId + createdAt` composite index. This plan is the first surface that lets a
musician actually *use* recordings: open them from a setlist row and hear the
reference take while building or rehearsing a setlist.

## Output
- `POST /api/recordings/upload` — multipart audio upload → Storage + `recordings/{id}` doc.
- `GET /api/recordings/file/[id]` — admin-side audio serving route (mirrors
  `/api/drive/file/[fileId]`), so playback needs no client Storage SDK and no
  `storage.rules` change.
- `src/lib/recordings/recordings-client.ts` — client lib: subscribe to recordings
  for a songId (newest-first via the v70-02 index), upload a recording, build the
  playback URL.
- `RecordingBindPopover.tsx` + `cells/RecordingCell.tsx` — the per-row UI: a small
  trigger button + a popover with the recordings list, inline `<audio>`, and a
  band-leader/admin upload affordance.
- Wired into `MobileRowCard` (the live render path), with tests.
</objective>

<acceptance_criteria>

## AC-1: Upload a recording for a song
```gherkin
Given a band-leader or admin user and a setlist row whose track has a song bound
When they open the recording popover, choose "upload recording", pick an audio
    file, and submit
Then the file is stored under recordings/{id}.{ext} in Firebase Storage
And a recordings/{id} Firestore doc is written with songId set to the row's song,
    plus title, fileName, mimeType, storagePath, createdAt, createdBy
And a non-privileged (member/musician) user gets no upload affordance, and a
    direct POST to /api/recordings/upload from such a user is rejected (403)
And a non-audio file or an oversized file is rejected (400)
```

## AC-2: List + play recordings for a song inline
```gherkin
Given a setlist row whose song has one or more recordings/{id} docs
When the user opens the recording popover for that row
Then the recordings for that song are listed newest-first
And each list item exposes an inline <audio controls> that plays the recording
    through GET /api/recordings/file/[id]
And a row whose song has no recordings shows an empty state (plus, for privileged
    users, the upload affordance)
```

## AC-3: Recording serving route is auth-gated and streams audio
```gherkin
Given a recordings/{id} doc and its stored audio file
When an authenticated member requests GET /api/recordings/file/[id]
Then the audio bytes are returned with the doc's audio Content-Type, inline
And an unauthenticated request without browser fetch-metadata is rejected
And a request for an unknown id returns 404
```

## AC-4: Recording affordance is wired into the row card without hijacking gestures
```gherkin
Given the setlist row card (MobileRowCard)
When a row whose track has a song bound is rendered
Then it shows a recording affordance icon next to the chart indicator
And activating it opens RecordingBindPopover for that row
And the activating click does NOT toggle the card's tap-to-edit pane
    (stopPropagation — same pattern as v70-03-01's chart link)
And a row with no song bound shows the recording affordance disabled
    (recordings attach to a song, not a bare track)
And the card's long-press context menu and drag-handle behavior are unaffected
```

  <name>Task 1: Recording upload + serving API routes</name>
  <files>src/app/api/recordings/upload/route.ts, src/app/api/recordings/file/[id]/route.ts</files>
  <action>
    Two new App-Router routes. Follow the EXISTING patterns exactly.

    POST /api/recordings/upload  (model on src/app/api/library/upload/route.ts):
      - `createApiHandler` + `checkRateLimit(ctx.req, 'upload')`.
      - Authorize band-leader OR admin only (mirrors the recordings/{id} Firestore
        write rule). Use `ctx.auth.isBandLeader` / `ctx.auth.isAdmin`. Reject others
        with 403.
      - Accept multipart/form-data: `file` (audio), `songId` (REQUIRED — the song to
        link), `title` (optional → defaults to filename sans extension), `notes`
        (optional).
      - Validate: audio mime types only — keep a small ALLOWED map (audio/mpeg,
        audio/mp4, audio/wav, audio/x-wav, audio/ogg, audio/webm, audio/aac) plus an
        extension fallback (mp3, m4a, wav, ogg, webm, aac). Enforce MAX_FILE_SIZE —
        reuse 25MB.
      - `const recordingId = `rec-${crypto.randomUUID()}``.
      - Derive `ext` from mime/filename; compute the Storage path with
        `getRecordingStoragePath(recordingId, ext)` (already exported from
        firebase-storage.ts). Upload via the firebase-admin Storage bucket directly
        — DO NOT reuse `uploadToStorage`/`getStoragePath` (they hardcode the
        `library/` prefix). Add a minimal exported helper
        `uploadRecordingToStorage(recordingId, buffer, mimeType, ext)` to
        `src/lib/firebase-storage.ts` that writes to the recordings path with a sane
        contentType + cacheControl — keep it recordings-specific and small.
      - Write the `recordings/{recordingId}` doc with the v70-02 `Recording` shape:
        { id, songId, title, fileName: file.name, mimeType, storagePath,
        notes? (omit if absent), createdAt, createdBy: ctx.auth.uid }. Use the
        project's FirestoreDate convention for createdAt — check how
        library/upload + models.ts handle timestamps; match it. Omit
        `durationSeconds` (do NOT add a media-parsing dependency just for duration).
      - Return 201 { success, recordingId, title }.

    GET /api/recordings/file/[id]  (model on src/app/api/drive/file/[fileId]/route.ts):
      - `createApiHandler` + `checkRateLimit(ctx.req, 'api')`.
      - Auth: accept Bearer (`ctx.auth`) OR browser fetch-metadata via
        `hasBrowserFetchMetadata(ctx.req)` — the same defense-in-depth drive/file
        uses, because an `<audio>` element cannot attach a Bearer header. Reject
        otherwise.
      - Load `recordings/{id}` doc; 404 if missing. Read its `storagePath`.
      - Download the file from Storage admin-side at that EXACT path and stream it
        back with the doc's `mimeType` as Content-Type and
        `Content-Disposition: inline`. The existing `downloadFromStorage` takes a
        fileId and guesses paths — recordings know their exact `storagePath`, so add
        a minimal `downloadFromStoragePath(path)` helper to firebase-storage.ts (or
        an equivalent direct-path read) and use it.
      - Set a sane audio cacheControl header.

    Avoid: reusing getStoragePath/uploadToStorage (library/ prefix); a media-metadata
    dependency; touching the sync engine; changing storage.rules (the admin SDK
    bypasses Storage rules — that is the entire reason for a serving route).
  </action>
  <verify>`npx next build` compiles both routes clean (App Router export rules — build, not just tsc, per memory feedback_nextjs_route_exports).</verify>
  <done>AC-1 + AC-3 satisfied at the API layer: upload writes Storage + recordings/{id} doc with role gating + validation; serving route streams auth-gated audio and 404s unknown ids.</done>

        — client `onSnapshot` on
        `query(collection(db,'recordings'), where('songId','==',songId), orderBy('createdAt','desc'))`.

        index was shipped for. Map docs to the `Recording` type. Return the
        unsubscribe fn. Include an onSnapshot error handler that calls
        `recoverFromFirestoreShutdown(err)` (exported from `@/lib/firebase`) — the
        project-wide pattern for listener resilience.
      - `uploadRecording(input: { file: File; songId: string; title?: string; notes?: string }): Promise<{ recordingId: string; title: string }>`

        `/api/recordings/file/${recording.id}` (the Task 1 serving route).

    directly. (v70-02 SUMMARY explicitly deferred this lib to v70-03 to avoid
    premature over-building — build only what RecordingBindPopover needs.)

    Avoid: introducing the Firebase client Storage SDK; building a global store;
