<objective>

## Goal
Stop the mobile date picker from silently resetting the user's selection
back to today's date when assigning a date to a setlist on a mobile browser.

## Purpose
Daniel UAT 2026-05-13: "when setting a date on mobile, it keeps accidently
ressetting to the current date instead of the date that i have assigned…"

Mobile UX is iPad-first (band uses iPads on stage; Daniel uses iPad to
build setlists). Date assignment is a core workflow — every setlist needs
a service date. A picker that resets to today is worse than no picker.

## Output
- Working date picker on mobile (iOS Safari, Android Chrome) — assigns
  the user's chosen date and persists it to the setlist doc
- Test coverage for the input handler if mobile-specific logic exists
- `.paul/phases/v60-14-mobile-date-picker/v60-14-01-SUMMARY.md`

  <action>
    1. Find the setlist date picker:
       - `grep -rn "eventDate\|setlistDate\|datepicker" src/components/setlist/`
       - Identify which input element handles date selection
       - Check if there's a mobile-specific code path (touch / virtual-keyboard)
    2. Reproduce locally if possible — open Chrome DevTools → device-mode
       (iPhone) → the editor → set a date → observe whether it resets
    3. Hypotheses to evaluate (in order of likelihood):
       a. **`<input type="date">` with `defaultValue` instead of `value`** —
          re-renders reset the field to defaultValue
       b. **Controlled-input race** — onChange writes to local state, then
          a snapshot re-render flips state back to original (this would be
          related to v60-13-06 hydrator dedup; if that fixes the symptom,
          this whole phase may be moot)
       c. **Date format mismatch** — mobile sends `YYYY-MM-DD` to a parser
          expecting ISO timestamp, parser falls back to today
       d. **Virtual-keyboard close handler** — visualViewport resize
          triggers a state reset
    4. Document the actual root cause in a checkpoint:decision before
       writing code.
  </action>
