<objective>
## Goal
Prove the bulletproof loop holds end-to-end under sustained random failure
injection — random edits, airplane-mode toggles, force-quits, cross-tab edits,
AND the v50-07-03 lazy-hydration cascade — across at least 100 iterations,
with zero data loss and per-doc drain ordering preserved. Then add a thin
Playwright smoke that asserts the lazy-hydration cascade happens
end-to-end on a real React tree (not just at the harness layer).

## Purpose
v50-06 proved the substrate (substrate stabilization + reconciliation modal +
cross-leader visibility + per-doc drain ordering under offline). v50-07-03
extended the substrate to historical data (lazy hydration + perf-view
dual-read). v50-07-04 is the **system-level** confidence test: the union of
all those primitives, exercised by random failure mixes, holds the same
invariants the unit + integration tests prove individually. After this plan,
the only remaining gates before milestone close are operations
(Sentry alarms in v50-07-05) and human (UAT in v50-07-05).

## Output
- New `v50-07-04 kitchen-sink` describe block in `property-failures.test.ts`
  using fast-check to drive ≥100 iterations of mixed-failure scenarios,
  asserting the v50-03 AC-9 no-data-loss invariant + per-doc drain ordering
  + lazy-hydration cascade idempotency.
- New `e2e/lazy-hydration.spec.ts` Playwright smoke covering the
  lazy-hydration end-to-end on the real React tree (scope sized by the
  decision checkpoint — see Task 0).
- New `npm run test:kitchensink` script for ergonomic local re-runs of just
  the kitchen-sink describe block.
- SUMMARY.md documenting iteration counts, invariants asserted, decision
  outcome, and any deviations.

## AC-1: Kitchen-sink fast-check property holds across ≥100 iterations
```gherkin
Given the v50-07-04 kitchen-sink describe block in property-failures.test.ts
And fast-check is configured with numRuns: 100 (CI-tunable via env)
When the property runs a randomized mix of:
  - applyEdit('set'|'update'|'delete') across 'tracks' and 'setlists'
  - airplane-mode toggles via OfflineToggleAdapter (online → offline → online)
  - force-quit simulations (fresh engine.start() with orphaned 'sending' rows)
  - cross-tab edits via TwoWriterAdapter (two engines, distinct lock channels)
  - lazy-hydration injection (a mid-run setlist mount with hydrated:false +
    embedded tracks, exercising the v50-07-03 fan-out cascade)

  - Every committed applyEdit is reflected in the remote store OR an outbox row (v50-03 AC-9)

  - No orphaned 'sending' outbox rows remain after engine.start() recovery
  - Lazy-hydration cascades produce exactly N writes per setlist (one per legacy track + one hydrated:true update) with no duplicates across re-mounts
```

  <files>src/lib/sync/__tests__/property-failures.test.ts, package.json</files>
  <action>
    1. **Add new describe block** at the bottom of property-failures.test.ts:
       `describe('v50-07-04: kitchen-sink under random failure mix', ...)`.

    2. **Define the action grammar** as a fast-check arbitrary that produces
       a sequence of 5–30 ops drawn from:
       - `{kind: 'edit', op: 'set'|'update'|'delete', collection: 'tracks'|'setlists', docId: <fc.constantFrom seed pool>, payload: <small fc.record>}`
       - `{kind: 'toggle-offline'}` (driven by OfflineToggleAdapter; toggles online↔offline)
       - `{kind: 'force-quit'}` (stop engine, leave outbox rows in 'sending'; restart engine — should resume)
       - `{kind: 'cross-tab-edit', tabIdx: 0|1, edit: ...}` (route through second engine sharing remote)
       - `{kind: 'lazy-hydrate', setlistId, embeddedTracks: <fc.array of 1–10 tracks>}` (mounts a fresh hydrator with hydrated:false → fans out via applyEdit; assert per-doc invariants hold across the cascade)

    3. **Reuse helpers** — import `setupTwoWriterRace`, `SharedRemoteSubscriber`,
       `OfflineToggleAdapter`, `SharedRemote`, `FakeClock`, the per-doc drain
       harness model. Do NOT copy-paste forks. If a small new helper is needed
       (e.g., `simulateLazyHydration(engine, setlistId, embeddedTracks)`), add
       it co-located in the same file.

    4. **State the property** as a fast-check `assert(fc.asyncProperty(...))`
       wrapping the action grammar:
       - For each generated sequence, dispatch ops sequentially via the engine
       - On `'force-quit'`: call engine.stop(), spin up a fresh engine bound to
         the same Dexie + adapter, call engine.start() — should drain
         orphaned 'sending' rows
       - On `'toggle-offline'`: flip OfflineToggleAdapter.online; let the
         engine FSM transition into/out of 'offline' state
       - On `'cross-tab-edit'`: dispatch via the second-engine path
       - On `'lazy-hydrate'`: invoke the simulateLazyHydration helper, which
         issues N applyEdit('set','tracks',...) + 1 applyEdit('update','setlists',{hydrated:true})
       - At the end, await `waitForQuiescence` (engine state === 'idle' AND
         outbox empty OR all rows in terminal status)
       - Assert invariants:
         - **AC-9 (no data loss):** every committed applyEdit is in remote OR in outbox
         - **per-doc ordering:** for every docId touched, the last committed payload === remote's current payload
         - **no orphaned 'sending':** post-quiescence, no outbox row in 'sending' status
         - **lazy-hydration idempotency:** if a setlistId was lazy-hydrated, re-mounting (= re-running the lazy-hydrate op) does NOT enqueue duplicate outbox rows for the same tracks

    5. **Configure fast-check** with `{ numRuns: process.env.CI ? 100 : 25 }`
       so local runs stay fast and CI runs hit the user's ≥100 floor. Use a
       deterministic seed via `fc.assert(...)` default (no manual seeds —
       reproducibility comes from the failing-case shrinker output).

    6. **Add `test:kitchensink` script** to package.json:
       `"test:kitchensink": "vitest run --testNamePattern='v50-07-04: kitchen-sink'"`

    Avoid:
    - Real wall-clock timeouts in the harness — use FakeClock pattern from
      v50-03 to keep determinism. fast-check + real timers = nondeterministic
      test failures.
    - Adding new dependencies. fast-check is already in devDeps from v50-03.
    - Forking SharedRemote / OfflineToggleAdapter — extend in place if needed.
    - Creating a new test file. The harness lives in property-failures.test.ts
      by convention (single test bed for all property claims).
    - Calling Firestore for real. Adapters stay in-memory.
  </action>
