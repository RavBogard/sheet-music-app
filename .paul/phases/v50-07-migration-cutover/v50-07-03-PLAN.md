<objective>
## Goal
Implement Option C Hybrid (Lazy Hydration) at the application layer:

1. **Lazy hydration in SetlistGridHydrator** — on first edit-open of a legacy
   setlist, fan out `applyEdit('set', 'tracks', ...)` for every embedded track
   so they land in the top-level `tracks/{id}` collection via the existing
   sync engine. Mark the setlist with `hydrated:true` to prevent repeat
   migrations on subsequent mounts.

2. **Perf-view dual-read in useSetlistPerformance** — when reading tracks for
   the performance view, prefer the live top-level `tracks/{id}` collection
   (subscribed via `onSnapshot` query) and fall back to the legacy embedded
   `setlists/{id}.tracks[]` array when top-level is empty. Both code paths
   stay backward-compatible — Rabbi must be able to view ANY of the 24
   historical setlists either before or after their first hydration.

## Purpose
v50-07-02 cleared the data-layer prerequisites (MARKER_PATH bug + liveState
scrub). v50-07-03 closes the perf-view audit Outcome 2 routing from v50-06-03.

After this plan ships:
- The 24 legacy setlists render correctly in BOTH the editor and perf-view
- Editing a legacy setlist for the first time migrates it forward to the v5.0
  shape automatically (no manual intervention)
- Perf-view stays correct for both legacy-only and hydrated setlists during
  the transition window
- The bulletproof loop (write engine + reconciliation + cross-leader visibility
  from v50-06) extends to historical data without breaking it

## Output

- `LocalSetlist` type gains optional `hydrated?: boolean` field

       d. After all fan-out completes (await Promise.all), call
          `applyEdit({op: 'update', collection: 'setlists', docId: setlistId,
          patch: { hydrated: true }, expectedUpdatedAt: initialSetlist.updatedAt})`
          with `withoutUndo: true`.
       e. Errors during fan-out: catch, warn-log via `logger.warn`. Don't
          throw out of the effect. The setlist stays unhydrated and will retry
          on next mount.

    3. Use a guard ref or local state (`hydrationFanoutStarted`) to ensure
       the lazy-hydration effect only fires ONCE per mount, even if the
       effect's dependencies churn. Use `useRef<boolean>(false)`.

    4. The lazy-hydration effect must run AFTER the existing Dexie priming
       (so the local Dexie tracks are written first; outbox enqueues happen
       on top of correctly-primed local state).

    5. Pass `applyEdit` as a prop with default = real applyEdit (test-seam
       pattern matching existing `startSnapshotListener` prop).

    Avoid:
    - Writing the `hydrated` flag to setlist BEFORE the fan-out completes
      (would mark hydrated even if some tracks fail to enqueue).
    - Calling `applyEdit` outside the React effect lifecycle (e.g., during
      render).
    - Stripping the legacy `setlists/{id}.tracks[]` array (preserve as backup;
      cleanup is a separate future plan).
    - Per-track sequential await — fan-out can be parallel via Promise.all
      (each applyEdit is its own Dexie tx; no shared write contention).

## SCOPE LIMITS
- This plan does NOT delete the legacy `setlists/{id}.tracks[]` arrays after
  hydration. Rollback requires the originals to stay in place.
- This plan does NOT migrate setlists in bulk — only on first edit-open.
  The 24 legacy setlists remain unhydrated until someone opens each one.
- This plan does NOT bootstrap `songs/*`. Sticky-memory features only kick in
  for songs the v5.0 editor explicitly creates from now on.
- This plan does NOT cover the songId problem identified in v50-07-01 audit
  (legacy tracks have no songId). The hydrated tracks just keep their legacy
  `id`/`fileId` shape; if/when the user re-binds a chart, the new `songId`
  comes from ChartBindPopover.
- This plan does NOT add Firestore indexes — `where('setlistId', '==', X)`
  uses the existing single-field auto-index for `setlistId` (or no index if
  the field isn't indexed; the query is small enough that a collection scan
  fits within Firestore's free-tier limits for our 24 setlists × ~27 tracks
  = ≤650 docs total).
- This plan does NOT change the public perf-view URL or routing.
- This plan does NOT touch Playwright (v50-07-04 territory).
- This plan does NOT add Sentry alarms (v50-07-05 territory).

</boundaries>
