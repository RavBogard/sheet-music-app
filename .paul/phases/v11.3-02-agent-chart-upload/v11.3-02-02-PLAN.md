<objective>
## Goal
Add a **chunked inline** chart-upload path (`begin` → `append` × N → `commit`) so a
Cowork/MCP agent can upload a chart's bytes **through MCP tool arguments** in
sub-cap pieces — no direct-to-GCS PUT (which the Cowork sandbox proxy 403s) and
no single oversized base64 arg (which blows the ~25K-token tool-result cap). This
is the secondary fix for David's report (`BUG-cowork-chart-upload-2026-06-10.md`),
covering non-Drive sources that Plan 01's server-side conversion can't reach.

## Purpose
Plan 01 closed the common case (charts already in Drive). The remaining dead-end:
a chart that exists only as a local file in the Cowork sandbox. The signed-URL
path (`request_chart_upload_url` → PUT) is blocked by the sandbox egress proxy;
inline `upload_chart` base64 exceeds the token cap above ~50 KB. Chunking the
bytes through tool args sidesteps both — each chunk stays under the cap, the
server reassembles and runs the SAME `processChartUpload` pipeline. [[user_mcp_is_primary_author_workflow]]

## Output
- Three MCP tools on the existing `upload_sessions` substrate:
  - `begin_chunked_chart_upload` — creates a session (status `awaiting-chunks`), no signed URL.
  - `append_chart_upload_chunk` — server-side writes one base64 chunk to Storage.
  - `commit_chunked_chart_upload` — assembles chunks in order → staged `raw` blob →
    delegates to the existing `finalizeChartUpload` → **org-stamps the result**.
- Emulator regression tests for the full begin→append→commit flow + guards, each
  citing David's report.
</objective>

<acceptance_criteria>

## AC-1: Multi-chunk upload reassembles and imports
```gherkin
Given an upload-allowed caller and a chart file split into N base64 chunks
When the caller calls begin_chunked_chart_upload, then append_chart_upload_chunk
  for chunk indices 0..N-1, then commit_chunked_chart_upload
Then the server concatenates the chunks in index order into the original bytes
And runs them through processChartUpload (dedup / conversion / library_index +
  songs write / library_signals broadcast)
And returns { ok: true, fileId, title, collection }
And the assembled byte content equals the original file exactly
```

## AC-2: Committed chunked chart carries the caller's org
```gherkin
Given a caller whose resolved org is 'broslaz'
When they complete a chunked upload via commit_chunked_chart_upload
Then the resulting library_index/{fileId} row has orgId 'broslaz'
  (commit org-stamps the result, since finalizeChartUpload does not)
```

## AC-3: Session + chunk integrity is enforced
```gherkin
Given an active chunked upload session
When append/commit is called with: a non-owner bearer, a missing chunk index at
  commit, a non-base64 chunk, or a cumulative size over the 25 MB session cap
Then the matching rich-error envelope is returned (upload_session_owner_mismatch /
  missing_chunk / invalid_base64 / size_exceeds_cap)
And no library_index / songs / Storage chart write occurs
```

## AC-4: Auth + dedup contracts match the other upload tools
```gherkin
Given a pending user without canUpload, OR a duplicate-title chart
When they attempt the chunked flow
Then begin/commit refuse with the same envelopes as upload_chart
  (upload permission required; duplicate_detected_in_library 409 with force:true escape)
```
</acceptance_criteria>

  <name>Task 1: Implement begin/append/commit on the upload_sessions substrate</name>
  <files>src/lib/mcp/tools/library-upload-session.ts</files>
  <action>
    Add three exported functions to the EXISTING module (reuse its getBucket,
    stagedPath, UPLOAD_SESSION_TTL_MS, MAX_SESSION_SIZE_BYTES, loadUploader,
    isUploadAllowed, isTrustedLeader, curatedCatalogGate, uploadForbidden,
    rateLimitEnvelope helpers — do NOT re-implement them):

    1. `beginChunkedChartUpload(uid, args: BeginChunkedChartUploadArgs)` where args =
       { title, mimeType, fileName?, collection?, key?, bpm?, tags?, totalChunks? }.
       - Validate title + mimeType non-empty (mirror requestChartUploadUrl).
       - Auth gate (isUploadAllowed→uploadForbidden), curated gate, upload-tier
         rate-limit (bypass trusted leader) — identical to requestChartUploadUrl.
       - Create `upload_sessions/{usess-uuid}` doc with the same metadata fields as
         requestChartUploadUrl PLUS `status: "awaiting-chunks"`, `mode: "chunked"`,
         `totalChunks: args.totalChunks ?? null`, `receivedBytes: 0`,
         `chunkPrefix: "upload-sessions/{sid}/chunk-"`. No signed URL minted.
       - Return { ok:true, uploadSessionId, status:"awaiting-chunks",
         maxChunkBytes: 256*1024, maxTotalBytes: MAX_SESSION_SIZE_BYTES,
         recommendedChunkBytes: 48*1024 } with guidance that ~48 KB binary keeps a
         chunk under the agent's 25K-token result cap.

    2. `appendChartUploadChunk(uid, args: { uploadSessionId, chunkIndex, dataBase64 })`.
       - Load session; verify exists, ownerUid===uid (else
         upload_session_owner_mismatch), status==="awaiting-chunks" (else
         invalid_session_state — finalized/expired/wrong-mode), not expired.
       - Re-check auth + rate-limit (role can change mid-flow, mirror finalize).
       - chunkIndex must be an int >= 0. Validate dataBase64 with the SAME RFC-4648
         regex + %4 length check upload_chart uses (extract a shared
         `decodeBase64Strict(s): Buffer | {error}` helper if clean, else inline).
       - Enforce per-chunk cap (256 KB decoded) and cumulative cap: read session
         receivedBytes, reject with size_exceeds_cap if receivedBytes + chunk >
         MAX_SESSION_SIZE_BYTES.
       - Write the decoded bytes to Storage at
         `{chunkPrefix}{String(chunkIndex).padStart(6,"0")}` (idempotent overwrite
         on retransmit of the same index — recompute receivedBytes from the set of
         present chunk objects rather than blindly adding, OR track a per-index
         byte map on the session doc to stay correct under retransmit).
       - Update session receivedBytes + a receivedIndices set (FieldValue arrayUnion).
       - Return { ok:true, chunkIndex, receivedChunks, receivedBytes }.

    3. `commitChunkedChartUpload(uid, args: { uploadSessionId, force? }, org)`.
       - Load + owner + status + expiry checks (status must be "awaiting-chunks").
       - List chunk objects under chunkPrefix (bucket.getFiles({prefix})). Derive the
         max index; require contiguous 0..max present (else `missing_chunk` rich
         error naming the gap). If totalChunks was set at begin, require count===totalChunks.
       - Download each chunk in ascending index order, concat into one Buffer; enforce
         empty + MAX_SESSION_SIZE_BYTES caps (mirror finalize's checks).
       - Write the assembled buffer to the session's `stagedPath(sid)` ("raw"), then
         delegate to `finalizeChartUpload(uid, { uploadSessionId, force })` — which
         downloads raw, runs processChartUpload, marks the session finalized, and
         maps dedup→409 via the shared uploadFailureEnvelope. Reuse it; do NOT
         duplicate the pipeline.
       - If finalize returns ok: `stampOrg(db, result.fileId, org)` (finalize itself
         does NOT stamp — this is the AC-2 fix), best-effort delete the chunk objects
         (storage lifecycle is the long-tail), and return finalize's result.
       - If finalize errors: return its envelope unchanged (session already marked
         failed by finalize); leave chunks for the lifecycle sweep.

    Import `stampOrg` from "@/lib/mcp/org-context" and the OrgId/DEFAULT_ORG_ID types
    (mirror library-upload.ts). Avoid: a second processChartUpload call; mutating
    finalizeChartUpload's signature or the signed-URL path; unbounded chunk counts
    (cap total decoded at MAX_SESSION_SIZE_BYTES — the per-chunk + cumulative guards
    already bound it).
  </action>
  <verify>`SKIP_ENV_VALIDATION=1 npx tsc --noEmit` clean; read-back confirms commit delegates to finalizeChartUpload + stampOrg after, and reuses the module's existing gate helpers</verify>
  <done>AC-1/AC-2/AC-3 enabled at the tool layer: chunks assemble in order, commit reuses finalize + org-stamps, integrity guards return rich errors.</done>
</task>
