<objective>
## Goal
Make `import_chart_from_drive` accept **Google-native Docs** and **uploaded Office
docs (`.docx`)** by converting them to PDF **server-side** before the existing
`processChartUpload` pipeline runs — so a Cowork/MCP agent can bond a real chart
file by passing a Drive reference, never bytes. Closes the primary dead-end in
David's report (`.paul/research/BUG-cowork-chart-upload-2026-06-10.md`).

## Purpose
Agent authoring is a primary surface (MCP-first pivot). Today a band leader who
has a chart as a Word doc / Google Doc in Drive hits a hard wall: the import path
rejects both, the inline base64 path exceeds the 25K-token tool cap, and the
signed-URL PUT is 403'd by the Cowork sandbox proxy (Anthropic-side, out of
scope). Server-side conversion runs on Vercel with unproxied Drive egress, so it
sidesteps every one of those walls for the common case. [[user_mcp_is_primary_author_workflow]]

## Output
- `DriveClient.fetchAsPdf(fileId, sourceMime)` — a server-side converter that
  yields PDF bytes for Google-native exportable types (via `files.export`, reusing
  the existing `exportDoc`) and for Office types Drive can convert (`.docx` etc.,
  via convert-on-copy: `files.copy` → Google Doc → export PDF → delete temp).
- `importChartFromDrive` routes convertible Drive types through the converter
  instead of rejecting them; genuinely-unconvertible types still get a clear refusal.
- Updated MCP tool description (no longer says "native doc types are rejected").
- Emulator regression tests covering both conversion paths + temp cleanup + the
  still-rejected case. Each cites David's report as the coverage source.
</objective>

<acceptance_criteria>

## AC-1: Google-native Doc imports as PDF
```gherkin
Given a Google Drive file whose mimeType is application/vnd.google-apps.document
And the caller is an upload-allowed user (admin / band_leader / musician / canUpload)
When import_chart_from_drive is called with that driveFileId
Then the server exports the Doc to PDF via files.export (no convert-on-copy)
And the resulting PDF bytes run through processChartUpload
And a library_index row + songs row are written with mimeType application/pdf
And the tool returns { ok: true, fileId, title, collection }
```

## AC-2: Uploaded .docx imports as PDF via convert-on-copy
```gherkin
Given a Google Drive file whose mimeType is
  application/vnd.openxmlformats-officedocument.wordprocessingml.document (a .docx)
When import_chart_from_drive is called with that driveFileId
Then the server copies it to a temporary Google Doc (files.copy with target
  mimeType application/vnd.google-apps.document)
And exports that temp Doc to PDF (files.export)
And deletes the temporary Doc (best-effort; failure to delete must NOT fail the import)
And the PDF bytes run through processChartUpload and write the library row
And the tool returns { ok: true, fileId, ... }
```

## AC-3: Unconvertible native types still get a clear refusal
```gherkin
Given a Drive file whose mimeType is a native Google type Drive cannot export to
  PDF (e.g. application/vnd.google-apps.folder) or an unsupported binary type
When import_chart_from_drive is called
Then the tool returns the existing rich-error envelope (drive_invalid_target for a
  folder; unsupported_drive_native_type / upload_failed otherwise)
And NO partial library_index / songs / Storage write occurs
```

## AC-4: dryRun + binary passthrough unregressed
```gherkin
Given an ordinary binary Drive file (application/pdf, image/png, octet-stream MusicXML)
When import_chart_from_drive is called (with or without dryRun: true)
Then it behaves exactly as before this plan — no conversion attempted,
  bytes fetched via getFile, dryRun still writes nothing
And the predicted-shape dryRun result is byte-identical to current output
```

  <name>Task 1: Add DriveClient.fetchAsPdf — export + convert-on-copy</name>
  <files>src/lib/google-drive.ts</files>
  <action>
    Add a method `fetchAsPdf(fileId: string, sourceMime: string): Promise<ArrayBuffer>`
    that returns PDF bytes for a convertible Drive source. Two branches, both
    wrapped in the existing `withRetry`:

    1. **Google-native exportable** (sourceMime starts with
       `application/vnd.google-apps.` AND is one of document/spreadsheet/presentation/drawing):
       delegate to the EXISTING `this.exportDoc(fileId, 'application/pdf')`. Do NOT
       duplicate the export call — reuse exportDoc.

    2. **Office / other Drive-convertible** (sourceMime is an Office type such as
       the .docx/.xlsx/.pptx openxmlformats mimes, or legacy msword/ms-excel/
       ms-powerpoint): convert-on-copy:
         - `this.drive.files.copy({ fileId, requestBody: { mimeType:
           'application/vnd.google-apps.document' (Docs for word types; Sheets for
           spreadsheet types; Slides for presentation types), name: '<orig>-crc-tmp' },
           fields: 'id', supportsAllDrives: true })` → temp Google file id.
         - `this.exportDoc(tempId, 'application/pdf')` → PDF arraybuffer.
         - In a `finally`, best-effort `this.drive.files.delete({ fileId: tempId,
           supportsAllDrives: true })` wrapped in try/catch — a failed temp-delete
           logs a warning and MUST NOT throw (the import already has its bytes).
       Map the word→Docs / spreadsheet→Sheets / presentation→Slides target via a
       small lookup; default word→Docs.

    Add a sibling pure helper `driveSourceIsConvertible(mime: string): 'export' |
    'copy' | null` (exported) so the wrapper in Task 2 and the tests can classify a
    mime without reaching into Drive: returns 'export' for exportable google-apps
    types, 'copy' for the Office set, null otherwise. `fetchAsPdf` uses it to pick
    the branch and throws an Error if called with a null-classified mime (caller is
    expected to gate first).

    Reuse the module's existing imports + `withRetry`; do NOT add a new auth path
    (the constructor already grants the full `drive` scope, which covers copy+delete).
    Avoid: leaking the temp Doc on the happy path; converting on a mime the helper
    classifies null; a second export implementation.
  </action>
