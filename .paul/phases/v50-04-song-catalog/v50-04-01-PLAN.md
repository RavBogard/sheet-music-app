<objective>
## Goal
Promote `songs/{id}` to first-class with `defaults: { key, lead, bpm }` + rolling `recent[]` history. Bump Dexie to v2. Ship a pure helper module for read-through (seed-on-add) and debounced write-back (propagate-on-edit) — no UI wiring. Ship a one-shot Firestore migration script that backfills `defaults` from most-recent setlist occurrence with dry-run, idempotency, and rollback.

## Purpose
"Sticky song memory" is the second leg of the Bulletproof Editor (v5.0). When a song is added to a setlist, its key/lead/BPM should auto-populate from the last time it was used. When those fields are edited, the change should travel with the song to every future setlist. v50-04 lays the data plumbing; v50-05 (editor cutover) consumes it.

## Output
- Dexie schema v2 with `LocalSong.defaults` + `LocalSong.recent[]`
- `src/lib/songs/defaults.ts` — `seedTrackFromSong()` + `propagateTrackEditToSong()` helpers (debounced, route through `applyEdit('update', 'songs', ...)`)
- `scripts/migrate-v50.ts` — one-shot Firestore backfill with `--dry-run`, `--force`, `--rollback`
- Tests covering schema upgrade, helper debounce/propagation, migration dry-run/apply/rollback/idempotency
- SUMMARY.md at `.paul/phases/v50-04-song-catalog/v50-04-01-SUMMARY.md`
</objective>

  <action>
    Create `src/lib/songs/defaults.ts` exporting two pure functions plus an injectable clock + flush primitive (mirroring the v50-03 FakeClock pattern):

    ```
    export type TrackDefaults = { key?: string; lead?: string; bpm?: number }
    export type SongDefaultsClock = { now: () => number; setTimeout: (fn, ms) => Handle; clearTimeout: (h) => void }

    export async function seedTrackFromSong(songId: string): Promise<TrackDefaults>
    export function propagateTrackEditToSong(
      songId: string,
      patch: TrackDefaults,
      setlistId: string,
      opts?: { clock?: SongDefaultsClock; debounceMs?: number }
    ): void
    export function flushPendingPropagations(): Promise<void>  // test/teardown helper
    export function __resetForTests(): void
    ```

    Behavior:
    - `seedTrackFromSong(id)`: read `songs.get(id)` from Dexie; return `defaults ?? {}`. Never throws — missing row → {}. Coerce to TrackDefaults shape (drop unknown fields).
    - `propagateTrackEditToSong(id, patch, setlistId)`: maintain a module-level `Map<songId, { timer, pendingPatch, pendingSetlistId }>`. On each call merge `patch` into `pendingPatch` (latest-wins per field) and (re)schedule a timer at `debounceMs` (default 1000). When the timer fires:
      1. Read current `songs.get(id)` from Dexie to compute merged `defaults` and updated `recent[]`.
      2. Compute new `defaults = { ...existing.defaults, ...pendingPatch }` (drop undefined keys).
      3. Compute new `recent = [{ ...pendingPatch, setlistId, performedAt: clock.now() }, ...(existing.recent ?? [])].slice(0, 5)`.
      4. Call `applyEdit({ op: 'update', collection: 'songs', docId: id, patch: { defaults, recent } })` from `src/lib/local/write.ts`.
      5. Clear the map entry.
    - Different song IDs MUST NOT share a debounce timer (per-song independent).
    - `flushPendingPropagations()`: await all in-flight applyEdit promises and pending timer firings (used by tests + page-unload paths v50-05 wires up later).

    Use the FakeClock pattern from `src/lib/sync/engine.ts` / v50-03 tests: clock is injectable; default uses real `setTimeout` and `Date.now`.

    Tests in `__tests__/defaults.test.ts` (FakeClock injection, NOT vi.useFakeTimers — race with fake-indexeddb microtask scheduling):
    - seedTrackFromSong returns defaults for an existing song
    - seedTrackFromSong returns {} for a missing song (no throw)
    - Three rapid calls within debounce window → exactly one applyEdit invocation; final patch reflects last-wins merge
    - Two different songIds debounce independently (advance clock, observe both fire)
    - `recent[]` caps at 5 (push 7, assert length 5, FIFO order)
    - Bonus: applyEdit failure is propagated (test-mode exposure via flushPendingPropagations rejection)

    Avoid:
    - Do NOT touch Firestore directly — go through `applyEdit` (the engine handles outbox + Firestore commit)
    - Do NOT use `vi.useFakeTimers` — see v50-03 lesson (fake-indexeddb microtask race)
    - Do NOT add UI imports (this module is consumed by v50-05 editor; must stay pure data-layer)
    - Do NOT depend on the editor's existing `useMusicStore` or `setlist-firebase.ts` (legacy editor surface, deleted in v50-05)
  </action>

  <name>Task 3: Migration script — backfill song defaults from setlist history</name>
  <files>
    scripts/migrate-v50.ts,
    scripts/__tests__/migrate-v50.test.ts
  </files>
  <action>
    Create `scripts/migrate-v50.ts` using Firebase Admin SDK (mirror `scripts/ingest-library.ts` for env loading: `dotenv.config({ path: '.env.local' })` + `initializeApp({ credential: cert({ projectId, clientEmail, privateKey }) })`).

    CLI flags:
    - `--dry-run` → enumerate planned mutations; zero writes
    - `--force` → ignore `system/migrations/v50` marker
    - `--rollback` → restore from `migrations/v50/snapshot/{songId}` and delete marker
    - default → apply

    Apply algorithm (per ARCHITECTURE.md §5.3):
    1. Read `system/migrations/v50` doc. If present and `--force` not set, log "already applied at <timestamp>" and exit 0.
    2. Compute pre-state hash of every `setlists/*` doc (deterministic JSON.stringify with sorted keys, sha256). Store in memory.
    3. Read all `setlists/*` docs ordered by `eventDate || date` ASC. Build a per-song accumulator:
       ```
       Map<songId, Array<{ key?, lead?, bpm?, setlistId, performedAt }>>
       ```
       For each track in each setlist with a `songId` (or `fileId` resolvable to a song doc — match by querying `songs/{songId}` existence; orphan tracks skipped per §5.3), append a record IF the track has at least one of key/leadMusician/bpm set.
    4. For each affected song:
       - Snapshot existing `defaults` + `recent` (or `null` if absent) into `migrations/v50/snapshot/{songId}` doc with `{ defaults, recent, snapshottedAt }`.
       - Compute new `defaults` = most-recent record's fields (later eventDate wins per field; missing field stays undefined).
       - Compute new `recent` = last 5 records (FIFO, latest first).
       - Write `defaults` + `recent` to `songs/{songId}` via `update()`.
       - In `--dry-run` mode: log `[DRY] songs/{id} ← defaults={...}, recent=[N entries]` and skip both snapshot and update.
    5. Write `system/migrations/v50` with `{ appliedAt: FieldValue.serverTimestamp(), affectedSongCount }`.
    6. Compute post-state hash of every `setlists/*` doc. Assert it MATCHES pre-state. On mismatch, throw and exit 1.
    7. Print summary: songs touched, recent entries written, runtime.

    Rollback algorithm (--rollback):
    1. Read all `migrations/v50/snapshot/*` docs.
    2. For each: if snapshot.defaults is null, `update(songs/{id}, { defaults: FieldValue.delete(), recent: FieldValue.delete() })`. Else `update(songs/{id}, { defaults: snapshot.defaults, recent: snapshot.recent ?? FieldValue.delete() })`.
    3. Delete `system/migrations/v50` marker.
    4. Snapshot subcollection is preserved (manual cleanup after 30-day soak per §5.5).

    Dry-run output format must include enough info to spot-check 3 sample songs by hand. Print first 3 affected songs with full planned `defaults` + `recent` before the summary count.

    Test suite `scripts/__tests__/migrate-v50.test.ts` uses an in-memory Firestore mock (the existing pattern in `src/lib/sync/__tests__/` for the engine; or extract a small fake — same shape as the FirestoreAdapter used in v50-03 tests):
    - Seed: 3 setlists referencing songs A/B/C with overlapping tracks, varying eventDates
    - Apply: assert defaults match most-recent occurrence per song; recent[] capped at 5; setlist hashes invariant; marker written
    - Re-apply (no --force): assert exit-early; zero new writes
    - Re-apply with --force: assert idempotent (same result)
    - Rollback: assert defaults/recent revert to pre-state; marker deleted
    - Dry-run: assert zero Firestore writes (mock spies on .update/.set/.delete count == 0); stdout contains "[DRY]" lines
    - Setlist invariance: deliberately mutate a setlist's track key in code under test — assert the hash check FAILS the run (regression guard against accidental setlist writes)

    Avoid:
    - Do NOT touch `setlists/*` docs (read-only). Hash check is the regression guard.
    - Do NOT delete the snapshot subcollection at the end of apply (manual cleanup, separate concern)
    - Do NOT use FieldValue.serverTimestamp() in snapshot reads (snapshot is for restore, not audit)
    - Do NOT assume every track has a songId — orphan readings/prayers are skipped silently
    - Do NOT batch updates across songs in a single WriteBatch larger than 500 ops (Firestore limit). Chunk if affectedSongCount > 400.
  </action>
