<objective>
## Goal
Stand up the local-first sync engine — Dexie IDB store, atomic write API (`applyEdit`), and an outbox-draining state machine with retry, dead-letter, version-mismatch handling, offline awareness, and cross-tab coordination — wired into a Firestore adapter and exposed via a sync-status store. Built **standalone**: the existing editor and write path are not touched. Property-based tests with random failure injection prove no committed write is ever silently lost.

## Purpose
Foundation of v5.0. Every later phase depends on this:
- v50-04 song catalog & sticky memory writes through `applyEdit`
- v50-05 spreadsheet editor cutover replaces the old write path with this engine
- v50-06 concurrent-edit safety reuses the `Conflict` state + reconciliation hooks
- v50-07 migration & cutover relies on the engine being trusted before band traffic returns

The user-stated "bulletproof" goal lives or dies here: the contract is **a committed `applyEdit()` is durable in IDB, and the outbox guarantees it eventually lands in Firestore or surfaces as a Conflict/Failed for the user — never silently dropped**.

## Output
- Dexie 4.x database singleton with 5 stores (`setlists`, `tracks`, `songs`, `outbox`, `meta`) per ARCHITECTURE.md §2.2
- `applyEdit()` write helper that mutates entity rows + enqueues an outbox row in the **same transaction**
- Sync engine implementing the FSM in ARCHITECTURE.md §3 (`Idle | Dirty | Saving | Conflict | Failed | Offline`)
- Retry policy: `[500ms, 1s, 2s, 4s, 8s]`, 5 attempts max, dead-letter on exhaustion
- `BroadcastChannel('crc-sync')` cross-tab lock with 5s heartbeat lease
- Sync-status store (zustand) exposing `useSyncStatus()` for future v50-05 consumers
- Property-based test harness using `fast-check` + `fake-indexeddb` proving no data loss under random failure injection (≥100 runs × 50 ops with seeded reproducibility)
- Old editor and `src/lib/setlist-firebase.ts` / `setlist-flush.ts` / `setlist-draft.ts` paths **untouched**
- SUMMARY at `.paul/phases/v50-03-sync-engine/v50-03-01-SUMMARY.md`
</objective>

<acceptance_criteria>

## AC-1: `applyEdit` is atomic
```gherkin
Given a Dexie database with empty `tracks` and `outbox` stores
When `applyEdit({ op: 'update', collection: 'tracks', docId: 't1', payload: { key: 'G' }, expectedUpdatedAt: 0 })` is called
And the underlying transaction throws after the track mutation but before the outbox insert (failure injected via Dexie hook)
Then the track row reverts to its prior value
And no outbox row is created
And the function rejects with a typed error
```

## AC-2: Successful drain reaches Idle
```gherkin
Given the outbox contains one `pending` row for a `tracks.update`
When the engine drains and the Firestore adapter resolves successfully on first attempt
Then the engine FSM transitions Dirty → Saving → Idle
And the outbox row is removed
And `useSyncStatus()` exposes `{ state: 'idle', queued: 0 }`
```

## AC-3: Backoff + retry honors the schedule
```gherkin
Given an outbox row that the Firestore adapter rejects with a transient 5xx 4 times before succeeding
When the engine drains
Then attempts occur at delays approximating [500ms, 1s, 2s, 4s] from prior failure (±50ms tolerance under fake timers)
And `attempts` is incremented per try and reaches 4 before the success
And the FSM ends in Idle
```

## AC-4: Version-mismatch routes to Conflict, no further retry
```gherkin
Given an outbox row whose `expectedUpdatedAt` does not match the server document
When the Firestore adapter rejects with a `VersionMismatchError`
Then the FSM transitions Saving → Conflict
And the row stays in the outbox with status `failed` and `lastError` populated
And no automatic retry occurs until `engine.resolveConflict(row, 'mine' | 'theirs')` is invoked
```

## AC-5: Auth failure (401/403) is one-shot retry only
```gherkin
Given an outbox row whose first send rejects with 401
When the engine drains
Then exactly one Firebase token-refresh attempt is made
And on second-attempt failure, the row is marked `failed` immediately (no further retries)
And the FSM transitions to Failed
```

## AC-6: Retry budget exhaustion → Failed (dead-letter)
```gherkin
Given an outbox row that the Firestore adapter rejects 5 times with transient 5xx
When the engine drains through the full retry budget
Then `attempts` reaches 5
And the row's `status` becomes `failed`
And the row remains in IDB indefinitely (no auto-purge)
And the FSM transitions to Failed
And `useSyncStatus()` reports `{ state: 'failed', queued: 1 }`
```

## AC-7: Offline detection + auto-resume
```gherkin
Given the engine is in Idle and `navigator.onLine` becomes false
When `applyEdit()` is called
Then the FSM enters Offline (not Saving)
And the outbox row stays `pending` with `scheduledFor = now`
When `navigator.onLine` becomes true
Then the engine re-enters its prior state and drains within 250ms
```

## AC-8: Cross-tab single-leader drain
```gherkin
Given two engine instances (simulated separate tabs) sharing the same `BroadcastChannel('crc-sync')`
When both observe pending rows
Then exactly one acquires the lock and drains
And the other engine reports `{ state: 'idle' }` (lock-deferred drainer is silent, not erroring)
When the lock-holder calls `engine.shutdown()` (simulating tab close)
Then the survivor takes over within 5500ms (5s heartbeat lease + jitter) and resumes draining
```

## AC-9: Property-based — no committed write is silently lost
```gherkin
Given a `fast-check` property running 100 iterations of 50 random operations
And operations are drawn from { applyEdit-update, applyEdit-set, applyEdit-delete, network-timeout, 401, 412, 5xx, force-quit }
When each iteration completes
Then every successfully-committed `applyEdit()` is reflected in EXACTLY ONE of:
  - the Firestore mock having received the corresponding write, OR
  - the outbox containing a row whose `status ∈ { 'pending', 'failed' }` and whose payload matches the local state delta
And no committed write is observed in neither location
```

    **Create `state-machine.ts`:**
    - Export a pure-functional FSM: `type SyncState = 'idle' | 'dirty' | 'saving' | 'conflict' | 'failed' | 'offline'`
    - `type SyncEvent = { type: 'EDIT_COMMITTED' } | { type: 'DRAIN_STARTED' } | { type: 'DRAIN_OK' } | { type: 'DRAIN_VERSION_MISMATCH' } | { type: 'DRAIN_RETRY_PENDING' } | { type: 'DRAIN_BUDGET_EXHAUSTED' } | { type: 'DRAIN_AUTH_FAILED' } | { type: 'NETWORK_OFFLINE' } | { type: 'NETWORK_ONLINE' } | { type: 'CONFLICT_RESOLVED' }`
    - Export `transition(state: SyncState, event: SyncEvent): SyncState` implementing ARCHITECTURE.md §3.2 transitions
    - Multi-state precedence (per §3.1): if outbox has both `failed` AND `pending` rows, Failed beats Dirty. Encode this rule in a separate `deriveStateFromOutbox(rows: OutboxRow[]): SyncState` helper used at engine startup and after each drain pass.
    - Pure functions only — no side effects, no Dexie calls, no timers. This is the testable core.

    **Create `firestore-adapter.ts`:**
    - Export `async function commitOutboxRow(row: OutboxRow): Promise<void>`
    - Throw typed errors for the engine to discriminate:
      - `VersionMismatchError` (412 / Firestore precondition failure)
      - `AuthError` (401/403 / Firebase auth/credential errors)
      - `NetworkError` (TypeError fetch / `navigator.onLine === false`)
      - `TransientError` (5xx / Firestore unavailable / deadline exceeded)
      - All other → re-throw raw (treated as transient by the engine)
    - For `'set'` / `'update'`: route through Firestore Web SDK using existing `firebase.ts` client; `'update'` uses `runTransaction` with `expectedUpdatedAt` precondition (mirror the pattern in `setlist-firebase.ts`); `'delete'` uses `deleteDoc`
    - Allow dependency-injection of the underlying Firestore client (the engine wires it from the existing client; the test harness injects a mock that fails on demand). Accept a `FirestoreLike` interface as constructor param of an adapter factory; default export uses the real client.
    - Avoid: using Firebase Admin SDK here (this is the *client* sync engine); coupling to `setlist-firebase.ts` (no shared imports — keep the new engine standalone so v50-05 can delete the old path cleanly)

    **Create `cross-tab-lock.ts`:**
    - Export `class CrossTabLock` with constructor `(channelName: string, leaseMs = 5000)`
    - Methods: `tryAcquire(): boolean`, `release(): void`, `isHolder(): boolean`, `shutdown(): void`, `onLost(cb: () => void)`, `onAvailable(cb: () => void)`
    - Implementation: `BroadcastChannel('crc-sync')`; lock-acquire posts `{ type: 'lock-acquired', tabId, ts }`; heartbeat every `leaseMs / 2` (2.5s); other tabs maintain a `lastHeartbeat` per-tab; if no heartbeat in `leaseMs`, lock is reapable
    - Use `crypto.randomUUID()` for `tabId`
    - Tie-break on simultaneous acquire: lower `tabId` wins (deterministic, no timestamp races)
    - Avoid: `localStorage` (event timing differs per browser); `Web Locks API` (Safari support too uneven for the iPad floor we set in §1.1)

    **Create `engine.ts`:**
    - Export `class SyncEngine` with constructor `({ db, adapter, lock, clock, onStateChange })`
      - `clock` is a `{ now(): number; setTimeout(fn, ms): handle; clearTimeout(handle) }` object — production passes the host globals; tests pass a fake-clock impl so AC-3 can assert delays without real time passing
    - Methods: `start()`, `shutdown()`, `pump()` (one drain pass), `resolveConflict(localId, choice)`
    - Drain loop:
      1. `tryAcquire()` cross-tab lock; if not holder, listen for `onAvailable` and exit
      2. Query `db.outbox.where('[status+scheduledFor]').between(['pending', -Infinity], ['pending', clock.now()])`
      3. For each row in scheduledFor ASC order:
         - mark `status = 'sending'`
         - call `adapter.commitOutboxRow(row)`
         - on success → delete the row
         - on `VersionMismatchError` → `status = 'failed'`, FSM `DRAIN_VERSION_MISMATCH`, abort drain
         - on `AuthError` → if `attempts === 0`, attempt token refresh via `getIdToken(true)`, requeue with `attempts = 1` and immediate `scheduledFor`; if `attempts >= 1`, `status = 'failed'`, FSM `DRAIN_AUTH_FAILED`
         - on `NetworkError` → FSM `NETWORK_OFFLINE`, requeue with backoff, exit drain (resume on `online` event)
         - on `TransientError` (or unknown) → `attempts += 1`; if `attempts < 5`, set `scheduledFor = now + backoff[attempts - 1]` (`[500, 1000, 2000, 4000, 8000]` ms); if `attempts === 5`, `status = 'failed'`, FSM `DRAIN_BUDGET_EXHAUSTED`
    - Schedule the next drain pass via `clock.setTimeout` for the soonest `pending` row's `scheduledFor`, capped at 30s as a sentinel
    - Listen on `window.addEventListener('online' / 'offline')` (guarded for SSR) to fire `NETWORK_ONLINE` / `NETWORK_OFFLINE` events into the FSM
    - On `start()`, call `deriveStateFromOutbox()` to recover after a force-quit
    - On `shutdown()`, release the lock, clear timers, and unsubscribe network listeners

    **Create `store.ts`:**
    - Export a zustand store: `useSyncStatus = create<{ state: SyncState; queued: number; lastError?: string; lastSyncAt?: number }>(...)`
    - Export `wireSyncEngineToStore(engine: SyncEngine): () => void` — subscribes `onStateChange` and updates the store; returns unsubscribe
    - Avoid: rendering anything; consuming this store from any existing editor component (v50-05 territory)

    **Tests:**
    - `state-machine.test.ts`: exhaustive transition table — every (state, event) pair asserted; `deriveStateFromOutbox` covers the precedence rule
    - `cross-tab-lock.test.ts`: jsdom + a `BroadcastChannel` polyfill (use `worker_threads` MessageChannel-backed shim or `broadcast-channel` if cleaner); two `CrossTabLock` instances on the same channel — only one acquires; on holder shutdown, survivor acquires within `leaseMs + tolerance`; tie-break test
    - `engine.test.ts`: covers AC-2 (success on first try), AC-3 (backoff schedule under fake clock — use `vi.useFakeTimers()` and the clock injection), AC-4 (version-mismatch → Conflict; no retry), AC-5 (one-shot auth refresh), AC-6 (5-attempt budget → Failed), AC-7 (offline → Offline → resume on online), AC-8 (cross-tab handoff)
    - `vi.useFakeTimers` is required for AC-3, AC-7; reuse the project pattern (per CLAUDE.md memory: `vi.useFakeTimers` for time-dependent tests)
    - Mock `firestore-adapter` per-test; the property test in Task 3 uses the real adapter shape against a more elaborate harness
