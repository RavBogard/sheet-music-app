### Scope (final plan in v50-06)

Three concerns in one plan, vertical-slice preferred:

1. **Cross-leader live-edit visibility** — Firestore `onSnapshot` listeners on `tracks/*` + `setlists/*` so when leader-tab edits land server-side, follower tabs/devices update via local Dexie writes (replaces the deleted v50-02 live-swap UI; this was always the v50-02 deletion's "implicit replacement"). **Closes the v50-06-02 'theirs' gap** (today, after a 'theirs' resolution the loser's local row stays stale until reload — onSnapshot listener will rehydrate automatically). Pattern likely: snapshot listener writes `db[collection].put` directly (mirror SetlistGridHydrator's idempotent direct-put approach), with a "skip if our own outbox has a pending row for this docId" guard.

The v50-03 property-failures harness already proves the engine side; v50-06-03 adds the realistic sequence (offline → 5 edits → reconnect → drain → all 5 land in order).

### Edge cases to surface in PLAN

- **'theirs' resolution + onSnapshot listener interaction** — after user picks 'theirs' in the modal, the engine deletes the failed outbox row. v50-06-02 currently leaves the local row stale; once the onSnapshot listener exists, it will see the remote doc (winner's state) and `db.put` it locally → loser's local row finally reflects remote. Verify this flow lands cleanly (no race between resolveConflict's outbox.delete and the listener's local-write).
- **'mine' resolution + onSnapshot during drain** — after re-queue, engine drains → server commit succeeds → server timestamp updates → onSnapshot fires with our own write echoing back. Engine writeback (v50-06-01) already updates the local row's updatedAt inside the same Dexie tx as outbox-row delete, so the listener's `db.put` of the same data should be a no-op. But verify: the listener's "skip if outbox has pending row" guard must NOT skip just because our drain JUST completed — there's a millisecond window where outbox is empty + listener fires + nothing pending.
