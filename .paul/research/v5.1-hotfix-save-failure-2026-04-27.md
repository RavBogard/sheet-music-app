## Executive Summary (TL;DR)

**The two strongest signals converge on the same architectural blind spot:**

1. v51-03 introduced a **new direct-Firestore-write path** (`cloneSetlist` in `src/lib/setlist-firebase.ts`) that bypasses the engine outbox AND has **no Sentry instrumentation** (gap from the v50-07-05 capture map). If this path fails, users see a generic "Failed to create setlist" toast and nothing else — invisible to monitoring.
2. The **existing `createSetlist` path** has the same Sentry gap (long-standing, not a v5.1 regression — but newly exposed because v51-03 made the wizard the dominant create flow).
3. The **edit path** (cell-commit → engine → outbox → Firestore) IS instrumented at all 6 v50-07-05 capture sites. If editing is failing in production, Sentry should have data. **First production datum to check: Sentry events filtered to `tag.feature:dead-letter` since `b023ea0` deploy.**

**Boundary verification:** No commits between `62298c0` (v5h-01 close) and `b023ea0` (v5.1 close) touched `firestore.rules`, `src/lib/sync/`, `src/lib/local/`, `src/lib/auth-context.tsx`, or `src/types/models.ts`. The single commit (`6c5040a` v51-03 close) touches `src/lib/setlist-firebase.ts` (`cloneSetlist`) and `src/hooks/use-creation-wizard.ts` (templateType write) — and is exactly where the new architectural risk lives.

**Critical caveat (echoing v5h-01-04 lesson #5):** Daniel said "creating AND editing" both fail. The synthesis above explains create well; for edit, the engine-side path SHOULD have left a Sentry trail. If Sentry shows zero events, the symptom may be misattributed — Daniel might be seeing wizard "Create new" toast errors after every clone attempt and conflating them with edit failures. Production capture decides.

## Pass 2: Hypothesis Ranking from v5.1 Diff (Subagent 1 findings, condensed)

### H1 (HIGH): cloneSetlist direct-write fails silently for some field-shape or auth condition
**Mechanism:** `src/lib/setlist-firebase.ts:288–322` `cloneSetlist` calls `addDoc(...)` directly, bypassing the engine + outbox + Sentry. Catch block at line 322 throws to caller → `useCreationWizard.ts:250` → `toast.error('Failed to create setlist')`. No Sentry breadcrumb anywhere on this path.

The fields written: `name`, `date`, `eventDate`, `tracks`, `trackCount`, `ownerId`, `ownerName`, `musicians` (`source.musicians || []`), `assignedUids` (`(source.musicians || []).map(m => m.uid).filter(Boolean)`), `rabbi` (conditional), `clonedFrom`. Some sources may have `musicians` as `undefined` from older legacy data → empty arrays; `clonedFrom` is brand-new in production write history; `assignedUids` may be empty.

**Refutation datum:** Pass 1.2 outbox check (cloneSetlist failures don't appear in outbox — bypass — so the absence of a `setlists` create row in outbox + presence of "Failed to create setlist" toast = this hypothesis confirmed). Also Pass 1.3 Network tab status code on the addDoc XHR.

### H2 (MEDIUM): findLastMatchingService rejection leaves wizard mode='clone' but cloneSource=null
**Mechanism:** `src/hooks/use-creation-wizard.ts:114–143` async lookup. If `service.findLastMatchingService(inferred, eventDate)` rejects (offline, permission, race), the catch sets `cloneSource=null` but if `setMode('clone')` already fired before resolution, mode persists. canCreate guards correctly (line 81: `mode === 'clone' ? !!cloneSource : !!name.trim()`), so this would surface as "Create button stays disabled" not "save failed", BUT a user who clicks rapidly might trigger `create()` between mode-flip and source-clear and hit the early return at use-creation-wizard.ts ~line 168 (`if (!cloneSource || !eventDate) return`), producing no toast and silent failure (not "Failed" toast).

**Refutation datum:** Pass 1.3 console logs — would show "cancelled" warnings or unmount-during-pending state errors.

### H3 (MEDIUM): SetlistGridHydrator lazy-hydration re-fires + outbox-pending guard race
**Mechanism:** v50-07-03's `fanoutStartedRef` guard prevents most re-fires, but React StrictMode or fast nav-back-nav-forward could double-mount. If a cell-edit's outbox row exists but the new `setlistOutboxRow` query reads stale before re-priming, hydrator could overwrite local with server-stale data → next sync writes a stale value → engine drain rejects with VersionMismatch → user sees toast.

**Refutation datum:** Pass 1.2 outbox check for duplicate rows on same docId, or rows with status='failed' and lastError containing "VersionMismatch" or expectedUpdatedAt mismatch.

### H4 (LOW-MEDIUM): Engine drain transient failure produces dead-letter for unrelated edit
**Mechanism:** `src/lib/sync/engine.ts:198–297` per-doc drain ordering. Transient network failure → row goes 'failed' after 5 attempts → dead-letter → captureSyncFailure fires (this IS instrumented). Sentry should see it.

**Refutation datum:** Pass 1.1 Sentry query — if dead-letter events exist post-`b023ea0` deploy with `tag.collection:setlists` or `tag.collection:tracks`, this is the cause.

### H5 (LOW): templateType field handling in clone produces an invalid Firestore index lookup downstream
**Mechanism:** Speculative; defensive code at `src/lib/setlist-firebase.ts:101–113` handles undefined templateType correctly. Likely a non-issue.

## Pass 3: Prior-Art Recurrence Check (Subagent 2 findings, condensed)

### 3a — Firestore rules current state ✓ no recurrence
- `match /tracks/{trackId}` block intact at `firestore.rules:115–120` (the v5h-01-02 fix).
- `match /songs/{songId}` block intact at `firestore.rules:128–133`.
- `match /setlists/{setlistId}` uses an OPEN allow pattern (lines 83–104) — no field whitelist, no `affectedKeys().hasOnly()`. v51-03's new `clonedFrom` + `assignedUids` fields are permitted implicitly. **Rules are NOT the blocker.**

### 3b — Sentry capture wiring ✓ intact; ⚠ gap on direct-write paths
All 6 v50-07-05 sites verified:
- SetlistGridHydrator lazy-hydration catch ✓
- engine.ts dead-letter (line 377 before DRAIN_BUDGET_EXHAUSTED dispatch) ✓
- 4 snapshot-listener swallow sites ✓

**GAP:** `cloneSetlist` (line 316) and `createSetlist` (line ~104) in setlist-firebase.ts throw directly to caller without Sentry capture. The wizard's catch shows toast.error but emits no telemetry. **This is exactly where v51-03's new code lives.** Recommendation (for the eventual fix plan): add `captureSyncFailure({ feature: 'write-atomicity', ... })` wrappers matching v50-07-05 pattern.

### 3c — Outbox drain ordering ✓ correctly preserved post-v5.1
Per-doc drain ordering invariant (engine.ts:208–212, blockedDocs set) is intact. Failed rows block subsequent rows for same docId. No code changes since v50-06-03.

### 3d — Auth claim / token refresh ✓ no recurrence pathway
v5.1 did NOT deploy new firestore.rules → no stale-claim window like v5h-01-02. Auth-context's `getIdToken(true)` force-refresh path at `src/lib/auth-context.tsx:128` is unchanged. Edge case: if Daniel's session is from this morning (pre-v5.1) and he hasn't navigated away, the token is whatever was minted then — but rules haven't changed, so the token's claims should still satisfy them.
