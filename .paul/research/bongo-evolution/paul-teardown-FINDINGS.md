## §1 — PAUL Architecture Overview (the model in ~1 page)

PAUL is a **single-thread, file-as-brain, loop-driven** development workflow. One human ("visionary/product owner") + one Claude ("the builder") — `references/quality-principles.md:4-11` is explicit: "No teams, stakeholders, ceremonies, coordination overhead… Estimate effort in context usage, not human dev time." It has **no coordination layer at all** — that is precisely the net-new thing bongo adds.

**Three-layer separation (the headline structural insight, mirrored almost exactly in gsd):**

1. **Thin command** (`commands/paul/*.md`, ~30-40 lines each, fits one screen) — frontmatter (`name`, `description`, `argument-hint`, `allowed-tools`) + a two-slot `@`-include: `<execution_context>` lazy-loads the static procedure (`@~/.claude/paul-framework/workflows/X.md`), `<context>` loads dynamic project state (`@.paul/STATE.md` + `$ARGUMENTS`), and `<process>` is one line: "Follow workflow: @…X.md". `rules/commands.md:31-37`: "Commands are thin wrappers… A command should fit on one screen. If it grows beyond that, logic belongs in a workflow."
2. **Workflow procedure** (`paul-framework/workflows/*.md`, 200-700 lines) — the real step-by-step logic as `<step name=...>` blocks. No frontmatter (`rules/workflows.md:10-12`); required `<purpose>`/`<when_to_use>`/`<process>`.
3. **Templates + references** (`paul-framework/templates/` = the `.paul/` state schema; `paul-framework/references/` = cross-cutting design philosophy lazy-loaded when relevant).

**State lives in `.paul/`** (the only persistence substrate — there is no CLI; **everything is hand-edited markdown by the LLM**): `PROJECT.md` (business context + requirements + Key Decisions table), `ROADMAP.md` (milestones→phases→plan checklists), `STATE.md` (**the single source of truth** — a <100-line living digest), `paul.json` (machine-readable satellite manifest mirroring STATE.md), `config.md` (toggles: `enterprise_plan_audit`, `sonarqube`, `preferences.parallel_agents`), `SPECIAL-FLOWS.md` (skill registry), `phases/{NN}-{name}/` (per-plan `CONTEXT`/`DISCOVERY`/`PLAN`/`SUMMARY`/`UAT`/`FIX`/`AUDIT` docs), `debug/<slug>.md`, `codebase/*.md` (7 brownfield maps), `ISSUES.md`, `MILESTONES.md`, `research/`.

**The loop is the spine: `PLAN → APPLY → UNIFY`** (`references/loop-phases.md`). Every unit of work completes the full loop; "Never leave a loop incomplete… This is what makes PAUL a system, not random loops" (`workflows/unify-phase.md:251`). Pre-loop feeders (`map-codebase`, `research`, `discover`, `discuss`, `assumptions`) build context artifacts but don't advance loop state. `plan-phase` writes `PLAN.md` (optionally gated by adversarial `audit-plan`); `apply-phase` executes it task-by-task via an **Execute/Qualify (E/Q)** loop; `unify-phase` reconciles → writes `SUMMARY.md`, and on last-plan-in-phase **mandatorily** fires `transition-phase` (evolve PROJECT.md, git-commit the phase, blocking cross-file state-consistency check, route onward). Management workflows (`roadmap-management` add/remove-phase, `consider-issues`, `verify-work` UAT) fire anytime and feed fixes back into PLAN via a shared **Intent/Spec/Code** diagnostic router.

**The two cores most relevant to bongo:**
- **Verification-by-distrust without tooling.** PAUL's anti-false-completion machinery (E/Q loop, `evidence_before_claims` chain, adversarial `audit-plan`) is pure *discipline + persona*, enforced by re-reading files and re-running commands — no deterministic CLI behind it. This is bongo's exact auditor philosophy, articulated in prose but **not codified**.
- **PAUL parallelizes almost nowhere.** Only `map-codebase` (4 disjoint-domain Explore agents) and `research` (N independent topic agents) fan out — both read-only, both governed by one rule ("fan out only when self-contained + disjoint + no blocking checkpoints, then consolidate + human-review before touching trusted state"). `config.md` ships `preferences.parallel_agents: false` by default. **APPLY — the code-writing node — is deliberately, strictly serial.** That serial node is exactly what bongo replaces with parallel coders; PAUL is a pure *design-pattern donor* for state/verification discipline, not a coordination model.

## §2 — Per-Axis Findings

### Axis 1 — Command/skill structure & composition
- **Thin-command → workflow delegation via two-slot `@`-include.** `commands/paul/plan.md` is ~30 lines: `<execution_context>` lazy-loads `workflows/plan-phase.md` (385 lines) + templates + references; `<context>` loads `@.paul/{PROJECT,STATE,ROADMAP}.md` + `$ARGUMENTS`; `<process>` = "Follow workflow: @…plan-phase.md". The workflow path appears twice (static load + imperative dispatch) — deliberate. `@`-refs are **lazy-load signals, read at execution time, not pre-expanded** (`rules/style.md:71-73`).
- **Fixed 4-key frontmatter** (`name`, `description`, `argument-hint`, `allowed-tools`) with `allowed-tools` scoping the tool surface per command (read-only `status`/`progress` get `[Read]`; mutating commands get `Write`/`Edit`; subagent-spawners `discover`/`research` get `Task`). `rules/commands.md:12-27` mandates section order: `<objective>`→`<execution_context>`→`<context>`→`<process>`→`<success_criteria>`.
- **Namespacing:** flat `paul:kebab-case`. Verb taxonomy: lifecycle verbs are bare imperatives (`plan`, `apply`, `unify`); management verbs are `<verb>-<noun>` (`add-phase`, `complete-milestone`); query verbs are state-words (`progress`, `status`, `help`). ~28 commands across 8 categories (`help.md:46-55`).
- **Commands cross-reference to disambiguate** rather than overlap: `assumptions.md:13` "shows what CLAUDE thinks; discuss gathers what USER wants"; `discover.md:14` "distinct from research" (discovery *decides*, research *gathers*); `research-phase` vs `research` ("Claude identifies what needs researching" vs "user knows").
- **Sub-command multiplexing on a positional arg:** `flows.md:38-66` routes `$ARGUMENTS ∈ {∅, add, audit, list}`; `research.md` parses `--codebase`/`--web`. One command, several modes — keeps the surface small.
- **Authoring contract** (`rules/style.md`): imperative voice; banned filler ("Let me", "Just", "Simply"); banned sycophancy ("Great!", "Awesome!"); a **temporal-language ban** ("never 'Previously', 'No longer', 'Instead of' — describe current state only," exception: SUMMARY deviations + commits); XML = semantic containers, Markdown headers for hierarchy within.
- **Cautionary outliers (PAUL violating its own thin-command rule):** `help.md` (525 lines — but deliberately a static catalog, hard-gated "Output ONLY the reference content… Do NOT add analysis/git-status/suggestions"), `plan-fix.md` (216 lines, inlines its whole process instead of delegating), and the un-migrated frontmatter-less `config.md`/`map-codebase.md`. These mark where a thin-command discipline erodes without a rule-enforcer.

### Axis 2 — State persistence across context resets
- **STATE.md is THE source of truth** — read first in *every* workflow, a **<100-line digest, not an archive** (`templates/STATE.md:105,181-191`: "keep only 3-5 recent decisions, full log elsewhere"). Carries Current Position, ASCII Loop Position (`◉` active / `○` pending / `✓` done across PLAN/APPLY/UNIFY), Accumulated Context (Decisions/Deferred-Issues/Blockers tables), and a **Session Continuity** block (Last session / Stopped at / Next action / Resume file / Resume context — `references/context-management.md:146-160`).
- **paul.json satellite manifest** (`templates/paul-json.md`) — a **tooling-generated, never-hand-edited** JSON mirror of STATE.md (`milestone`/`phase`/`loop.position` enums + timestamps + `satellite.groom`) so an *external* system can locate project state without parsing prose. `register-manifest.md` reverse-engineers it for legacy projects by best-effort-parsing STATE.md's prose (including reading the ASCII loop markers to derive `loop.position`).
- **Two-level handoff** (`references/context-management.md:139-176`): *light* = STATE.md Session Continuity (quick same-day resume); *full* = `HANDOFF-{date}.md` written for a **zero-context reader** ("You have no prior context. This document tells you everything" — `templates/HANDOFF.md:9-11`), regenerated each pause, **consumed then archived** on resume (`resume-project.md:145-169`, cleans handoffs >7 days).
- **Filesystem-derived completion oracle:** phase-completion = `PLAN.md file-count == SUMMARY.md file-count` (`unify-phase.md:193-201`) — a stateless signal derived from disk, no separate ledger to drift.
- **Mutation discipline is per-doc** (clearest in `templates/DEBUG.md:60-98`): `status`/`Current Focus`/`Resolution` = **OVERWRITE**; `trigger`/`Symptoms` = **IMMUTABLE** (set once); `Eliminated`/`Evidence` = **APPEND-ONLY** ("prevents re-investigating dead ends after context reset"). `SUMMARY.md` immutable-once-written; `MILESTONES.md` append-newest-first; `ISSUES.md` append + move Open→Closed.
- **Context brackets** (`references/context-management.md:8-43`): FRESH(>70%)/MODERATE(40-70%)/DEEP(20-40%)/CRITICAL(<20%) drive behavior (load-full → re-read-keys → summary-before-full → finish-and-handoff). Quality-degradation curve (`references/work-units.md:9-22`): peak 0-30%, "completion mode" crash at the 40-50% inflection — hence the <50%-context, 2-3-tasks-per-plan rule.

### Axis 3 — Workflow lifecycle (phases/milestones/roadmaps)
- **`PLAN → APPLY → UNIFY` loop**, each node a STATE.md ASCII marker. Hard invariants (`references/loop-phases.md:156-186`): never skip PLAN ("no plan = no acceptance criteria = no way to verify"), never execute without explicit approval, always close with UNIFY ("no UNIFY = lost traceability").
- **Ceremony-by-size routing** (`plan-phase.md:52`): quick-fix (objective + 1 task + 1 AC, compressed) vs standard/complex (full boundaries + verification) — "a one-line fix doesn't need boundaries sections." Still loops through apply/unify.
- **Coherence check** (`plan-phase.md:234-272`) — zero-friction-when-clean validation across 4 axes (PROJECT.md constraints / STATE.md decisions / recent SUMMARY overlap / ROADMAP scope), surfaces *only* on conflict.
- **`transition-phase`** is where **PROJECT.md evolves** — requirements migrate Active→Validated (`✓ … — Phase X`) / →Out-of-Scope (with reason) / emerged-requirement added (`transition-phase.md:62-95`). The roadmap is a living hypothesis ledger, not a fixed plan. Includes a **blocking cross-file state-consistency gate** (alignment matrix of Version/Phase/Status across STATE.md × PROJECT.md × ROADMAP.md + stale-reference scan; "misalignment is a blocking error — do not route to next phase," `:236-289`).
- **Decimal phases** for urgent insertions (`6.1` between `6` and `7`); filesystem-sortable; **only "Not started" phases are removable** (`roadmap-management.md:151` — "they have no artifacts yet"), with directory renumbering kept in lockstep with the roadmap table.
- **`consider-issues`** — periodic triage with a two-tier issue store (global `ISSUES.md` enhancements vs phase-scoped `*-UAT.md` bugs), "accidentally resolved" detection (re-check against refactored code), natural-fit matching to upcoming phases.
- **Milestones** group phases; on `complete-milestone`, completed work collapses into `<details>` (not deleted), continuous numbering never restarts, a permanent `MILESTONES.md` entry + archived ROADMAP + git tag (created, **not pushed** — "user controls when to push").

### Axis 4 — Subagent orchestration & parallelization
- **PAUL parallelizes in exactly two read-only places.** `map-codebase.md` is the most parallel: **4 Explore agents, `run_in_background=true`, spawned simultaneously with disjoint-domain ownership** (Agent1 Stack+Integrations / Agent2 Architecture+Structure / Agent3 Conventions+Testing / Agent4 Concerns) → collect via `TaskOutput` → aggregate by predeclared document ownership. **Conflict-free because scopes are disjoint** ("Fresh context per domain, no token contamination," `:8-13`). `research.md` fans out N independent topic agents ("Spawn multiple agents in single message… Consolidate when all complete"; anti-pattern: "DON'T spawn A, wait, spawn B").
- **The dispatch gate** (`references/subagent-criteria.md`): subagents appropriate only when **ALL** of — Task Independence / Clear Scope / Parallel Value / Complexity Sweet-Spot (15-60 min) / Token Efficiency / State Compatibility. "Subagents are for parallelization of well-defined work, not context offloading." "Prefer in-session when uncertain."
- **The firewall:** subagent output **never auto-integrates** — "Main session always reviews findings" (`research.md:6`). Agent-type matching: `Explore` for codebase, `general-purpose` for web.
- **Everything else is single-thread.** APPLY executes "for each task in order"; there is no parallel execution model. `config.md` ships `parallel_agents: false`. **This is the boundary of PAUL's relevance to bongo: PAUL contributes the *fan-out-for-read-only-research* pattern (which Bongo Evolution Phase 1 is itself doing right now), and nothing about concurrent *writers*.**

### Axis 5 — Verification/validation discipline
- **`evidence_before_claims` chain** (`references/quality-principles.md:59-84`): "Execute → Verify (run command) → Read output → Compare to spec → THEN claim." Breaking any link = false completion. Backed by the canonical **anti-rationalization table** ("If you're thinking 'Should work now' → Run the verify command and read its output → Confidence is not evidence"; "'I already checked this' → Check again, fresh → Memory of checking is not verification"). Embedded inline in the APPLY qualify step for operational enforcement.
- **Execute/Qualify (E/Q) loop** (`apply-phase.md` + `loop-phases.md:86-96`): every auto task is Executed, then **independently Qualified** — re-read actual files, re-run verify *fresh*, compare line-by-line against spec AND linked AC — because "the implementer's report of their own work is inherently optimistic." Scored **PASS / GAP / DRIFT**; GAP/DRIFT → fix-and-requalify loop, max 3 attempts then escalate.
- **Four-state honest reporting** (`loop-phases.md:70-85`): DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED. "NEVER silently produce work you're unsure about… NEEDS_CONTEXT is not failure — it's honest communication."
- **Adversarial enterprise plan audit** (`workflows/audit-plan.md`) — the rigor centerpiece, a *sub-step of PLAN* (does NOT advance loop position). Role-primes Claude as "senior principal engineer + compliance reviewer… Do not validate or encourage. No praise unless it supports a risk decision." Six-section output ending in "Would you sign your name to this system?"; **three severity tiers** (Must-Have release-blocking / Strongly-Recommended / Can-Safely-Defer); **auto-remediation** — must-have + strongly-recommended findings are *automatically written into the plan* (marked `<!-- audit-added -->`); and a **hard verdict gate** — verdict "not acceptable" *removes the APPLY option entirely* from routing (`:291-301`). Anti-rubber-stamp: "Do NOT produce a positive audit without substantive analysis."
- **`verify-work` (UAT)** — Claude generates the checklist + guides; the *USER* performs all testing via per-test AskUserQuestion (Pass/Fail/Partial/Skip → Blocker/Major/Minor/Cosmetic). Issues → phase-scoped `*-UAT.md`, never global ISSUES.md.
- **Intent/Spec/Code diagnostic classification** (`references/checkpoints.md:136-156`, applied in both APPLY checkpoint-failures and verify UAT-failures): classify root cause *before* fixing — Intent→re-plan (archive superseded), Spec→fix ACs/tasks before code, Code→fix-in-place. "Claude's default under pressure is to patch code because it's the fastest visible action — but speed at the wrong layer creates more work."
- **`quality-gate` (SonarQube)** — the deliberate *non-blocking* counterweight: "Quality as input, not gate. A failing gate means 'address this' not 'stop everything'" (`quality-gate.md:14-17`). Updates `codebase/CONCERNS.md`; never blocks the loop. Two-speed model: hard architectural gate (audit-plan, blocks) vs soft metrics report (quality-gate, advises).
- **`debug`** — scientific-method: falsifiable one-at-a-time hypotheses, **root-cause-confirmed-with-evidence before fixing**, Eliminated ledger prevents re-investigating dead ends, "minimal fix = SMALLEST change that addresses root cause," verify against original Symptoms.

### Axis 6 — Quality gates & checkpoints
- **Three checkpoint types** (`references/checkpoints.md`) — **identical taxonomy to gsd**: `human-verify` (90% — confirm automated work), `decision` (9% — architectural choice w/ pros/cons options), `human-action` (1% — only truly un-automatable: email links, 2FA, OAuth, 3DS). **Golden rule: "If Claude CAN automate it, Claude MUST."** Users never run CLI/deploy/build.
- **Auth gates are dynamic, not pre-planned** (`:158-167`): Claude tries CLI → 401 → *then* creates a dynamic checkpoint → human authenticates → retry. "Pre-planned 'I need you to deploy' is WRONG; 'I tried to deploy but need credentials' is CORRECT."
- **Checkpoint hygiene:** automate everything *before* the checkpoint; be specific ("Visit https://… not 'check deployment'"); one verification per checkpoint; avoid verification fatigue (combine into one at the end).
- **`assumptions`** — surfaces *Claude's own* assumptions across 5 axes (Technical Approach / Implementation Order / Scope Boundaries [In/Out/**Ambiguous**] / Risk Areas / Dependencies) with **confidence tagging** ("Fairly confident" / "Assuming" / "Unclear") *before* expensive planning. No file output — pure conversational misalignment-catcher.
- **`SPECIAL-FLOWS` declared-capability auditing** — required-vs-optional skill registry; "required" skills generate a **gap logged at UNIFY** if not invoked ("If a skill is important enough to use, it's important enough to track"). Warn, don't block.
- **Mode toggles** (`config.md`): `enterprise_plan_audit.enabled` (drives audit-plan), `sonarqube.enabled` (drives quality-gate) — pipeline rigor is per-project configurable.

### Axis 7 — Config & flows
- **`config.md`** — YAML-in-markdown: `project.{name,version}`, `enterprise_plan_audit.{enabled}`, `sonarqube.{enabled,project_key}`, `preferences.{auto_commit, verbose_output, **parallel_agents: false**}`. Boolean toggles adapt PAUL behavior; the `parallel_agents` default-off is the tell that PAUL treats concurrency as an unfinished advanced feature.
- **`configure-special-flows`** — scans `~/.claude/commands/` for skills, maps them to work-types with required/optional priority + trigger conditions, generates `SPECIAL-FLOWS.md` + a PROJECT.md quick-ref. Sub-commands `add`/`audit`/`list`; the `audit` sub-command checks the current phase against declared flows (verification during UNIFY). Layered reinforcement: SPECIAL-FLOWS → ROADMAP phase annotation → PLAN `<skills>` section → UNIFY gap-check.
- **No model profiles.** PAUL has *no* per-role/per-task model selection — a gap relative to gsd (see §7).

### Axis 8 — Resume / handoff
- **Deterministic single-next-action routing — no menus.** `resume-project.md:96-108` maps loop state → exactly ONE action (PLAN○→`/paul:plan`; PLAN✓APPLY○→`/paul:apply`; APPLY✓UNIFY○→`/paul:unify`; all✓→`/paul:plan` next phase; Blocked→address blocker). "Do NOT offer multiple options. Pick the ONE correct action… Prevents decision fatigue." `progress.md` is the read-only mid-session router with the same table + a context-capacity advisory (DEEP/CRITICAL → "Recommended: /paul:pause").
- **Handoff lifecycle:** `pause-work` writes HANDOFF + STATE Session Continuity (optional WIP commit with a commit?/branch? two-question gate) → `resume-project` reads them, presents context, routes one action → **handoff consumed → archived** (`handoffs/archive/`, cleans >7 days). Conflict rule: if STATE.md and files disagree → report + ask; if handoff older than STATE.md → "Trust STATE.md."
- **`status` is DEPRECATED** in favor of `progress` — a deliberate retirement of *multi-option* status suggestions for *single-routing*. The deprecation stub (`status.md:3` "[DEPRECATED] Use /paul:progress") is kept, not deleted: the distinction itself is the lesson (single-routing > option-menus).

### Axis 9 — Init / onboarding
- **`init-project`** — type-adaptive conversational walkthrough (Application/Campaign/Workflow/Other) with complexity inference (simple/standard/complex) scaling question depth; **one question at a time**; populate-from-answers (not skeleton templates). Creates the whole `.paul/` substrate (PROJECT/ROADMAP/STATE/paul.json/phases/ + optional config.md, SPECIAL-FLOWS.md). SEED off-ramp for complex projects; optional `PLANNING.md` import.
- **`register`** — generates `paul.json` for pre-v1.1 projects lacking one, by reverse-parsing STATE.md prose into structured fields (refuses if `.paul/` missing or paul.json exists). The graduation path for legacy projects into the machine-manifest world.
- **`map-codebase`** (brownfield) — the 4-parallel-Explore-agent fan-out (Axis 4) producing the 7 `codebase/*.md` maps, each agent carrying **mandatory file-path citations** ("Concerns without file paths are not actionable… Do NOT include line numbers, they go stale, just file paths") — then a git commit `docs: map existing codebase` and a STATE.md note.

## §3 — TOP Patterns Bongo Should ADOPT (ranked)

> Each maps to a concrete `.coord/` file or `/bongo:` command. Bongo's edge is concurrency; these are chosen because they *strengthen* parallel coordination, not replace it. (Where a pattern also appears in coder-7's gsd dig, I note the convergence — those are highest-confidence because two mature frameworks independently arrived at them.)

### ADOPT-1 — The two-slot thin-command → workflow split for `/bongo:*` ★ highest structural leverage
**paul:** every command is one screen; logic lives in `paul-framework/workflows/*.md`, pulled via `<execution_context>` (static) + `<context>` (dynamic state + `$ARGUMENTS`) + a one-line `<process>` dispatch (`rules/commands.md:31-37`, `commands/paul/plan.md`).
**bongo today:** the cold-boot logic lives inside giant `.coord/cold-boot/{SUPERVISOR,AUDITOR,CODER}-startup.md` files that each fully re-state the startup sequence (I read CODER.md + CODER-startup.md this session — they overlap heavily and drift independently). There is no shared procedure file; the three role specs duplicate protocol.
**Mapping:** extract role behavior into `bongo-framework/workflows/{supervisor,auditor,coder}-boot.md` + shared `workflows/{push-protocol,claims-protocol,ship-notice}.md`, and make `/bongo:resume <role>` a thin command whose `<context>` loads the role spec + `$ARGUMENTS` (role keyword) and whose `<process>` is "Follow workflow: @…<role>-boot.md". One edit to `push-protocol.md` then fixes the protocol for all three roles at once. **Convergence with gsd ADOPT (coder-7 §1, Axis 1) — both frameworks use this exact separation; adopt with high confidence.** Pair with paul's `rules/style.md` + `rules/commands.md` authoring contract (imperative voice, no-sycophancy, temporal-language ban, fixed section order, one-screen rule) as `bongo-framework/rules/` so the `/bongo:` surface stays self-consistent as it grows past today's 4 commands.

### ADOPT-2 — Per-doc mutation discipline (OVERWRITE / IMMUTABLE / APPEND-ONLY) tagged on every `.coord/` file
**paul:** `templates/DEBUG.md:60-98` tags each section's write mode explicitly — the single best concurrency-safety primitive PAUL offers. Append-only sections are inherently safe under concurrent writers; overwrite sections need single-owner.
**bongo today:** the write rules exist but are scattered in `README.md`'s prose table and learned the hard way (`feedback_auditor_hot_inbox_append`: "append via `cat >>` not Edit, the mutation-guard fires on sibling writes" — a rule discovered by a bug, not declared by schema).
**Mapping:** stamp a mutation-mode header at the top of each `.coord/` file's template: `shared/decisions.md` = **APPEND-ONLY** (with a stable monotonic ID column, supersede-don't-delete per paul's PROJECT.md Key-Decisions `Active/Superseded`); `inbox/<id>.md` = **APPEND-ONLY** (codify the `cat >>` rule into the schema, not memory); `shared/master-tip.md` = **OVERWRITE, single-writer = last-pusher**; `status/<id>.md` = **OVERWRITE, owner-only**; `shared/claims.md` = **APPEND-row + edit-own-row-to-release**. This turns three memory-logged bug classes into declared schema. **Convergence with gsd (coder-7 ADOPT-6) — both lift this from the debug-session protocol.**

### ADOPT-3 — Adversarial pre-dispatch audit of the *lane prompt* (paul's `audit-plan`, adapted) — auditor as pre-flight reviewer
**paul:** `audit-plan` role-primes a hostile reviewer over the PLAN *before* APPLY, classifies Must-Have/Recommended/Defer, **auto-applies the top two tiers into the plan**, and **strips the proceed-path on a "not acceptable" verdict** — a hard gate, not a comment. Crucially it is a *sub-step of PLAN that does not advance loop state* (`audit-plan.md:259-261`) — quality-check separated from progress-state.
**bongo today:** the auditor only validates *after* a coder ships (post-hoc SHIP-NOTICE probe). There is no pre-dispatch review of whether the lane prompt itself is sound — yet the memory shows lane prompts shipping with "5 code-deploy gaps in 4 prompts" (`feedback_cowork_prompt_verify_before_write`) and dead-duplicate lanes dispatched off stale specs. The expensive failure happens *after* a tab burns context on a bad prompt.
**Mapping:** an optional **`/bongo:audit <lane-prompt>`** the auditor runs on a drafted lane prompt before the coder is fired — adversarial-persona review for must-have coverage, disjointness vs sibling lanes, and *deployed-surface verifiability* of the acceptance bar, returning a Must-Have/Recommended/Defer verdict. A "not acceptable" verdict blocks dispatch (mirrors audit-plan's verdict-gate). **Constraint to resolve at synthesis:** bongo's ratified Hard-NO bars the auditor from *authoring dispatch intent* (`decisions.md` 2026-05-19 item A) — so the auditor *reviews* the prompt, the supervisor *authors+revises* it (paul keeps audit a PLAN sub-step for exactly this separation). This is the pre-flight analog of the already-ratified repro-paste mandate, moved author-side. **Seam with gsd:** gsd's pre-execution `plan-checker` (8-dimension goal-backward, coder-7 §2 Axis 5) is the structured-checklist flavor of the same idea — synthesis should likely fuse gsd's checklist with paul's adversarial-persona + verdict-gate (see §7).

### ADOPT-4 — `wave / depends_on / files_modified` frontmatter on lane assignments (planner-time disjointness)
**paul:** `templates/PLAN.md:12-20` + `references/plan-format.md:27-35` pre-compute `wave: N`, `depends_on: []`, `files_modified: []`, `autonomous: bool` at *plan time* — a parallel-execution dependency graph with file-conflict detection, with an explicit anti-pattern against **reflexive chaining** (`references/context-management.md:107-133`: "Does 02 actually need 01's output? ### ADOPT-6 — Persistent debug-session protocol for the parallel setting

Routes the bounce correctly instead of reflexively patching code. This is **paul-distinctive** (coder-7's gsd dig did not surface an equivalent) — a pattern only paul contributes to the synthesis.

## §4 — ADAPT (single-thread ideas needing rework for concurrency)

- **STATE.md single global mutable digest → shard per-lane, keep only shared scalars central.** PAUL's STATE.md is one file "updated after every significant action" with a <100-line cap (`templates/STATE.md:104-206`) and a *single* loop cursor (one PLAN/APPLY/UNIFY position). Two concurrent writers clobber it; one cursor can't represent lane-1-applying-while-lane-2-planning. **Adapt:** bongo already does the right shard (`status/<id>.md` per-lane = paul's STATE Current-Position + Session-Continuity, owner-only-overwrite; `shared/{master-tip,decisions,claims}` = only genuinely-shared scalars under append/single-owner discipline). Borrow paul's *<100-line digest* and *Session-Continuity block* into `status/<id>.md`, and its *ASCII loop marker* per lane for a supervisor glance-dashboard — but never re-centralize into one STATE.md.
- **paul.json satellite manifest → per-lane manifest + an aggregate, reconciled against git not just disk.** paul.json is one machine-readable cursor (`milestone`/`phase`/`loop.position`) mirroring one linear actor, and `register-manifest` *trusts* STATE.md prose. In bongo, N worktrees + origin/master diverge constantly (this very session: my worktree's base SHA `9d221e3bf` was 2 commits stale within minutes because coder-7 + others pushed). **Adapt:** if bongo adds a manifest, it must be *per-lane* + an aggregate, and any "where is master?" read must **reconcile against `git rev-parse origin/master` / `git ls-tree`** (Windows-safe per `feedback_git_ref_path_check_windows` — `git cat-file -e <rev>:<path>` mangles the colon-path; use `git ls-tree`), reporting drift rather than trusting the markdown. (`master-tip.md` already documents the stale-tip hazard; a manifest must not reintroduce it.)
- **`config.md` rigor toggles → express as bongo's existing risk-tiers, don't add a parallel config axis.** paul toggles `enterprise_plan_audit`/`sonarqube` per project. Bongo already has a ratified **Tier 0/1/2** verification system (`README.md` Verification flow). **Adapt:** map paul's audit-on/off onto the tiers (Tier 0 = self-evidence only; Tier 1 = + auditor deployed probe once/wave; Tier 2 = + independent prod-probe + binary verdict) rather than introducing a second `config` knob.
- **audit-plan auto-remediation → bongo can't auto-rewrite a lane prompt the way paul auto-rewrites a PLAN.** paul's audit *modifies the plan in place* because the same single actor owns plan + execution. In bongo the auditor must not author dispatch intent (Hard-NO item A). **Adapt:** audit-plan's *findings* (must-have/recommended/defer) carry over, but the auto-apply step becomes a structured CONCERN handed to the supervisor, who applies it — keep the verdict-gate (block dispatch) but not the auto-edit.
- **E/Q max-3-attempt fix loop → make it the coder↔auditor inbox round-trip, capped + async.** paul's qualify retries in one session (max 3, then escalate). Bongo's analog is the coder's SHIP-NOTICE → auditor BLOCK → coder follow-up — but it's async across tabs, not a tight in-session loop. **Adapt:** cap the auditor↔coder bounce (e.g. 2 rounds) before escalating to the supervisor/Daniel, mirroring paul's bounded-loop-then-escalate, rather than an unbounded ping-pong.
- **`verify-work` human-UAT → keep, but it's already bongo's deferred UAT-PENDING model.** paul's UAT is synchronous (user tests now). Bongo already defers human-verify (`feedback_uat_checklist`: "human-verify checkpoints don't block APPLY; append to UAT-PENDING.md, verify at milestone end"). **Adapt:** borrow paul's *per-test severity capture* (Blocker/Major/Minor/Cosmetic → distinct routing) and *AC→test mapping* into bongo's UAT-PENDING entries, but keep bongo's deferred (non-blocking) timing.
- **map-codebase / research fan-out → bongo already does this; formalize it.** paul's 4-disjoint-domain Explore fan-out is *exactly* what Bongo Evolution Phase 1 is doing right now (and what I did this session: 4 subagents over disjoint corpus chunks → my synthesis). **Adapt:** promote this from ad-hoc to a named `/bongo:research` flow with paul's disjoint-domain-ownership + mandatory-file-citation rules baked in.

## §5 — REJECT / Anti-patterns (don't bloat bongo)

- **The whole PLAN→APPLY→UNIFY lifecycle + roadmap/milestone/phase spine.** PAUL is a *project workflow* with a linear loop and its own STATE/ROADMAP/PROJECT/transition/complete-milestone machinery. Bongo is a *coordination layer over an already-running, already-roadmapped project* — and the CRC app **already runs PAUL** (`.paul/` is the live project planner). Importing PAUL's lifecycle into bongo would *duplicate the thing already in use one directory over*. **Reject the lifecycle; borrow the mechanics (mutation discipline, frontmatter waves, verification distrust, diagnostic classification, routing).** (Coder-7 reached the identical conclusion about gsd's `.planning/` spine — neither planner's lifecycle belongs *inside* bongo.)
- **Single-global-STATE.md / single-loop-cursor / paul.json single-actor manifest.** Already covered in §4 — the parts of PAUL that *assume one linear writer* are exactly the parts bongo's `.coord/` sharding exists to replace. Re-importing them would undo bongo's reason to exist. **Reject** the centralization; bongo's per-agent shard is the destination.
- **Monotonic global IDs assigned at write-time** (paul's `ISS-NNN`). Two concurrent appenders both grab `ISS-007` → collision. Bongo's `decisions.md` should either pre-allocate ID ranges per agent, namespace by agent, or rely on atomic append (bongo already chose atomic `cat >>` for inboxes — `feedback_auditor_hot_inbox_append`). **Reject** write-time global monotonic numbering for any concurrently-written file.
- **Edit-in-place checklist mutation** (paul's `- [ ]`→`- [x]` and Open→Closed moves in ISSUES/UAT/ROADMAP). A read-modify-write on a shared file = lost-update under concurrency. **Reject** in-place checklist flips on shared files; prefer append-only event logs the supervisor compacts later.
- **SonarQube/quality-gate integration.** App-code-quality tooling — that's the *project's* concern (owned by the CRC app's own CI / PAUL), not the agent-coordination layer's. **Reject** as out of bongo's layer. (The *two-speed* idea — hard gate vs soft advisory — is worth keeping conceptually, but it's already bongo's BLOCKS-GREEN-vs-POLISH tagging, `decisions.md` 2026-05-19.)
- **SPECIAL-FLOWS as a full subsystem.** paul's skill-registry + UNIFY-gap-audit is elegant but heavyweight. Bongo's equivalent need is narrow ("did the coder use `/ui-ux-pro-max` on a frontend lane?" — `feedback_ui_ux_skill`). **Reject** the full registry; a one-line "required skills" field in the lane assignment + an auditor check covers bongo's actual need without the machinery.
- **`help.md`-scale static catalogs and inlined heavy commands.** paul's own thin-command rule erodes in `help.md` (525 lines) and `plan-fix.md` (216, inlined). **Reject** letting any `/bongo:` command balloon — enforce the one-screen rule via the borrowed `rules/commands.md` (ADOPT-1) precisely so bongo's cold-boot files (today's biggest offenders) don't become paul's `help.md`.

Bongo's analog is auditor-BLOCK and Daniel-feedback bounces. Confirm it attaches to the BLOCK-TEARDOWN message schema (ADOPT-7) and the cycle-fix-wave intake.
