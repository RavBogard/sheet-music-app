Per row, all fourteen. Reads only; no write, no dedupe pass, no fuzzy sweep of any kind:

read is a **finding**, not a gap to fill with an inference — pair 3's larger side may well be one, and if the bytes are

## N2 · the proposal, and the rule for when there is nothing to say

One proposed title per row, and **every distinguisher in it must appear in N1's packet.** Preferred order, most
recognisable first: **arranger or setting** → **key** → **language or script** → **page count** → **duration** →
**format**. Two or three distinguishers is a name; five is an inventory entry the band will not read on an iPad on a
Friday night. Keep the stem the band says out loud — `Lecha Dodi`, `V'Shamru` — and put the distinguisher after it, so
search on the stem still finds both rows (the MCP's own title matching normalises spacing, underscores, hyphens and
diacritics, so the *stem* is what a musician's search hits).

**Where N1 measured no distinguisher, the row keeps its title, and the return says so by name.** That is `-26`'s hard
edge: a name that carries no measured difference is a lie about a difference, and a suffix is worse than the collision
it hides.

**Transliteration is not a distinguisher.** `Veshamru` vs `V'Shamru` is the same word twice, and this order does not
standardise spellings — the MCP normalises them for search anyway, and choosing house transliteration for the
congregation's own liturgy is Daniel's, not a wave's.

## N3 · the write, and how each one is undone

**Tool** `edit_library_entry {rowId, edits: {title}}` — `dryRun` defaults **true** and returns `plannedPatch`; the real
write needs `dryRun: false, force: true`, and it stamps `humanRenamedAt` and sets `enrichmentStatus:
"human_curated"`. **One row per call. Fourteen calls at most, no batch form used even if one exists.**

**Undo** the same tool with the prior title. Which is only true if the prior title still exists somewhere — so, per
`R-0904-live-cw-8`, **all fourteen `{id, title}` pairs go into the return before the first write**, not after the last.
A rename is reversible exactly as long as the old name is written down; a rename whose only record of the old name is
the row that was overwritten is not a rename, it is a loss.

Quote each `plannedPatch` from the dry run next to the real result. If a row's live title already differs from the table
above, **stop on that row and report it** — someone or something renamed it since 15:0xZ, and that is worth knowing
before a second hand writes over it.

## Where this sits, and why a rename waits for the gate

Wave **3** of `PROGRAM-SATELLITE-HEALTH-2026-09-04.md`, immediately after the gate goes on, and **the first wave that
touches what the band sees.**

I considered arguing it out from under the boundary rule, and it does not survive the argument. The case for going
early: a title is not code, nothing deploys, no chart moves, and the whole change is one text field per row. The case
that wins: **the name IS the band's interface.** A musician on the bimah finds a chart by typing a stem into a search
box; rename fourteen rows and the thing they memorised is different — the risk is not breakage, it is **recognition**,
and recognition failing at 19:15 on a Friday is exactly the harm the boundary rule was written for. And N4 changes a
row's **visibility** in browse, which is the boundary's plainest case.

So it waits. Not because a rename is dangerous, but because Daniel's condition on approving the program was that the net
exists before anything on this side of the line is touched — and this is the wave the net was built for. Running it
first *after* the gate is the honest exercise of the gate, rather than choosing a safe wave and calling the mechanism
proven.
