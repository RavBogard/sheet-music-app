# Research: web-app (browser app outside Perform, plus the v2 redesign)

Walked live on https://www.centralreform.live on 2026-10-31 with a `test-gap-` band_leader account (loginable, minted through the `create_test_account` ops tool and the `/test-login?code=` path). Desktop 1440x900 and iPad 820x1180. Screenshots are in `research/shots/` (`d-*` desktop, `i-*` iPad). Nothing real was written: no row was edited, no setlist created. The test account was revoked at the end (`revoke_test_account` returned `revoked:true, authDeleted:true`; `list_test_accounts` is empty).

Not covered: admin-only pages (`/manage/library-review`, `/platform/*`, `/monitor/admin`), because a band_leader is redirected away or gets a 404. Write flows (Create New Setlist, Upload, Add Song, template editor saves) were not exercised, to avoid prod writes.

## 1. How it works today

- Login lands on `/setlists` (redirect from `/test-login`). The top nav is Setlists, Schedule and Library, plus search, notifications and a user menu (`d-setlists.png`). `/` is a separate dashboard with one "Today" hero card (Perform and Edit) and an onboarding card (`d-dashboard.png`, `DashboardClient.tsx`, `components/dashboard/HeroCard.tsx:97`). So there are two "homes".
- `/setlists` (`(main)/setlists/page.tsx`, data in `hooks/use-setlist-dashboard.ts`) has: rabbi chips (free-text `s.rabbi`, lines 412 and 442), Create New Setlist, Upcoming (2 cards), then "Library & past events" as a ~4000px list (`d-setlists-full.png`) with "Load older setlists".
- `/setlists/[id]` is the editor: a drag-sortable row list (`components/setlist/grid/MobileRowCard.tsx`) with key pill, chart-open icon and recordings icon. The number shown is `track.order + 1` (`MobileRowCard.tsx:292`). It has no Perform button in the header.
- `/perform` is the index of services, `/perform/setlist/<id>` the band view with notes, page numbers, Swap, Save-offline, Print and Edit. A chart opens at `/perform/setlist/<id>/track/<trackId>` with Prev/Next.
- `/library` is a flat searchable list (CRC 249, Shireinu 272, Nava Tehilah 142, Uploads 188, Audio 65). A tap opens the chart straight in the Perform viewer at `/perform/<driveFileId>`. There is no song detail page.
- `/manage` has People, Library (Drive sync, archived, tools) and Sound (bridge, X32). `/manage/templates` is the template editor. `/admin` and `/audio` are redirect aliases. `/settings` holds account, theme, live-gig mode and push.
- `/schedule` lists upcoming gigs with "No musicians assigned yet".
- `/v2` is a single showcase page (see section 3).

## 2. Findings

## 3. v2 redesign: state and recommendation

- **Completeness:** one page, `src/app/(v2)/v2/page.tsx` (84 lines), plus 7 primitives in `src/components/v2/` (650 lines with tests and a README). All content is demo. The README says "Foundation only. No production routes have been migrated." The last change was an i18n pass on 2026-10-12 (`782f8d30`).
- **Reachable:** yes, by the footer link on every v1 page for every logged-in user, and directly at `/v2` (login required, `proxy.ts:106-118`). Any `/v2/<child>` is 404. The opt-in cookie is cosmetic (never read), so "opting in" changes nothing.
- **Cost of keeping:** a second font load (Geist), a second token set in `globals.css`, i18n keys, tests, and a footer link that invites musicians into a dead end.
- **Recommendation: delete.** Evidence: no migrated route, nothing consumes the cookie, no live planning doc outside `archive/` continues it, and Daniel authors via MCP, so a new browser shell has no author to serve. Step 1 (XS, safe): remove the footer link now. Step 2 (S): delete `src/app/(v2)`, `src/components/v2`, the `[data-theme="v2"]` block, the `v2.*` i18n keys and the `/v2/` branch in `proxy.ts`. If a denser look is wanted, port `DenseList` into the review view (WEB-14) inside v1 instead of reviving a parallel app. Merging is not worthwhile (one demo page). Finishing is not recommended (a full second UI for a backup surface).

## 4. Big bets

1. **Review mode for a setlist ("what the band will see").** Problem: review is the app's main job and the editor is a tall edit grid with no chart identity. Sketch: `/setlists/[id]/review`, one line per row (number, title, key, page, chart chip with format/version/instrument, notes), flags for missing chart, key mismatch, unbound rows and order collisions, plus a diff against last week's same-service setlist. Risk: a second view of the same data; keep one data hook. Effort M-L.
2. **Song page with variants grouped.** Problem: 8 entries for one prayer, filenames as titles, wrong-chart risk. Sketch: `/library/song/<id>` shows variants (by key, arrangement, instrument), the default, last used and setlists; "make default" is a small edit; search lands here instead of the viewer. Risk: needs the song/variant model to be clean (cross-check the MCP researcher). Effort M-L.
3. **Slim the shell to four things:** Setlists (Today pinned), Library, Review (bet 1) and Manage. Delete Schedule, v2, Changelog and the alias routes. Problem: sprawl and dead ends. Risk: low. Effort S-M.
4. **Pre-service check panel** on Review: every chart reachable and cached, key mismatches, empty rows, time of last edit. Problem: Perform reliability and trust, since nothing is fixable mid-service. Sketch: reuse `verify-chart-bond-health` results and the offline-saved state. Risk: per-device cache state is client-side only and needs a small report endpoint. Effort M-L.
5. **Variant folding in `/setlists`:** collapse per-instrument and "(Copy)" setlists under one service row with an expander, plus search by title and date. Effort M.
