# Mission — make centralreform.live truly multi-tenant, Nava Tehila first

Filed 2026-10-12 from a Cowork kickoff interview with Daniel. This is the brief every
later doc in this folder answers to. Rulings here are Daniel's; nothing below is a guess.

## Why

Nava Tehila (the Jerusalem band / davening community) saw the backend, the Claude MCP
connector and the charts and want a version for themselves. Daniel ruled that instead of
hand-rolling a third tenant the way Brothers Lazaroff was done (June 2026), the platform
becomes properly multi-tenant, able to add tenants easily, up to roughly 20 at most.
Nava Tehila is the first tenant onboarded through the new path and the proof it works.

## Outcome (what exists when this is done)

1. A tenant is data, not code: registry, branding, vocabulary, colours, fonts, time zone,
   email sender, print footer, feature flags all live in per-tenant config (Firestore),
   with a seed path (script and/or console) that creates a working tenant end to end.
2. Roles are per tenant. Daniel is the single platform owner ("super-admin") who sees
   every tenant. Each tenant has its own admin. Sign-up joins only the tenant whose
   address you signed up through (the current "every new user joins CRC and BL"
   default is gone).
3. A super-admin console (UI) for managing all tenants, and MCP tools that let Daniel do
   the same things through Claude.
4. Shared chart collections: a tenant can publish a collection read-only to other
   tenants, and Daniel can manually assign any collection to be viewable/usable in other
   tenants. Pickers default to the tenant's own charts, with opt-in to shared
   collections. Nava Tehila's catalogue is the first shared collection (it already
   exists as the `nava` collection inside CRC's library and becomes Nava's seed library).
5. One Vercel deployment and one Firebase project for all tenants. Every tenant gets a
   subdomain by default; a custom domain is an automated add-on (people will want their
   own domains). Daniel has no strong opinion on mechanism — whatever is simplest and
   robust on one deployment.
6. Per-tenant feature flags for: mixer / X32 bridge, Drive chart inbox, scheduling
   emails, today.json / Overlays feed, notify_band, iPad Perform. Nava starts with
   charts, setlists, Perform and MCP only.
7. Nava Tehila is set up shul-style (service types, liturgy frames, books — not BL's
   "band mode"), Asia/Jerusalem time zone, and the band-facing interface is available in
   Hebrew (right-to-left) from day one. A web siddur for them is a possible later
   addition, out of scope here.
8. Everything still hardcoded to CRC (time zone in ~7 places including cron, scheduling
   emails, calendar feed, chart footer, gig-packet title, legal pages, library tabs,
   liturgy frames/books, the MCP agent guide, DEFAULT_CONFIG, BASE_URL) is made
   per-tenant.

## Boundaries

- CRC and Brothers Lazaroff keep working exactly as they do today throughout. Any change
  to what a CRC or BL user sees or can do interrupts Daniel.
- Stays on one Vercel project and one Firebase project. No hosting ceiling was set;
  the analysis should still state the expected cost shape at 20 tenants.
- Billing tenants is out of scope for now.
- Money (any new paid service, any plan change on Vercel / Firebase / Resend) interrupts
  Daniel.
- No calendar. Daniel gets cost and shape, not a schedule.

## Authority

- Interrupts Daniel: money; CRC/BL-visible behaviour changes; any data migration that
  cannot be reversed; genuine product judgment calls with no precedent in this brief.
- Claude decides and logs everything else, and deploys to production without asking when
  it looks ready (September 2026 ruling stands).
- Machine gates decide readiness (see Proof).

## Proof ("done means verified, not written")

- The BL isolation probe (scripts/e2e-bl-tenant-probe.mjs) generalised to every tenant
  and passing in production.
- A brand-new throwaway tenant created end to end (script or console) with a real Google
  sign-in that lands only in that tenant.
- An MCP connection through that tenant's address that cannot see CRC data.
- An independent adversarial pass on the Firestore rules attempting cross-tenant reads
  and writes.
- No sign-off from Nava's side is required to call it done; their admin is to be
  determined later.
