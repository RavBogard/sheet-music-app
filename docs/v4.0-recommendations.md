# CentralReform v4.0 — Feature Recommendations

Five proposals based on the v3.5 codebase audit. Each addresses a real architectural gap or user pain point observed during the cleanup and feature work.

---

## 1. Real-Time Collaborative Setlist Editing

**The problem:** Two music directors open the same setlist. Both reorder songs. Both hit save. The second save silently overwrites the first — `updateDoc(docRef, cleanData)` does a blind last-write-wins with no conflict detection. There's no presence awareness (who's looking at this setlist right now?), no live cursor tracking, and no way to see edits as they happen. For a shared liturgical planning tool, this is a critical gap.

**The evidence:** `setlist-firebase.ts` line 91 — `updateDoc(docRef, cleanData)` with no version check, no transaction, no optimistic concurrency. The `subscribeToSetlist` listener pushes server state to the client, but the editor doesn't merge incoming changes with local edits — it either ignores them or stomps the user's work.

**What ships:**
- Firestore transactions with optimistic concurrency: read-modify-write with version field, retry on conflict
- Presence system: `setlists/{id}/presence/{uid}` subcollection with heartbeat, shows colored avatars of who's viewing/editing
- Operation-based updates: instead of replacing the entire `tracks` array, send granular operations (reorder track 3→5, add track at position 7, update notes on track 2) that merge cleanly
- Live edit indicators: when another user is editing a track's notes or details, show a subtle "Karen is editing..." indicator
- Conflict resolution UI: if two users move the same track simultaneously, surface the conflict rather than silently dropping one

**Impact:** Music directors can plan services together in real time — one picking songs while the other sets keys and adds notes. Eliminates the "who has the latest version?" problem that plagues shared documents.

## 2. Background PDF Pipeline

**The problem:** The print route (`/api/setlist/print/route.ts`, 313 lines) does everything synchronously in a single HTTP request: authenticate → fetch each PDF from storage → extract chords via OCR → transpose each chord → re-render the PDF → merge all PDFs into one packet → return the blob. For a 15-song setlist with transpositions, this chains 15 network fetches + 15 OCR passes + 15 PDF renders + 1 merge — all within Vercel's 60-second function timeout. It works for small setlists today, but it's one bad PDF away from a timeout failure with no recovery.

**The evidence:** `print/route.ts` lazy-loads `pdf-chord-extractor` and `pdf-transpose-renderer` per request. Each `extractChordsFromPdf` call runs OCR on every page. There's no caching of extracted chords (the `chord-cache` API exists but isn't used in the print path), no progress feedback, and no way to resume a failed job.

**What ships:**
- Job queue: print requests create a job document in Firestore (`print_jobs/{jobId}`) with status tracking (queued → processing → complete/failed)
- Chord extraction cache: when a file is first analyzed, store extracted chord positions in `library_index` metadata so subsequent prints skip OCR entirely
- Incremental processing: each track is processed independently, results cached. If track 12/15 fails, the first 11 are still available
- Progress SSE stream: client subscribes to job status via Server-Sent Events, sees "Transposing track 4 of 15..." in real time
- Pre-generation: when a setlist is finalized, kick off background print generation so the packet is ready before anyone requests it

**Impact:** Print never times out. Second print of the same setlist is instant (cached). Progress visibility eliminates the "is it working?" anxiety of staring at a spinner for 30 seconds.

## 3. Smart Library Browser with Liturgical Categories

**The problem:** The library has ~180 files with rich metadata — key signatures, topics, BPM, artists — all generated by the Gemini enrichment engine. But the only way to find a song is to type into a Fuse.js search box. There's no way to browse by liturgical function ("show me all Shema settings"), filter by key ("what do we have in D major?"), discover related songs ("other pieces by this composer"), or see what's commonly used together. The metadata exists but it's invisible.

**The evidence:** `enrichment-engine.ts` extracts topics like "Worship", "Joy", "Sorrow" — but no consumer of those topics exists in the UI. The library page renders a flat alphabetical list with a search bar. The liturgical templates in `liturgical-templates.ts` define slot-to-query mappings, proving the liturgical categorization is valuable, but that structure isn't exposed to users for browsing.

**What ships:**
- Liturgical section browser: top-level categories matching the service structure (Opening, Shema & Its Blessings, Torah Service, Closing) — each shows all matching songs
- Faceted filters: key signature dropdown, topic tags, BPM range — combine freely with text search
- "Songs like this" recommendations: when viewing a song, show others with matching topics or liturgical function
- Usage frequency: track which songs appear in setlists most often, surface "congregation favorites" and "rarely used" categories
- Key compatibility view: when building a setlist, highlight songs that are in compatible keys for smooth transitions (e.g., relative major/minor, circle-of-fifths neighbors)

**Impact:** The music director goes from "I know we have a Mi Chamocha somewhere" to "show me all our Mi Chamocha settings, sorted by how often we use them, filtered to keys that work with our current setlist flow." Discovery time drops from minutes to seconds.

## 4. End-to-End Test Infrastructure

**The problem:** The app has 273 unit tests — all on utility functions (chord transposition, music math, Fuse search, rate limiting). Zero tests on React components, zero tests on API routes, zero end-to-end tests. The setlist editor, performance view, admin panel, print pipeline, auth flow, and every user-facing feature are completely untested. Every deployment is a manual QA session. The v3.1 cleanup found conditional hooks in AdminSections that had been shipping broken for who-knows-how-long because nothing tested it.

**The evidence:** `vitest.config.ts` runs only `*.test.ts` files, all in `src/lib/`. No `@testing-library/react` in `package.json`. No Playwright or Cypress. No API route test harness. The closest thing to integration testing is "does `tsc --noEmit` pass?"

**What ships:**
- **Playwright E2E suite**: core user flows — sign in → browse library → create setlist → add songs → enter performance mode → navigate between songs → print packet. Runs against a local dev server with Firestore emulator
- **API route integration tests**: test each route with real HTTP requests against the emulator — auth, library list, setlist CRUD, print generation, admin actions. Catches the kind of bugs that TypeScript can't (wrong status codes, missing error handling, auth bypass)
- **Component tests**: React Testing Library for critical interactive components — SetlistEditor drag-and-drop, PerformerView swipe navigation, SmartTransposer chord rendering, MusicianProfileSettings form
- **CI pipeline**: GitHub Actions runs the full suite on every push — unit + component + API + E2E. Block merge on failure
- **Visual regression**: Playwright screenshot comparison for performance mode layout, print output formatting, mobile responsive breakpoints

**Impact:** Deploy with confidence instead of crossed fingers. Catch regressions before users do. The test suite becomes living documentation of how every feature is supposed to work.

## 5. Multi-Voice Part Management

**The problem:** A worship band has guitar, piano, bass, drums, vocals, and sometimes brass or strings. Currently, everyone sees the same PDF for each song — typically a lead sheet with melody and chords. But the pianist needs a different arrangement than the guitarist. The bassist needs a chord chart, not a melody line. The drummer needs a rhythm chart. The data model already has `leadMusician` on `SetlistTrack` and `MusicianProfile` with `instrument` — but there's no way to associate multiple files with a single song, or to show different charts to different musicians.

**The evidence:** `SetlistTrack.fileId` is a single string — one file per track. `MusicianProfile.instrument` is set but never used for view filtering. The print route generates one packet for everyone. The performance view shows the same PDF regardless of who's logged in. A guitarist and a pianist sitting next to each other see identical screens.

**What ships:**
- **Song entity** (new): decouples "the song" from "the chart." A song has a title, key, and liturgical metadata. It links to multiple files — lead sheet, guitar chart, piano part, rhythm chart, etc. Each file is tagged with its voice/instrument
- **Per-musician performance view**: when entering performance mode, the app checks the musician's instrument profile and shows their part. Guitarist sees the guitar chart, pianist sees the piano arrangement, everyone else sees the lead sheet as fallback
- **Per-musician print packets**: the print pipeline generates instrument-specific packets. The music director prints one for each stand, not one for everyone
- **Bulk upload for parts**: when adding a new song, upload multiple PDFs at once — "lead sheet," "guitar," "piano," "rhythm" — and tag each by voice
- **Missing parts dashboard**: admin view showing which songs have only a lead sheet vs. full parts, so the music director knows where to invest arrangement time

**Impact:** Musicians get charts tailored to their instrument instead of squinting at a lead sheet and mentally extracting their part. The music director can distribute real parts. The app becomes infrastructure for a band, not just a songbook.

## Recommended Priority

| Feature | Effort | Musician Value | Music Director Value | Architectural Value |
|---------|--------|---------------|---------------------|-------------------|
| 1. Real-Time Collab | Large | Medium | Very High | Very High |
| 2. Background PDF Pipeline | Medium | Medium | High | Very High |
| 3. Smart Library Browser | Medium | Medium | Very High | Medium |
| 4. E2E Test Infrastructure | Medium | None (indirect) | None (indirect) | Critical |
| 5. Multi-Voice Parts | Large | Very High | Very High | High |

**If stability is the priority:** #4 (Tests) + #2 (PDF Pipeline). The test suite prevents regressions and the async pipeline eliminates the most fragile part of the system. Both are invisible to users but transformative for reliability.

**If features are the priority:** #3 (Smart Browser) + #5 (Multi-Voice). These are the features musicians will *feel* — browsing a categorized library and seeing instrument-specific charts changes the daily experience.

**If collaboration is the priority:** #1 (Real-Time Collab) + #3 (Smart Browser). Together these make the app a proper planning tool rather than a document viewer with a list attached.
