## Part 1: Project Health Assessment

### What's Working Well

**Architecture is clean.** Clear separation: API routes handle auth and data, components handle display, lib files handle logic. The `requireAuth()` middleware eliminated auth boilerplate across all 19 routes. Zustand stores are scoped and minimal. No prop-drilling messes.

**Testing is solid for core logic.** 326 tests covering music-math (transposition, chord parsing), liturgical calendar, templates, print pipeline, rate limiting, caching, and type validation. The tests that exist are meaningful — they've caught real regressions (the Unicode ♯/♭ bug, the A#m→Bm correction).

**The bridge architecture is production-ready.** Heartbeat, DHCP guard, sleep detection, X32 auto-reconnect, duplicate detection, one-click installer. This went from "experimental" to "set it and forget it" in one session.

**Print pipeline is sophisticated.** Background PDF generation with chord extraction, per-musician transposition, result caching, and batch "Print All Packets" for the entire ensemble. This is the feature that makes the app irreplaceable.

**Liturgical intelligence exists.** Hebrew calendar integration, parasha lookup, template-based setlist generation ("Build me a setlist for this Friday"), seasonal awareness. This is infrastructure no competing app has.

---

### Failure Points & Risks

#### 🔴 Critical

**1. `build-info.json` is frozen at v2.2.0.**
We shipped v3.0, v3.1, and are deep into what should be v3.5+. But the version file says 2.2.0 from weeks ago. The changelog hasn't been updated since the UI restructure. Anyone checking the footer or about screen gets wrong information. The version number needs to be a source of truth, ideally auto-incremented on deploy.

**2. Firestore rules don't cover `library_index` or `chordData`.**
These collections are only accessed via the admin SDK (server-side), so there's no active vulnerability. But it's a documentation gap and a latent risk: if anyone ever adds client-side reads against these collections, they'll get silent permission denials. The rules should explicitly deny client access to make the intent clear.

**3. The `setlists/{id}/history` subcollection has no Firestore rules.**
The audit trail writes server-side, so it works. But there's no rule preventing a client from reading or writing to it. Should be locked down to server-only (deny all client access) or admin-read.

**4. No monitoring or alerting.**
If the Vercel deployment fails, a cron job errors, or the Firebase quota spikes, nobody knows until a user reports it. There's no Sentry, no UptimeRobot, no Firebase alerting configured. For an app used during live services, this is a real risk.

#### 🟡 Significant

**5. Offline infrastructure exists but isn't connected.**
The `useOfflineManager` hook, `useOfflineSync` hook, and `offline-store.ts` (IndexedDB) are all built. The PWA service worker caches PDFs via Workbox. But there's no "Download for Offline" button visible to users. The library-cache.ts (IndexedDB for the file index) works but there's no UI indicator showing offline status or cache freshness. Musicians don't know they can use the app offline.

**6. No component-level tests.**
All 326 tests are unit tests on lib functions. Zero tests on React components. The admin panel (652 lines), setlist editor (283 lines), and performance toolbar (253 lines) have no test coverage. A refactor or dependency upgrade could break the UI silently.

**7. Two parallel auth middleware systems.**
Both `src/lib/api-auth.ts` (the `requireAuth`/`withAuth` pattern) and `src/lib/api-middleware.ts` (the `withAuth` wrapper with rate limiting) exist. Some routes use one, some use the other. This creates confusion about which pattern to use and risks inconsistent behavior.

**8. The AI chat agent has no guardrails on destructive actions.**
The chat API can execute `REMOVE_FROM_SETLIST`, `ADMIN_ACTION` (set roles), and arbitrary navigation. There's no confirmation step and no undo. An AI hallucination could delete setlist tracks or change a user's role.

**9. Enrichment engine has no retry or failure tracking.**
The nightly cron processes 20 files per run. If Gemini returns garbage JSON for a file, that file is marked as failed but the error isn't surfaced anywhere. After enough failures, the same files get retried endlessly. There should be a `failedAt` / `failCount` field to skip chronic failures.

#### 🟢 Minor

**10. AdminSections.tsx is 652 lines.** It's the largest component and handles sound system, user management, sync controls, and congregation config all in one file. It works, but it's approaching the point where changes become risky.

**11. The `api-middleware.ts` rate limiter (`globalLimiter`) isn't connected.** Rate limiting was properly wired via `checkRateLimit()` in the rate-limit.ts rewrite, but the older middleware wrapper still has a disconnected `globalLimiter` reference that does nothing.

**12. No backup strategy for Firestore data.** If the Firestore database is corrupted or accidentally wiped, there's no automated backup. Firebase offers scheduled exports to Cloud Storage, but they're not configured.

---

### Complexity vs. Value Assessment

**Overcomplicated for its current use:**

- **Multi-congregation support** (`CongregationProvider`, feature flags, configurable branding). Fully built but CRC is the only user. The abstraction adds indirection without current benefit. Not harmful, but premature.

- **Two separate offline systems.** `useOfflineManager` (Cache API) and `useOfflineSync` + `offline-store.ts` (IndexedDB). They do slightly different things but neither is fully wired into the UI. Should be consolidated into one system with one clear UX.

**Simpler than it should be:**

- **Error handling in the chat agent.** The Gemini response is parsed as JSON with a single try/catch. If the AI returns malformed JSON (which happens), the user sees a generic "Something went wrong" with no retry option.

- **Setlist track ordering has no conflict resolution.** Two people can reorder tracks simultaneously. Last writer wins. For a collaborative editing feature, this needs at minimum optimistic locking or operational transforms.

---

### What's Glaringly Missing

1. **Search within a song.** Musicians can find songs by name, key, or topic. But they can't search *within* a chart — "find the bridge," "where's the key change," "show me the coda." The chord data is already extracted; this is about exposing it.

2. **Notifications.** When a setlist is updated, a chart is replaced, or a new service is published, musicians find out by opening the app and checking. There's no push notification, no email digest, no "what changed since you last looked." The `lastViewedAt` data exists in presence but isn't used for this.

3. **Analytics / usage data.** How many musicians use the app each week? Which songs are most viewed? Which setlists have the most engagement? There's no telemetry. Even basic page-view tracking would help prioritize features.

4. **Bulk operations in admin.** Approving users, assigning roles, managing the library — all one-at-a-time. No multi-select, no bulk approve, no "add these 5 songs to this setlist."

5. **Version history for setlist tracks.** The audit trail logs *that* tracks changed but not *what* changed (no diff). If someone accidentally deletes 3 songs from a setlist, there's no way to see what was there before.

## Part 3: v4.1 Release Plan

### Theme: "Reliability, Visibility, Practice"

v4.1 focuses on three goals:
1. **Make what exists actually work end-to-end** (offline, monitoring, version tracking)
2. **Give musicians reasons to open the app between services** (practice dashboard, notifications)
3. **Give the music director visibility** (analytics, preparation tracking, better admin tools)

---

### Phase A — Housekeeping & Hardening (1 session)

Quick wins that fix the gaps identified above.

**A1. Version management overhaul**
- Auto-increment version in `build-info.json` from git tags
- Add version display to footer and admin panel
- Changelog auto-generated from conventional commit messages
- Tag the current state as `v4.0.0`

**A2. Firestore rules completion**
- Add explicit deny rules for `library_index` (server-only)
- Add explicit deny rules for `chordData` subcollections
- Add read-only admin rules for `setlists/{id}/history`
- Add rules for `config/monitor.bridge` (server-write, client-read)

**A3. Auth middleware consolidation**
- Remove the old `api-middleware.ts` wrapper
- All routes standardized on `requireAuth()` / `withAuth()` from `api-auth.ts`
- Remove dead `globalLimiter` reference

**A4. Enrichment failure tracking**
- Add `metadata.failCount` and `metadata.lastFailure` fields
- Cron skips files with 3+ failures
- Admin panel shows "X files failed enrichment" with retry button

**A5. Error monitoring**
- Add Sentry (free tier: 5K errors/month) for client + API
- Source maps uploaded on deploy
- Critical errors (auth failures, Firestore errors, bridge disconnects) auto-reported

---

### Phase B — Offline Done Right (1 session)

Complete the offline story that's 80% built.

**B1. Consolidate offline systems**
- Merge `useOfflineManager` and `useOfflineSync` into single `useOffline` hook
- Single IndexedDB database for both file index cache and PDF blobs
- Remove Cache API approach (redundant with Workbox PWA caching)

**B2. "Download for Offline" UI**
- Button on setlist view: "Make Available Offline" → downloads all PDFs in the setlist
- Progress indicator during download
- Offline badge on setlists that are cached
- Per-song offline indicator in library view

**B3. Offline status bar**
- Global indicator: "Online" / "Offline — using cached data"
- When offline: library loads from IndexedDB instantly, search works locally
- When back online: background sync pushes any pending changes (annotations, preferences)

**B4. Smart pre-caching**
- When a musician opens any setlist, pre-fetch all PDFs in background
- Cache the next 2 upcoming setlists automatically (by event date)
- Evict PDFs not accessed in 60 days

---

### Phase C — Practice Dashboard & Notifications (1-2 sessions)

The feature that turns this from "reference tool" into "daily companion."

**C1. "Your Week" dashboard section**
- Replace the generic homepage setlist list with a personalized view
- Shows upcoming setlists the musician is involved in (by date)
- Each setlist shows: preparation progress ring ("4/7 charts reviewed"), time until event
- "What's changed" badges on songs updated since last viewed

**C2. Preparation tracking**
- Track when each user views each chart (lightweight: write `lastViewedAt` to `users/{uid}/songPreferences/{fileId}`)
- Progress = songs viewed / total songs in setlist
- Music director sees aggregate preparation in admin: "Alice: 7/7 ✓, Bob: 3/7, Carlos: 0/7"

**C3. Notification system**
- Firestore `notifications` collection per user
- Triggers: setlist published, setlist updated (tracks changed), new chart uploaded, role changed
- In-app notification bell with unread count (simple, no push notifications yet)
- "What's new since your last visit" summary on homepage

**C4. Push notifications (optional)**
- Firebase Cloud Messaging integration
- "Shabbat setlist published" → push to all authorized musicians
- Configurable: users opt in/out per notification type
- Web push only (no native app needed — PWA supports this)

---

### Phase D — Rehearsal Mode (1-2 sessions)

The feature that makes musicians *want* to practice.

**D1. Audio player in performance mode**
- When a track has `audioFileId`, show a play bar at the bottom of the chart
- Basic controls: play/pause, scrub, volume
- Audio streams from Firebase Storage (already stored there)

**D2. Tempo control**
- Slider: 0.5x → 1.5x playback speed
- Pitch-corrected time stretching via Tone.js GrainPlayer
- Tempo saved per-song per-user in preferences

**D3. Loop markers**
- Tap "A" to set loop start, tap "B" to set loop end
- Section loops automatically until cleared
- Visual highlight on the timeline

**D4. Practice time tracking**
- Track total practice time per song per user
- Lightweight: increment counter in Firestore on session end
- Visible to the musician ("You've practiced this 3 times, 12 min total")
- Aggregate visible to music director in admin

---

### Phase E — Admin & Quality of Life (1 session)

**E1. Bulk operations**
- Multi-select in user management (bulk approve, bulk role change)
- Multi-select in library (bulk add to setlist, bulk tag)
- "Select all pending users" shortcut

**E2. Setlist diff / undo**
- Audit trail enhanced: store full track list snapshot on each change
- "View changes" shows what was added/removed/reordered
- One-click "Restore to previous version" from history

**E3. Admin panel decomposition**
- Split 652-line `AdminSections.tsx` into separate files:
  - `SoundSystemSection.tsx`
  - `UserManagementSection.tsx`
  - `LibrarySyncSection.tsx`
  - `CongregationSection.tsx`

**E4. Search within songs**
- New search mode: "Find in charts" searches extracted chord/text data
- Results show which songs contain the search term and where
- Useful for: "which songs are in D minor," "where do we play Mi Chamocha"

### What's Deliberately Deferred

| Feature | Why |
|---------|-----|
| E2E tests (Playwright) | CI was unreliable. Revisit when there's a dedicated test environment. |
| Component-level tests | High effort, moderate value. Invest in E2E instead when stable. |
| Multi-congregation | Only CRC uses the app. Build when there's a second customer. |
| Firestore backups | Configure when the data is large enough to matter (~1000+ documents). |
| Code signing for bridge exe | Requires a certificate ($200+/year). SmartScreen warning is documented. |
| Native mobile app | PWA covers 95% of needs. Not worth the maintenance overhead. |
