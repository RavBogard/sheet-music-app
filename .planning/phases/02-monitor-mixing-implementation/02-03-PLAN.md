<objective>
Connection reliability, graceful degradation, and bridge hardening

Purpose: During a live service, the connection between tablets and the X32 mixer must be bulletproof. When things go wrong, the app must degrade gracefully -- showing clear status, preserving last-known values, and never breaking non-monitor features. The bridge must auto-reconnect indefinitely rather than giving up after 10 minutes. This plan hardens both the client-side status display and the bridge-side reconnection logic.

Output: Enhanced ConnectionIndicator with bridge/mixer status differentiation, disconnected-state UI with last-known values, hardened bridge reconnection with exponential backoff, tests for all degradation scenarios.
</objective>

  <behavior>
    - attemptReconnect retries indefinitely (no MAX_ATTEMPTS cap) during a service
    - Backoff: starts at 2s, doubles each attempt, caps at 60s (2, 4, 8, 16, 32, 60, 60, 60...)
    - On successful reconnect, backoff resets to 2s for next disconnection
    - If reconnect succeeds, emits "reconnected" event
    - Concurrent attemptReconnect calls are deduplicated (reconnecting flag)
    - Health check continues running during reconnection attempts
  </behavior>
  <action>
    1. **Modify attemptReconnect in bridge/src/x32-client.ts:**
       - Remove `MAX_ATTEMPTS = 60` cap. Replace with infinite loop (`while (true)`).
       - Replace fixed `INTERVAL = 10000` with exponential backoff: start at 2000ms, double each attempt, cap at 60000ms.
       - On successful reconnect: reset the backoff delay for next disconnection event.
       - Add a `stopReconnecting()` method (called on bridge shutdown/destroy) to break the loop.
       - Log each attempt with the current backoff interval for debugging.
       - Keep the existing `/xinfo` probe with 5s timeout per attempt.

    2. **Improve health check robustness (per RESEARCH.md Pitfall 4):**
       - The existing 20s silence threshold is correct for marking disconnected.
       - Add a secondary liveness signal: if we're receiving Firestore state updates (the bridge writes state every 100ms when mixer is active), the bridge is online even if the heartbeat write fails.
       - This secondary signal is bridge-side only: if the X32Client hasn't received an OSC message in 20s, it IS disconnected from the mixer. Keep this logic as-is.
       - The concern from Pitfall 4 is about the iPad side (heartbeat staleness false positive). The bridge side is correct.

       - Test that successful reconnect resets the backoff.
       - Test that concurrent attemptReconnect calls are deduplicated.
       - These tests should mock the UDP socket and timer (vitest fake timers + mock dgram).
