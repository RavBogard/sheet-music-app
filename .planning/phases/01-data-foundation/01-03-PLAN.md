Output: PublishDialog shows conditional warning/success toasts based on emailError field. New resend-email API endpoint allows retrying email delivery. Resend button appears in PublishDialog when email errors occurred.
</objective>

Create a new POST endpoint at `/api/setlist/resend-email` that re-sends email notifications for a published setlist.

**Authentication and authorization:**
- Use `requireAuth` from `@/lib/api-auth` to verify the request has a valid Firebase auth token
- Check that the authenticated user is the setlist owner, a band_leader, or an admin. Load the setlist from Firestore and compare `userId` field to the auth result. If not authorized, return 403.
- Use `checkRateLimit` from `@/lib/rate-limit` with a reasonable limit (e.g., 5 resends per setlist per hour) to prevent email spam

**Request validation:**
- Validate request body with Zod: `{ setlistId: z.string().min(1) }`
- Return 400 on validation failure

**Logic:**
1. Load the setlist document from Firestore using the setlistId
2. Verify the setlist exists and is published (has `publishedAt` or `isPublic` flag). If not published, return 400 with "Setlist is not published"
3. Load the congregation/band members who should receive the email (same query the publish route uses to determine recipients)
4. Call `emailAllMembers()` from `@/lib/email` with the setlist metadata and member list
5. Return the result: `{ success: true, sent: N, failed: M, errors: [...] }`
6. If emailAllMembers throws, catch and return 500 with error message

**Follow existing patterns:**
- Look at `src/app/api/setlist/publish/route.ts` for the pattern of loading setlist data, checking auth, and calling emailAllMembers
- Use the same Firestore collection references and member query patterns
- Use `NextResponse.json()` for all responses
- Use `logger.error()` for error logging

**Security (per RESEARCH.md Pitfall 5):**
- Auth check is mandatory
- Rate limiting is mandatory
- Only setlist owner, band_leader, or admin can trigger resend
