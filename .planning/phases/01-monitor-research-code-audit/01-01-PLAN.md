  <action>
This is a research task that produces measured data. Follow this sequence:

1. **X32 Emulator/Mock Setup:**
   - First, try downloading and running the pmaillot X32 emulator (https://github.com/pmaillot/X32-Behringer) on Windows 11. If it doesn't build/run cleanly, create a minimal Node.js X32 mock server at `bridge/src/__tests__/x32-mock-server.ts` that:
     - Listens on UDP port 10023 (standard X32 port)
     - Responds to `/xinfo` with a valid X32 info response
     - Responds to `/xremote` (subscription renewal)
     - Handles `/ch/XX/mix/fader` get/set commands
     - Handles `/bus/X/mix/fader` get/set commands
     - Echoes state changes back (simulating the X32's behavior)
   - The mock only needs to handle the OSC addresses the bridge actually uses (check `bridge/src/x32-client.ts` for the specific addresses)

2. **Firestore Latency Measurement:**
   - Create a test utility at `src/lib/__tests__/bridge-latency.test.ts` that measures the full round-trip:
     - iPad sends command (addDoc to commands/pending)
     - Bridge receives command (onSnapshot on commands subcollection)
     - Bridge executes on X32 (OSC over UDP)
     - X32 echoes state back (OSC response)
     - Bridge writes updated state (set doc on monitor-live/state)
     - iPad receives updated state (onSnapshot on state doc)
   - Measure using `performance.now()` timestamps
   - CRITICAL: Measure cross-device latency, not local-write latency (see Pitfall 1 in RESEARCH.md)
   - Use `metadata.hasPendingWrites` to distinguish local cache hits from server-confirmed updates
   - Run at least 20 measurements and report min/median/p95/max
   - Test with both single fader changes AND rapid fader drag (20+ changes/sec for 5 seconds)
   - Threshold: < 200ms is acceptable for fader control, > 500ms is unusable

3. **Alternative Architecture Evaluation:**
   - Document the Firestore-only approach (current) with measured latency
   - Evaluate WebSocket alternative: what would it take to add a direct WebSocket from browser to bridge? Document the tradeoffs (self-signed certs on iPad, IP configuration needed, but lower latency)
   - Evaluate hybrid approach: Firestore for state sync, WebSocket for low-latency commands. Document when this is worth the complexity
   - For each approach document: latency, reliability, install complexity, iPad configuration burden

4. **Failure Mode Testing:**
   - Test bridge-side disconnect: stop the X32 mock for 30 seconds, verify bridge auto-reconnects and state updates resume (check `X32Client.discover()` reconnect loop -- 10s intervals, 60 attempts)
   - Test simulated client-side behavior: verify that if Firestore `onSnapshot` reconnects after a gap, state resumes correctly
   - Document each failure mode, recovery time, and user-visible impact

5. **Deployment Model Evaluation:**
   - Document production PC approach (Electron already configured, auto-start, auto-update)
   - Document Raspberry Pi approach (always-on, but requires hardware management, unclear Electron performance)
   - Recommend one with rationale based on the venue's actual setup (production PC runs during services, bridge already has wake detection)

  <name>Task 2: Write architecture decision document with all findings</name>
  <files>docs/bridge-architecture-decision.md</files>
  <action>
Synthesize all research findings from Task 1 into a comprehensive architecture decision document at `docs/bridge-architecture-decision.md`. Structure:

1. **Executive Summary** -- One paragraph: what architecture, what deployment, why.

2. **Transport Architecture Decision**
   - Recommended approach (Firestore-only, WebSocket, or hybrid)
   - Measured latency data (table with min/median/p95/max for each scenario)
   - Why the recommended approach wins (with specific data points)
   - What would trigger switching to an alternative (e.g., "if latency exceeds X in production, switch to hybrid")

3. **Deployment Model Decision**
   - Recommended: production PC or Raspberry Pi
   - Rationale with specific tradeoffs
   - Fallback if recommended doesn't work

4. **Install Experience**
   - Step-by-step install process (written for a non-technical person)
   - What the user downloads, clicks, enters (setup code flow)
   - What happens automatically (auto-start, auto-update, X32 discovery)
   - Screenshots or descriptions of each step

5. **Failure Modes and Recovery**
   - Table: failure mode, recovery mechanism, recovery time, user impact
   - Bridge-side failures: X32 disconnect, network drop, bridge crash, PC sleep
   - Client-side failures: WiFi drop, Firestore disconnect, app backgrounding
   - For each: is the recovery automatic? What does the musician see?

6. **Firestore Write Rate Analysis**
   - Measured write rates during fader drag
   - Document size analysis (~4KB calculated, actual measured)
   - Any rate limiting observed
   - Cost implications at expected usage (3-5 musicians, 1-2 hour services)

7. **X32 Development Environment**
   - What emulator/mock to use for day-to-day development
   - How to set it up
   - Limitations vs real hardware
   - When real hardware testing is required

8. **Open Risks**
   - Things that can only be validated with real X32 at the venue
   - Dependencies on Firestore pricing/limits at scale
   - iPad-specific behaviors (background tab throttling, wake lock interaction)

Per user decision: The PoC MUST run through the actual FaderStrip, QuickMonitorPanel, and ConnectionIndicator components already in the app -- not a separate CLI or minimal page. Document how to exercise the PoC through the existing UI.
